## 3. 과제 2와의 관계 분석

### 3.1 두 과제 본질 비교

| 측면      | 과제 1 (현재)      | 과제 2 (예정)                                                 |
| --------- | ------------------ | ------------------------------------------------------------- |

| 핵심 기술 | RAG · LLM         | OCR ·**비정형 표 정규화** · 코드 매핑 · 룰 엔진      |
| 판단 근거 | 약관 조항          | 약관 조항 + EDI 코드 매핑                                     |

### 3.2 핵심 통찰

> 과제 2의 **면·부책 판정**은 결국 "이 EDI 코드 항목이 약관상 보상 대상인가"를 묻는다. 이는 과제 1의 **약관 정형 검색(보상 판정 모드)**과 같은 질문이다.

따라서 두 과제는 별도 시스템이 아니라 **같은 플랫폼의 두 진입점**으로 가는 것이 맞다. 과제 1의 RAG/Graph가 *판단 엔진*, 과제 2가 *자동화 워크플로우*가 된다.

### 3.3 통합 아키텍처 옵션

| 옵션                          | 구조                                       | 적합성(캡스톤 범위)               |
| ----------------------------- | ------------------------------------------ | --------------------------------- |
| A — 별도 앱 + REST           | 인덱스·인증 이중화, 도메인 분리           | 낮음 (캡스톤 일정·인력에 비효율) |
| B — 단일 플랫폼 페이지 분기  | [챗봇][보험금 계산] 두 페이지, 공유 인프라 | **권장**                    |
| C — 마이크로서비스 + Gateway | 정식 운영 단계 구조                        | 캡스톤 범위 외 (Phase E 권고)     |

→ 옵션 B로 베타까지 완주. 옵션 C 전환은 회사 측 정식 운영 단계 권고 사항.

## 4. 과제 1 업데이트 — OCR · 메타 · 그래프

### 4.1 스캔본 PDF + 표·이미지 + OCR

베타 단계에서 추가 투입될 약관 문서 풀에는 **스캔본·이미지 PDF·복합 레이아웃** 표가 섞여 있다. 텍스트 추출만으로는 검색이 불가하므로 OCR이 필수.

#### 4.1.1 OCR 도구 비교 (단일 회사·사내 사용 기준)

| 옵션                                     | 한국어 정확도 | 표/레이아웃    | 비용          | 적합 영역                    |
| ---------------------------------------- | ------------- | -------------- | ------------- | ---------------------------- |
| Tesseract                                | 보통(~85%)    | 약함           | 무료          | 단순 텍스트                  |
| PaddleOCR + PP-Structure                 | 양호(~90%)    | **강함** | 무료          | **약관 1차 권장**      |
| Naver CLOVA OCR                          | 매우 높음     | 양호           | 월 1만건 무료 | 영수증·진단서 권장 (과제 2) |
| Upstage Document AI / Google Document AI | 매우 높음     | 매우 강함      | 유료          | 회사 정식 운영 단계          |

**약관 OCR 전략 (베타 1차)**: PaddleOCR + PP-Structure로 (1) 텍스트, (2) 표, (3) 이미지 영역을 분리 인식 → 각각 다른 청크 타입으로 인덱싱.

#### 4.1.2 다중 콘텐츠 타입 보존 인덱싱

스캔본 약관에서 추출되는 콘텐츠는 단순 텍스트가 아니다. 청크 메타에 콘텐츠 타입을 명시해 검색 후 적절히 표현한다.

| 콘텐츠 타입    | 저장 형식                                              | UI 표현                               |
| -------------- | ------------------------------------------------------ | ------------------------------------- |
| 본문 텍스트    | 일반 텍스트 청크                                       | 기존과 동일                           |
| 표             | **JSON(헤더+행) + 텍스트 직렬화 청크 동시 저장** | UI에 표 형식 + 원문 텍스트 둘 다 노출 |
| 이미지/도식    | 이미지 파일 + 캡션·위치 텍스트 청크                   | 출처 expander에 이미지 미리보기       |
| 수식/특수 기호 | 텍스트 청크 + raw 보존                                 | 그대로 노출                           |

청크 메타 추가 필드: `content_type ∈ {"text","table","image","formula"}`, `source_method ∈ {"native","ocr_paddle","ocr_clova"}`, `confidence` (OCR 신뢰도).

표는 검색 시 `text` 직렬화로 매칭하고, UI 렌더 시 `json` 형식으로 다시 표시. 이렇게 두 표현을 함께 두면 BM25/임베딩 검색은 가능하면서도 사용자 가독성을 잃지 않는다.

### 4.2 메타데이터 강화 (100개+ 약관 대비)

현재 메타 위에 다음 필드를 추가한다.

- `insurance_company` (자사=신한EZ / 타사명)
- `is_own_company`: bool (자사 약관 여부 — UI에서 자사·타사 분리 표시 가능)
- `product_name` / `product_type` (건강·실손·상해·해외여행·장기치료)
- `effective_date` / `version` (개정 이력 추적)
- `coverage_category` (질병급여·질병비급여·3대비급여·상해급여·상해비급여·입원·외래·약제)
- `clause_type` (보상하는 사항·보상하지 않는 사항·면책·정의·기타)

UI/검색 개선:

- 사이드바에 자사·타사 토글, 상품·시행일 범위 필터
- 자동 라우팅: 질의에 회사명·상품명 포함 시 해당 약관만 우선 검색
- **약관 비교 모드**: 동일 보장종목을 자사·타사 N개 약관에서 동시 검색 (자사 직원이 경쟁 상품과의 차이 파악)

### 4.3 GraphDB 도입 필요성 평가 (베타 안에서 게이트로)

> **결정 정책**: GraphDB·GraphRAG는 *베타 완성을 위해 필수인지*를 평가한 후 도입한다. 메타 강화 + 강화된 RAG로 베타 목표(약관 100개+ 검색·약관 비교·면·부책 판정 정확도)가 충족되면 도입은 회사 측 정식 운영 단계로 미룬다.

평가 기준 (Phase B 종료 시점에 확인):

| 신호                                                                                 | 도입 권장  | 비도입 권장     |
| ------------------------------------------------------------------------------------ | ---------- | --------------- |
| 다중 hop 추론 필요 (예: "자사 A 상품의 보장이 타사 B 상품의 어떤 조항과 충돌하는가") | 자주 발생  | 거의 발생 안 함 |
| 보장종목·코드·면책 간 관계가 RAG 답변에서 누락                                     | 빈번       | 드묾            |
| 약관 비교 모드가 텍스트 검색만으로 충분                                              | —         | 충분            |
| 100개+ 약관에서 검색 노이즈가 메타 필터로 해결 안 됨                                 | 해결 안 됨 | 해결됨          |

→ 권장 시 베타 마지막 마일스톤(M25)에서 **PoC 수준 GraphRAG**(20~50개 약관 한정, Neo4j 무료 또는 NetworkX 인메모리)로 도입. 본격 운영(Neo4j 클러스터·전체 약관 그래프)은 회사 확장 단계.

## 5. 통합 로드맵 (Phase A → D, 캡스톤 범위)

> **재배치 핵심**: 챗봇 베타 완성(Phase B + Phase C)이 과제 2(Phase D)보다 먼저 끝난다.

| Phase                                                             | 기간    | 핵심 산출                                                                                                                                   | 마일스톤   | 베타 배포 시점                  |
| ----------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------- |
| **A. 알파 종료 보정**                                       | ~2주    | 출처 첨부 보정, 디버그 로깅, smoke_qa v2 평가, 알파 종료 보고서                                                                             | M-α-final | —                              |
| **B. 베타 1 — 다중 약관 + 메타 강화**                      | 1~2개월 | 메타 스키마 확장, 100개 약관 자동 인덱싱, 사이드바 필터(자사·타사 토글 포함), 약관 비교 모드                                               | M18~M21    | —                              |
| **C. 베타 2 — 스캔본 OCR + 그래프 도입 평가 → 베타 배포** | 2개월   | OCR 파이프라인(PaddleOCR + PP-Structure), 표·이미지 보존 인덱싱, GraphDB 도입 필요성 평가, (필요 시) GraphRAG PoC,**챗봇 베타 배포** | M22~M25    | ✅**이 끝에서 베타 배포** |
| **D. 과제 2 — 영수증·진단서 자동 처리 + 보험금 계산**     | 3~4개월 | 비정형 표 → 데이터프레임 추출, 서류 분류, EDI 매핑, RAG ↔ 면·부책 호출, 보험금 계산 룰 엔진                                              | M26~M30    | —                              |

(이전 보고서의 Phase E는 9장 "회사 확장 권고"로 이전.)

각 Phase의 외부 의존:

```
Phase A ── (없음, 내부 보정만)
   │
   ▼
Phase B ── 100개 약관 입수 의존
   │
   ▼
Phase C ── 스캔본 약관 입수 의존, OCR 도구 라이선스 정책 확인
   │      (게이트) GraphDB 도입 평가 결과
   │
   ▼  ── 챗봇 베타 배포
   │
Phase D ── EDI 50만 행 표준 모델 발주 수령 의존
           비급여 사업자번호 매핑 데이터 의존
           Phase C에서 베타가 안정 운영 중일 것
```

### 5.1 Phase A 상세 (알파 종료 보정, ~2주)

- 출처 첨부를 "실제 답변에서 사용된 근거" 중심으로 좁히기
- Dense/BM25/RRF/Rerank 단계별 디버그 로그 (관리자 페이지에서 토글)
- smoke_qa v2 — 약관 정형 모드 10문항 추가, 자사 약관 보상 판정 케이스 포함
- 알파 종료 보고서 (성능 지표 v3 정리)

### 5.2 Phase B 상세 (베타 1 — 다중 약관 메타 강화, 1~2개월)

- **M18** — 메타 스키마 확장: `insurance_company`, `is_own_company`, `product_*`, `effective_date`, `version`, `coverage_category`, `clause_type` 추가. chunker 자동 추출 + 인덱싱 시 메타 yaml 동봉
- **M19** — 자동 인덱싱 파이프라인: `scripts/ingest_batch.py`로 약관 폴더 일괄 처리. 신규 약관 추가 시 1 명령으로 인덱스 갱신
- **M20** — 사이드바 필터 보강: **자사·타사 토글**, 상품·시행일·보장종목 다중 선택. 자동 라우팅(질의 회사명 추출)
- **M21** — 약관 비교 모드: 동일 보장종목 N개 회사 비교 표 (자사 직원의 경쟁 분석 시나리오)

### 5.3 Phase C 상세 (베타 2 — 스캔본·그래프 평가 → 베타 배포, 2개월)

- **M22** — OCR 파이프라인: PaddleOCR + PP-Structure로 텍스트·표·이미지 분리 인식. 약관 인제스트 시 자동 적용 (네이티브 텍스트가 있는 PDF는 텍스트 추출 우선, 빈 페이지·표 영역만 OCR로 폴백)
- **M23** — 다중 콘텐츠 청크 인덱싱: `content_type / source_method / confidence` 메타 추가, 표는 JSON+텍스트 직렬화 동시 저장, 이미지는 캡션 청크 + 파일 보관, UI 출처 expander에 표·이미지 렌더링 추가
- **M24** — GraphDB 도입 필요성 평가: 위 4.3 신호표를 기준으로 데이터·실측 근거 수집. 결과를 ADR(Architecture Decision Record)로 문서화
- **M25** — (조건부) GraphRAG PoC: 평가 결과 도입 권장이면, NetworkX 또는 Neo4j Community로 20~50개 약관 한정 그래프 구축. dense+BM25에 graph 점수 결합 RRF
- **베타 배포**: M22~M24(또는 M25)까지 완료한 시점에 신한EZ 사내 챗봇 베타 정식 배포

### 5.4 Phase D 상세 (과제 2 — 영수증 처리, 3~4개월)

- **M26** — 서류 입력·분류: 다중 파일 업로드, 자동 분류기(영수증/진단서/세부내역서). 룰 + LLM 보조 분류
- **M27** — **비정형 표 → 데이터프레임 추출 (핵심 모듈)**: 병원마다 다른 표 형식을 정형 데이터프레임으로 변환
  - 1차: pdfplumber·Camelot·Tabula로 텍스트형 표 추출
  - 2차: PaddleOCR PP-Structure(table)로 스캔/이미지 표 인식
  - 3차: layout-aware 후처리 — 헤더 자동 매칭(수가코드/항목명/단가/수량/금액/본인부담금/공단부담금 등 표준 컬럼), 합계 검산, 누락 행 감지
  - 결과: pandas DataFrame + 표준 컬럼 스키마 + 신뢰도 점수
  - 검증: 추출된 합계가 영수증 총액과 ±1원 이내 일치하는지 자동 체크
- **M28** — EDI 매핑 + 비급여 매핑: 50만 행 EDI 표준 모델 DB로 lookup. 비급여는 사업자번호 + 자체 코드 → 표준 매핑 테이블
- **M29** — RAG ↔ 면·부책 호출: 추출된 코드·보장종목을 입력으로 약관 정형 검색(보상 판정 모드)을 내부 호출. 답변을 면·부책 라벨로 정규화. (Phase C에서 GraphRAG 도입했다면 GraphRAG 호출)
- **M30** — 보험금 계산 룰 엔진 + 보고서: 공제·한도·중복 보장 차감 로직, 결과 보고서(고객용·사내용 PDF), 단건·배치 처리 두 모드

## 7. 권장 의사결정 항목 (사용자 결정 대기)

다음 단계 진입 전 결정 필요:

1. **Phase A 마무리 작업 범위** — 출처 보정·디버그 로깅·smoke_qa v2 모두 알파에 포함 vs 일부 베타 1로 미룸
2. **타사 약관 표시 정책** — 베타 UI에서 타사 약관 검색 결과를 자사와 동일하게 노출할지, 별도 표시할지
3. **OCR 1차 도구** — PaddleOCR(권장, 무료) vs CLOVA OCR(약관도 포함 시) — 약관 OCR 비용·정확도·속도 트레이드오프
4. **GraphDB 도입 평가 시점** — Phase C 안에서 평가(권장) vs Phase D와 병행
5. **EDI 50만 행 DB 발주 일정·인수 형식** — 발주 진행 상황과 인수 포맷 (SQL 덤프·CSV·API)
6. **사내 PDF·자료 클라우드 정책** — 베타 운영 환경(Streamlit Cloud vs 사내망)에 따라 어떤 자료까지 인덱싱 가능한지
7. **베타 배포 환경** — 현재 Streamlit Community Cloud 유지 vs 사내망 이전(보안 정책 의존)

## 9. 회사 측 정식 운영 확장 권고 (캡스톤 범위 외)

캡스톤 종료 후 신한EZ 측에서 정식 운영으로 이어가려 할 때 권장되는 확장 항목. 캡스톤 팀은 본 항목을 수행하지 않고 인수인계 문서로만 정리한다.

| 항목                | 내용                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------- |
| 마이크로서비스 분리 | 옵션 C — RAG·OCR/계산·인증·UI 각각 서비스로 분리, API gateway                           |
| 자체 GPU 인스턴스   | 사내 GPU(예: A6000·H100) 도입으로 exaone3.5 또는 더 큰 한국어 모델 운영, OpenAI 의존 축소  |
| GraphRAG 본격 운영  | (캡스톤에서 PoC만 했다면) Neo4j 클러스터로 100개+ 약관 전체 그래프, 다중 hop 추론 본격 활용 |
| 외부 객체 저장소    | 로그·인덱스·자산을 S3/R2/GCS에 영속화 (현재는 ephemeral)                                  |
| 운영 모니터링       | Prometheus + Grafana, 알림(Slack), 비용·성능 대시보드                                      |
| 사용자 관리 자동화  | SSO/OAuth 연동(사내 IdP), 사용자 라이프사이클 관리                                          |
| 비밀 관리           | Vault·AWS Secrets Manager 도입                                                             |
| CI/CD               | GitHub Actions/Jenkins 빌드·테스트·배포 파이프라인                                        |
| 보안·감사          | 외부 감사 로그 영속화, 접근 통제 강화, 데이터 분류·라벨링                                  |
| 약관 자동 수집      | 외부 공시 약관 크롤링·정기 갱신                                                            |

이 항목들은 모두 **신한EZ 정식 운영팀의 의사결정·예산이 필요한 작업**이며, 캡스톤 산출에 의존하지 않고도 도입 가능한 별도 트랙이다.

## 10. 결론 (한 줄 요약)

> **알파 종료 후 챗봇 베타 완성(Phase A→B→C, 약 3~4개월)을 우선 완료해 사내 배포한 뒤, 과제 2(보험금 자동 계산, Phase D)를 베타 위에 얹는다.** 그 과정에서 스캔본 OCR(표·이미지 포함)과 메타 강화는 베타에 필수 포함, GraphDB는 베타 안에서 도입 필요성 평가 후 PoC만 수행한다. 마이크로서비스·GPU 운영·GraphRAG 본격화는 회사 측 정식 운영 단계로 인수인계.
