## 1. 한눈에 보는 프로젝트 개요

### 1.1 프로젝트가 도달한 지점

이 프로젝트는 보험 문서를 찾아 답하는 단순한 질의응답 챗봇에서 출발했다. 약 3개월 동안 문서 정비, 검색, 근거 제시, 지식 구조화, 보상금 예상 계산, 사람의 승인, 운영 진단까지 범위를 넓히며 **보험 문서를 근거로 실무 판단을 지원하는 지식 운영 체계**로 발전했다.

현재 서비스의 핵심은 질문에 그럴듯한 문장을 생성하는 데 있지 않다. 답변의 출처를 보여 주고, 문서에서 확인되지 않는 내용은 단정하지 않으며, 계산 가능한 부분은 승인된 규칙으로 일관되게 처리하고, 불확실한 부분은 실무자 검토로 넘기는 데 있다.

### 1.2 서비스의 기본 구조

서비스는 크게 세 층으로 이해하면 된다.

1. **문서 근거 층**: 약관, 업무 자료, 표와 예시에서 질문과 관련된 내용을 찾고 출처를 연결한다.
2. **지식·검토 층**: 문서에서 발견한 개념, 동의어, 조건, 예외를 후보로 만들고 실무자의 승인 결과를 관리한다.
3. **판단 지원 층**: 승인된 기준과 입력값으로 예상 보상금을 계산하고, 자동 판단이 위험한 건은 검토 대상으로 분리한다.

세 층은 서로 연결되지만 역할은 분리되어 있다. 언어 모델은 질문을 이해하고 설명을 구성하는 역할을 맡으며, 최종 지급 여부나 금액을 임의로 결정하지 않는다.

### 1.3 프로젝트 전체 요약

| 영역 | 3개월 동안 한 일 | 현재 평가 |
|---|---|---|
| 문서 정비 | 복잡한 보험 문서의 본문·표·수치·쪽 정보를 복원하고 교정 기준을 마련 | 운영 가능한 교정 원천 확보 |
| 검색과 답변 | 키워드 검색과 의미 검색을 결합하고, 재정렬과 출처 제시를 적용 | 일반 질의응답에 사용 가능 |
| 지식 그래프 | 조항·조건·예외·근거의 관계를 구조화하고 시각화 | 조회·추적 가능, 품질 관리 지속 필요 |
| 지식 승인 | 개념과 동의어 후보를 만들고 승인·보류·거절·적용 상태를 관리 | 운영 반영, 사람의 검토 필수 |
| 예상 보상금 계산 | 세대·항목·공제·예외 조건을 승인된 규칙으로 계산 | 조건이 명확한 범위에서 사용 가능 |
| 실무 화면 | 대화, 출처 확인, 계산, 관리자 검토, 진단 기능을 하나의 웹 서비스로 통합 | 공식 사용 화면으로 정착 |
| 운영 체계 | 격리된 개발 공간, 독립 검토, 릴리스 기준, 운영 안내서 마련 | 기본 체계 확립, 잔여 검증 존재 |
| 오프라인 이전 | 새 장비에 옮기기 위한 설치 범위와 매뉴얼 설계 | 계획 단계, 실제 설치 검증 전 |

### 1.4 이 서비스가 지키는 경계

- 서비스는 **판단 보조 도구**이며 보험금 지급의 최종 결정자가 아니다.
- 출처가 없거나 서로 충돌하면 답을 확정하지 않는다.
- 문서에서 추출된 새 지식은 곧바로 운영 기준이 되지 않는다.
- 계산은 승인된 규칙과 확인된 입력값이 있을 때만 자동화한다.
- 불확실성은 숨기지 않고 검토 필요 상태로 남긴다.
- 모델을 바꾸는 것보다 문서, 검색, 규칙, 평가 절차를 먼저 점검한다.

### 2.2 주요 이정표

- **첫 번째 이정표 — 답변이 나오는 서비스**: 문서 검색, 대화, 출처 제시가 가능한 초기형을 확보했다.
- **두 번째 이정표 — 문서를 믿을 수 있는 서비스**: 표와 수치를 교정하고 원천 추적성을 갖췄다.
- **세 번째 이정표 — 계산을 설명할 수 있는 서비스**: 승인된 규칙으로 예상 금액을 계산하고 예외를 검토 대상으로 넘겼다.
- **네 번째 이정표 — 지식을 운영할 수 있는 서비스**: 후보를 사람이 승인한 뒤에만 실제 검색·그래프·규칙에 반영하도록 만들었다.
- **다섯 번째 이정표 — 실패를 숨기지 않는 서비스**: 무결성 오류, 불완전한 근거, 모호한 입력이 있으면 자동 처리를 중단하도록 강화했다.
- **현재 이정표 — 제한 조건이 명시된 안정 기준선**: 실무 사용은 가능하지만, 남은 회귀 오류와 현장 검증을 끝낸 뒤 최종 인수해야 한다.

## 3. 개발·협업 환경의 변화

### 3.1 로컬 중심에서 DGX 중심으로

초기에는 개발자의 로컬 컴퓨터에서 문서를 정리하고 화면을 빠르게 확인하는 방식이 효율적이었다. 그러나 문서량과 모델 규모가 커지고, 여러 종류의 검색 색인과 지식 그래프를 함께 다뤄야 하면서 로컬 환경만으로는 재현성과 성능을 유지하기 어려워졌다.

이후 역할을 분리했다.

- 로컬 컴퓨터는 작업 지시, 변경 검토, 문서 작성, 결과 확인을 담당했다.
- DGX는 실제 코드, 보험 문서, 모델, 검색 자료, 지식 그래프, 시험을 실행하는 기준 환경이 되었다.
- 두 환경은 보안 연결과 SSH를 통해 이어졌으며, 개발자는 로컬에서 DGX의 개인 작업공간을 제어했다.

이 전환으로 큰 모델과 대용량 데이터를 한곳에서 관리할 수 있었고, 실제 운영 조건과 유사한 상태에서 검증할 수 있게 되었다. 반면 연결 상태, 장비 재시작, 모델 준비 여부, 저장 공간 권한 같은 운영 변수가 개발 품질에 직접 영향을 주기 시작했다.

### 3.2 개인 작업공간과 보호된 운영 기준선

여러 사람이 같은 장비를 사용하므로 각자 격리된 작업공간에서 변경을 만들고 검증한 뒤, 검토를 거쳐 보호된 운영 기준선에 반영하는 구조를 채택했다. 데이터와 모델처럼 크거나 민감한 자산은 소스 버전 관리와 분리했다.

이 구조가 필요했던 이유는 단순했다.

- 한 사람의 실험이 다른 사람의 실행 중인 서비스를 깨뜨리지 않아야 했다.
- 승인되지 않은 지식이나 규칙이 운영에 섞이지 않아야 했다.
- 변경 전후의 차이와 책임을 추적할 수 있어야 했다.
- 실패했을 때 이전 안정 상태로 돌아갈 수 있어야 했다.

실제로 작업공간의 기준 버전이 서로 달라 같은 변경을 다르게 해석하거나, 한 환경에는 있는 자료가 다른 환경에는 없어 재구성이 실패하는 일이 있었다. 이후에는 작업 시작 전에 실제 상태를 확인하고, 변경을 작은 단위로 전달하며, 운영 반영 전에 별도 검토와 무결성 확인을 수행하는 절차가 자리 잡았다.

### 3.3 오프라인 우선 운영

보험 문서와 대화 데이터의 민감성을 고려해 주요 모델과 검색 자원은 DGX 내부에서 동작하도록 구성했다. 인터넷 연결이 없어도 핵심 질문, 검색, 계산, 지식 정비가 가능하도록 하는 것이 기본 방향이었다.

오프라인 운영은 단순히 모델 파일을 내려받는 것으로 끝나지 않았다. 모델 본체뿐 아니라 문서 인식, 임베딩, 재정렬, 표 처리에 필요한 모든 구성요소가 장비 안에서 준비되어야 했고, 실행 중 외부 다운로드를 시도하지 않는지 확인해야 했다. 이 경험은 이후 새 장비용 설치 계획을 세울 때 “모델만 복사하면 된다”는 접근을 버리게 한 계기가 되었다.

### 3.4 기획·개발·독립 검토의 역할 분리

후반부에는 작업을 다음과 같이 분리했다.

- **기획 역할**은 요구사항, 안전 경계, 완료 조건, 인수 기준을 정의했다.
- **개발 역할**은 변경을 구현하고 직접 시험한 근거를 남겼다.
- **독립 검토 역할**은 구현자의 설명이 아니라 실제 결과를 기준으로 통과 여부를 판단했다.

이 과정에서 한 번에 통과하지 못한 작업이 많았다. 원천 연결이 끊긴 지식, 형식상 정상이나 실제로는 손상된 그래프, 화면과 내부 상태의 불일치, 권한 문제 등이 검토 단계에서 발견되었다. 여러 차례의 수정 요청은 일정상 부담이었지만, “동작한다”와 “안전하게 운영할 수 있다”의 차이를 분명히 해 주었다.

### 3.5 환경 변화에서 얻은 교훈

1. 문서나 보고서에 적힌 상태보다 실제 실행 환경의 상태를 먼저 확인해야 한다.
2. 개발 환경과 운영 환경이 다르면 데이터, 모델, 권한, 설정의 차이를 모두 검증해야 한다.
3. 공유 장비에서는 개인 작업공간, 검토 단계, 보호된 운영 기준선이 필수다.
4. 오프라인 서비스는 실행 파일뿐 아니라 모든 모델·검색·문서 처리 자산의 완결성이 필요하다.
5. 장비나 네트워크 문제처럼 보이는 현상도 애플리케이션의 읽기·쓰기 방식에서 시작될 수 있다.

## 4. 우리가 구축한 서비스

### 4.1 문서 수집과 교정

- 디지털 보험 문서의 본문, 제목, 쪽 번호, 표를 읽어 검색 가능한 형태로 정리한다.
- 복잡한 표는 일반 본문과 분리해 행 단위로 복원한다.
- 여러 문서 인식 방식을 조합하고, 숫자와 병합 셀은 별도 규칙으로 보정한다.
- 사람이 확인한 교정본을 검색과 그래프의 기준 원천으로 사용한다.
- 새 문서는 먼저 임시 영역에서 검사한 뒤 승인된 경우에만 운영 원천으로 승격한다.
- 스캔 문서처럼 현재 자동 처리가 보장되지 않는 입력은 조용히 실패시키지 않고 차단 사유를 보여 준다.

### 4.2 근거 중심 검색과 답변

- 정확한 용어를 찾는 키워드 검색과 문맥이 비슷한 내용을 찾는 의미 검색을 함께 사용한다.
- 두 검색 결과를 합친 뒤 질문과의 관련성을 다시 평가해 우선순위를 정한다.
- 답변에는 관련 문서와 쪽을 연결하고, 사용자가 원문으로 이동해 확인할 수 있게 한다.
- 같은 내용을 반복해서 보여 주는 근거는 줄이고, 승인된 근거를 우선한다.
- 출처가 부족하면 일반 상식으로 빈칸을 채우지 않고 불확실성을 표시한다.

### 4.3 지식 그래프와 온톨로지

- 조항, 조건, 예외, 예시, 진단, 행위, 필요 서류와 그 관계를 구조화한다.
- 문서에서 새 개념과 동의어 후보를 추출하되 자동으로 운영 지식에 넣지 않는다.
- 실무자가 후보를 승인, 수정, 보류, 거절할 수 있다.
- 승인된 지식만 활성 목록에 들어가며, 이후 검색과 그래프 재구성에 사용된다.
- 보류 사유를 다음 후보 생성과 검토 기준에 다시 활용한다.
- 관리자는 전체 그래프의 제한된 핵심 영역과 선택한 항목 주변을 2차원 또는 3차원으로 조회할 수 있다.

### 4.4 예상 보상금 계산과 검토 전환

- 가입 세대, 급여·비급여 구분, 공제 기준, 한도, 예외 조건을 구조화해 계산한다.
- 계산 규칙은 언어 모델의 자유 판단이 아니라 승인된 규칙표를 따른다.
- 제외 조건이 확인되면 설명보다 제외 규칙을 우선한다.
- 여러 코드나 조건이 가능한 경우 임의로 하나를 선택하지 않는다.
- 비급여 여부가 불명확하면 전체 청구를 0원으로 만들지 않고 해당 항목을 자동 계산에서 분리한다.
- 계산에 사용한 입력과 규칙 상태를 대화에 구조화해 남긴다.
- 사용자가 조건을 명확히 수정했을 때만 이전 계산을 이어 받아 재계산한다.
- 정보가 부족하거나 여러 계산 건이 섞이면 질문을 되돌려 확인하거나 사람 검토 대상으로 전환한다.

### 4.5 대화와 사용자 화면

- 일반 질문과 예상 보상금 계산을 한 화면에서 처리한다.
- 대화 이력을 저장하고 다시 열 수 있다.
- 이전 질문의 맥락을 이어 가는 후속 질문을 지원한다.
- 답변에 연결된 출처를 선택해 원문 쪽을 확인할 수 있다.
- 내부 검색 정보나 시스템용 식별자가 최종 답변에 노출되지 않도록 필터링한다.
- 계산 결과는 확정 지급액이 아니라 조건부 예상 결과로 표현한다.

### 4.6 관리자와 운영 기능

- 문서 반입 진행 상태, 실패 사유, 다음 조치를 확인할 수 있다.
- 지식 후보의 승인 상태와 적용 이력을 관리한다.
- 검색, 모델, 그래프, 문서 상태를 진단할 수 있다.
- 사용 가능한 모델과 실제 활성 모델을 구분해 표시한다.
- 운영 안내서와 장애 대응 기준을 마련했다.
- 릴리스 전후에 데이터 무결성, 근거 연결, 화면 동작을 확인하는 절차를 만들었다.

## 5. 단계별 개발 여정과 주요 전환점

### 5.1 1단계: “답을 생성하는 챗봇” 만들기

첫 단계의 목표는 보험 문서를 넣고 질문하면 관련 내용을 찾아 자연어로 답하는 것이었다. 빠르게 동작하는 초기 서비스를 만들면서 문서 분할, 검색, 답변 생성, 출처 표시, 대화 저장의 기본 틀을 확보했다.

이때는 답변이 자연스럽고 검색 결과가 어느 정도 관련 있어 보이면 성공으로 판단하기 쉬웠다. 하지만 실제 보험 문서는 일반 설명문보다 표, 수치, 각주, 예외가 훨씬 중요했다. 자연스러운 답변만으로는 실무 신뢰를 얻을 수 없다는 사실이 곧 드러났다.

### 5.2 2단계: “검색 전에 문서를 바로잡기”

두 번째 단계에서는 문서 인식 품질이 전체 성능의 상한선을 결정한다는 사실을 확인했다. 특히 다음 문제가 반복되었다.

- 병합된 표의 행과 열이 뒤섞였다.
- 여러 줄 머리글이 본문 데이터로 들어갔다.
- 숫자와 단위가 분리되거나 다른 행에 붙었다.
- 표가 일반 문단으로 잘못 분류되었다.
- 그림을 제거하는 과정에서 필요한 숫자까지 사라졌다.

한 가지 도구로 모든 문서를 처리하려는 시도는 안정적이지 않았다. 한국어 본문 인식, 표 구조 복원, 특정 수치 보정, 제한적인 시각 교정을 조합했고, 중요한 표는 사람이 확인한 교정본으로 확정했다. 이후 검색과 계산은 원본 추출 결과가 아니라 이 교정 기준선을 사용하게 되었다.

전환점은 “인식률이 높은 도구를 찾는 문제”에서 “문서 유형별로 오류를 검출하고 교정 이력을 관리하는 문제”로 관점을 바꾼 것이었다.

### 5.3 3단계: “모델보다 전체 흐름을 본다”

답변이나 계산이 틀릴 때 처음에는 더 큰 모델이나 다른 모델을 시험했다. 그러나 여러 모델이 똑같이 틀리는 사례가 나왔다. 원인을 추적한 결과, 잘못된 표 행이 검색되거나 제외 코드를 우선 선택하거나 평가 기준이 지나치게 문자 일치에 의존한 경우가 많았다.

이후 문제를 다음 순서로 나눠 보게 되었다.

1. 원문이 올바르게 추출되었는가.
2. 질문에 맞는 문서와 표 행이 검색되었는가.
3. 세대, 항목, 예외 같은 조건이 올바르게 해석되었는가.
4. 승인된 계산 규칙이 적용되었는가.
5. 모델이 근거 범위 안에서 문장을 구성했는가.
6. 평가가 의미상 맞는 답을 잘못 실패 처리하지 않았는가.

이 진단 순서가 정착하면서 모델 교체는 마지막 선택지가 되었고, 데이터와 규칙의 품질이 먼저 개선되었다.

### 5.4 4단계: “설명형 지식과 계산 규칙을 분리한다”

보험 문서에는 설명에 유용한 개념 관계와 금액 계산에 직접 쓰이는 규칙이 함께 들어 있다. 초기에 지식 그래프가 계산 판단까지 맡을 수 있을 것으로 기대했지만, 연결 관계만으로는 세대별 공제, 한도, 제외 조건을 안정적으로 계산하기 어려웠다.

이에 따라 역할을 나눴다.

- 지식 그래프는 관련 조항, 조건, 예외, 근거를 연결하고 설명하는 데 사용한다.
- 계산 규칙은 승인된 구조화 기준으로 별도 관리한다.
- 언어 모델은 두 결과를 읽기 쉬운 답변으로 구성한다.

이 분리로 그래프가 풍부해져도 계산 결과가 임의로 바뀌지 않게 되었고, 계산 규칙을 변경할 때 승인과 이력을 관리할 수 있게 되었다.

### 5.5 5단계: “자동 추출에서 사람 승인으로”

문서에서 개념과 동의어 후보를 자동 추출했을 때 처음에는 후보가 거의 나오지 않거나, 반대로 문장 조각과 여러 뜻이 섞인 후보가 많이 나왔다. 위험한 지급·제외 표현이 포함된 후보를 모두 보류하자 승인 건수가 0이 된 적도 있었다.

이 결과를 실패로만 보지 않았다. 위험한 지식이 자동 적용되지 않았다는 점에서는 안전 장치가 작동한 것이었다. 대신 후보 품질 경고, 실무자가 이해할 수 있는 판단 기준, 보류 사유의 구조화, 중복 제거를 추가했다.

이후 지식의 생명주기는 다음처럼 정리되었다.

> 문서에서 발견 → 후보 생성 → 품질 검사 → 실무 검토 → 승인·수정·보류·거절 → 활성 지식 반영 → 검색·그래프 재구성 → 회귀 검증

### 5.6 6단계: “기능 완성에서 운영 안전으로”

기능이 늘어난 뒤에는 개별 기능이 동작하는 것보다 서로 연결될 때 깨지지 않는지가 중요해졌다. 검색 자료와 그래프의 식별자가 다르거나, 정상처럼 보이는 그래프에 끊어진 관계가 있거나, 읽기 전용 조회가 보조 파일을 만들어 다음 요청을 막는 일이 있었다.

후반부의 핵심 전환은 성공 건수를 세는 검증에서 **실패 조건을 찾아 차단하는 검증**으로 이동한 것이다. 단순히 자료 수가 맞는지 확인하는 데서 벗어나, 원천이 존재하는지, 관계의 양쪽이 실제로 존재하는지, 승인 목록과 운영 자료가 정확히 일치하는지, 손상 시 이전 상태를 보존하는지를 확인했다.

### 5.7 7단계: “시험 통과에서 실제 화면 검증으로”

자동 시험을 통과한 뒤에도 실제 브라우저에서는 다른 문제가 나타났다. 최종 답변에 내부 정보가 섞이거나, MRI 관련 수치가 서로 다른 조건에서 섞이거나, 코드와 예상 금액을 함께 물으면 안전 장치가 필요한 사실까지 숨기는 사례가 있었다.

이 경험을 계기로 다음을 분리해 평가했다.

- 내부 처리 과정이 맞는가.
- 최종 답변이 근거와 일치하는가.
- 사용자가 출처를 눌렀을 때 올바른 쪽으로 이동하는가.
- 연속 질문에서도 앞선 조건이 안전하게 유지되는가.
- 모호한 질문에 확정적인 지급 결론을 내리지 않는가.

불안정한 후보 버전은 되돌렸고, 필요한 보완만 적용한 안정 기준선을 다시 정했다. 이는 새 기능을 유지하는 것보다 안전한 상태로 복귀하는 능력이 중요하다는 것을 보여 준 사례였다.

## 6. 영역별 어려움과 시행착오

| 영역 | 처음 시도하거나 기대한 것 | 실제로 겪은 문제 | 바꾼 방식 | 남은 과제 |
|---|---|---|---|---|

### 6.1 가장 비용이 컸던 오해

가장 반복적으로 비용을 만든 오해는 다음 세 가지였다.

1. **자연스러운 답변은 정확한 답변이다.**
   실제로는 잘못 검색된 근거를 매우 자연스럽게 설명할 수 있었다.

2. **모델을 바꾸면 정확도가 오른다.**
   원문, 표, 검색, 계산 규칙, 평가 기준이 잘못된 경우 모델 교체로 해결되지 않았다.

3. **기능 시험이 통과하면 실무에서도 안전하다.**
   사용자가 보는 최종 문장, 출처 이동, 연속 질문, 장애 후 복구는 별도의 검증이 필요했다.

## 7. 시행착오를 통해 확립한 핵심 원칙

### 원칙 1. 출처 없는 판단은 하지 않는다

답변, 개념, 규칙, 계산 결과는 원문까지 추적할 수 있어야 한다. 출처가 없으면 미확인 상태로 남긴다.

### 원칙 2. 원문 품질이 모델 성능보다 먼저다

표와 수치가 틀리면 어떤 모델도 안정적인 답을 만들 수 없다. 문서 교정과 품질 검사는 검색·모델 개선보다 선행한다.

### 원칙 3. 언어 모델과 결정 규칙의 역할을 분리한다

언어 모델은 질문 이해, 요약, 설명에 사용한다. 지급 제외, 공제, 한도와 같은 결정은 승인된 규칙으로 처리한다.

### 원칙 4. 새 지식은 후보로 시작한다

자동 추출 결과는 제안일 뿐이다. 승인되지 않은 개념, 동의어, 규칙은 운영 검색과 계산에 반영하지 않는다.

### 원칙 5. 모호하면 멈추고 묻는다

여러 코드, 여러 계산 건, 불명확한 세대, 비급여 여부, 특약 조건이 있으면 임의 선택하지 않는다. 확인 질문이나 사람 검토로 전환한다.

### 원칙 6. 계산 가능성과 설명 가능성을 함께 확보한다

예상 금액만 보여 주지 않고 어떤 입력, 공제, 한도, 예외가 사용되었는지 설명할 수 있어야 한다.

### 원칙 7. 모든 지식 자료는 같은 원천을 가리켜야 한다

문서, 검색 색인, 표 행, 지식 그래프, 계산 규칙이 서로 다른 복사본을 사실로 취급하지 않도록 공통 원천과 이력을 유지한다.

### 원칙 8. 성공 수보다 실패 차단 조건을 검증한다

자료 개수나 응답 성공만 보지 않는다. 원천 없는 관계, 손상, 불일치, 승인 누락이 있을 때 실제 반영이 중단되는지 확인한다.

### 원칙 9. 자동 시험과 실사용자 검증을 분리한다

내부 결과가 맞아도 사용자가 보는 문장과 화면은 틀릴 수 있다. 브라우저에서 최종 답변, 출처, 연속 질문, 오류 안내를 따로 확인한다.

### 원칙 10. 변경은 되돌릴 수 있어야 한다

새 기능이 불안정하면 이전 안정 기준선으로 복귀할 수 있어야 한다. 운영 자료를 바꾸는 작업은 백업, 검증, 적용, 복구 순서를 갖춰야 한다.

### 원칙 11. 운영 상태를 추측하지 않는다

설치된 모델과 실제 활성 모델, 문서에 적힌 상태와 실제 환경, 계획과 구현을 구분한다. 화면과 보고에는 확인된 상태만 표시한다.

### 원칙 12. 민감정보와 운영 데이터를 개발 산출물과 분리한다

계정, 대화, 로그, 비밀정보, 원문 자료는 필요한 범위와 보존 기준을 정해 관리하며, 새 장비 이전이나 배포 때 무조건 함께 복사하지 않는다.

| 브라우저 사용자 검증 | 준비된 전체 질문 묶음의 최종 수행이 남음 | 실제 실무자가 답변·출처·연속 질문을 승인 |
| 완전 오프라인 새 장비 설치 | 포함 자산과 절차는 설계했지만 설치 매체 제작과 새 장비 시험은 하지 않음 | 구현·복사·무인터넷 설치·재시작 시험을 별도 완료 |

### 8.3 기준일 현재의 안정성 판단

기준일 현재 안정 기준선은 **v1.2.b**다. 이전 후보 버전에서 실사용자 검증 중 우선순위 높은 문제가 발견되어 안정 버전으로 되돌린 뒤 필요한 보완만 반영한 결과다.

다만 이를 “모든 인수 조건 완료”로 해석하면 안 된다. 마지막 전체 검증에서는 대부분 통과했으나 지식 그래프 대체 경로와 관련된 실패 두 건과 경고 한 건이 남았다. 최종 답변 근거성, 출처 이동, 임시 모델 정책, 그래프 읽기 회귀도 후속 확인 대상이다.

따라서 현재 상태는 **감독 아래 실무 사용이 가능한 안정 기준선**이며, 전체 사용자 검증과 잔여 회귀 해결을 끝낸 뒤 최종 인수 완료로 전환하는 것이 적절하다.

## 9. 실무자가 서비스를 사용할 때의 판단 기준

### 9.1 답변을 볼 때 반드시 확인할 것

1. **출처가 있는가**
   답변에 연결된 문서와 쪽을 열어 실제 문구를 확인한다.

2. **같은 상품·세대·특약인가**
   비슷한 표현이라도 적용 세대와 특약이 다르면 결론이 달라질 수 있다.

3. **조건과 예외가 함께 제시되었는가**
   한도만 보고 판단하지 말고 공제, 제외, 횟수, 기간, 증빙 조건을 함께 본다.

4. **답변이 사실 설명인지 예상 계산인지 구분되는가**
   문서 사실, 조건부 해석, 예상 금액, 최종 판단은 서로 다른 수준이다.

5. **불확실성이 표시되었는가**
   정보 부족이나 충돌이 있는데도 단정적인 문장이 나오면 사람 검토로 전환한다.

### 9.2 예상 보상금 계산 전 확인표

| 확인 항목 | 확인 질문 | 불명확할 때의 조치 |
|---|---|---|
| 가입 기준 | 적용 세대와 상품이 확실한가 | 증권 또는 계약 정보를 다시 확인 |
| 청구 항목 | 급여·비급여와 항목 구분이 명확한가 | 영수증·세부내역을 분리해 확인 |
| 금액 | 단위, 쉼표, 합계와 항목 금액이 맞는가 | 원증빙과 대조 후 다시 입력 |
| 코드 | 하나의 코드로 확정 가능한가 | 후보를 임의 선택하지 말고 담당자 확인 |
| 예외 | 제외, 특약, 특별 공제 조건이 있는가 | 관련 조항을 추가 확인 |
| 이전 계산 | 어느 계산 건을 수정하는지 분명한가 | 계산 대상을 먼저 선택 |
| 결과 표현 | 확정액이 아닌 예상액으로 표시되는가 | 최종 지급 판단과 분리해 기록 |

### 9.3 상태별 해석

| 화면 또는 결과 상태 | 실무 해석 | 해야 할 일 |
|---|---|---|
| 근거 확인됨 | 관련 원문을 찾았다는 뜻 | 적용 조건과 최신 문서 여부 확인 |
| 검토 필요 | 자동 판단에 필요한 정보가 부족하거나 위험 조건이 있음 | 담당자가 증빙과 약관을 확인해 결론 기록 |
| 지식 후보 | 문서에서 발견했지만 운영 지식으로 승인되지 않음 | 의미, 적용 범위, 원천을 검토 |
| 보류 | 지금은 승인하기 어렵고 추가 근거가 필요함 | 보류 사유를 해소한 뒤 재검토 |
| 승인 | 지식 자체가 검토를 통과함 | 실제 활성 반영 여부는 별도 확인 |
| 활성 | 운영 검색 또는 규칙에서 사용 가능한 상태 | 변경 이력과 적용 시점 관리 |
| 처리 차단 | 입력 또는 자료 상태가 안전 기준을 충족하지 못함 | 우회하지 말고 원인을 먼저 해소 |

### 9.4 즉시 사람 검토로 전환해야 하는 경우

- 출처가 없거나 답변과 원문이 일치하지 않는다.
- 서로 다른 문서가 같은 조건에 다른 기준을 제시한다.
- 상품, 세대, 특약, 계약 시점이 불명확하다.
- 여러 코드나 여러 청구 건 중 하나를 선택해야 한다.
- 비급여 여부, 특별 치료 여부, 예외 조건이 확인되지 않는다.
- 예상 금액이 원증빙 또는 기존 업무 계산과 크게 다르다.
- 서비스가 확정 지급을 암시하지만 근거에는 조건이 붙어 있다.
- 내부용 표현이나 의미를 알 수 없는 정보가 답변에 나타난다.
- 문서 반입, 그래프 재구성, 모델 준비 과정에서 경고나 차단이 발생한다.

### 9.5 좋은 질문을 만드는 방법

질문에 적용 상품, 세대, 항목, 금액, 급여 여부, 알고 싶은 판단을 함께 적으면 정확도가 높아진다. 한 번에 여러 청구 건을 섞기보다 한 건씩 묻고, 후속 질문에서 변경하려는 조건을 명시하는 것이 좋다.

예를 들어 “얼마 받을 수 있나요?”보다 “해당 세대 실손 계약에서 이 급여 치료비와 비급여 검사비를 각각 어떤 공제 기준으로 계산하는가?”처럼 묻는 편이 안전하다.

## 10. 실무진이 앞으로 맡아야 할 역할

### 10.1 문서 책임자

- 운영에 사용할 문서의 공식성, 버전, 적용 기간을 확인한다.
- 개정 문서가 들어오면 기존 문서와의 중복·충돌을 정리한다.
- 표와 수치 교정본을 표본 검사하고 승인한다.
- 더 이상 유효하지 않은 원천의 비활성 시점을 관리한다.

### 10.2 지식 승인자

- 개념과 동의어 후보가 한 가지 의미만 갖는지 확인한다.
- 지나치게 긴 문장 조각이나 여러 개념이 섞인 후보를 수정·거절한다.
- 지급, 제외, 공제, 한도 관련 후보는 보수적으로 검토한다.
- 보류할 때는 필요한 추가 근거와 사유를 구체적으로 남긴다.
- 승인된 지식이 실제 활성 목록에 반영되었는지 확인한다.

### 10.3 계산 규칙 승인자

- 세대별 공제, 한도, 제외, 특별 조건의 원문 근거를 확인한다.
- 모델의 답변이 아니라 구조화된 규칙과 예상 계산 사례를 승인한다.
- 새 규칙이 기존 계산에 미치는 영향을 대표 사례로 검증한다.
- 자동 계산이 허용되는 범위와 사람 검토 범위를 정한다.

### 10.4 사용자 검증 책임자

- 실제 질문을 일반 질의, 연속 질문, 계산, 경계 사례로 나눠 관리한다.
- 최종 답변 문장, 출처 이동, 조건 표현, 예상액을 직접 확인한다.
- 단순 통과율보다 잘못된 확정 결론이 있는지 우선 본다.
- 새 릴리스 전 같은 핵심 질문을 반복해 이전 동작이 깨지지 않았는지 확인한다.

### 10.5 운영 책임자

- 활성 모델, 문서, 검색, 그래프의 준비 상태를 확인한다.
- 경고나 차단이 발생하면 우회 실행보다 원인과 영향 범위를 기록한다.
- 운영 자료 변경 전 백업과 복구 가능성을 확인한다.
- 안정 기준선, 변경 일자, 승인자, 잔여 문제를 한곳에서 관리한다.

### 10.6 장애·개선 기록 책임자

- 사용자의 질문, 기대 결과, 실제 답변, 확인한 원문을 함께 남긴다.
- 모델 문제로 단정하지 않고 원문, 검색, 규칙, 답변 구성, 화면 순서로 분류한다.
- 임시 우회는 적용 이유, 종료 조건, 정식 개선 계획을 함께 기록한다.
- 반복 장애는 사용자 검증 사례와 운영 점검 항목에 추가한다.

### 10.7 권장 운영 리듬

| 주기 | 권장 활동 |
|---|---|
| 매일 | 주요 기능 상태와 새 경고 확인, 검토 필요 건 처리 |
| 매주 | 지식 후보 검토, 실패 질문 분석, 대표 질문 회귀 확인 |
| 문서 개정 시 | 원천 버전 확인, 교정, 후보·규칙 승인, 검색·그래프 재검증 |
| 릴리스 전 | 자동 검증과 실제 브라우저 사용자 검증, 복구 기준 확인 |
| 릴리스 후 | 핵심 질문 점검, 모델·검색·그래프 상태 확인, 잔여 문제 갱신 |
| 분기별 | 사용 범위, 정확성 지표, 승인 적체, 오래된 문서와 규칙 정리 |

## 11. 향후 개선 우선순위

### 우선순위 0. 최종 인수 전에 반드시 끝낼 일

#### 11.1 안정 기준선의 잔여 회귀 해결

- 지식 그래프 대체 경로에서 남은 실패를 해소한다.
- 읽기 전용 조회 후 상태가 변하지 않는지 반복 확인한다.
- 오류가 발생해도 검색 자료가 사라진 것처럼 잘못 안내하지 않도록 진단 순서를 정리한다.

**완료 기준:** 관련 회귀가 모두 통과하고, 실패를 의도적으로 만들었을 때 안전하게 차단되며, 정상 상태 복구가 확인되어야 한다.

#### 11.2 전체 실사용자 검증 완료

- 준비된 일반 질문, 연속 질문, 온톨로지 경계 질문을 실제 브라우저에서 수행한다.
- 내부 처리 과정이 아니라 사용자가 보는 최종 답변을 채점한다.
- 출처 선택 시 올바른 문서 쪽으로 이동하는지 확인한다.
- 과도한 지급 결론, 조건 누락, 내부 정보 노출이 없는지 확인한다.

**완료 기준:** 우선순위 높은 오류가 없고, 잔여 오류의 업무 영향과 우회 방법을 실무 책임자가 승인해야 한다.

#### 11.3 임시 안전·모델 정책 정리

- 특정 모델을 모든 검색 답변에 강제로 사용하는 임시 정책의 필요성을 재평가한다.
- 사실 설명, 계산, 지급 결론에 서로 다른 안전 기준을 적용한다.
- 임시 우회가 남는다면 적용 범위와 종료 조건을 공식 운영 기준에 기록한다.

**완료 기준:** 어떤 질문이 어떤 모델과 안전 정책을 사용하는지 설명할 수 있고, 임시 조치의 제거 또는 유지가 승인되어야 한다.

#### 11.4 인수 기준선 보존

- 운영에 필요한 문서, 검색 자료, 그래프, 승인 지식, 계산 규칙의 기준 시점을 함께 기록한다.
- 복구 가능한 백업을 만들고 실제 복원 점검을 수행한다.
- 잔여 문제, 담당자, 우선순위, 재검증 방법을 인수 목록에 남긴다.

**완료 기준:** 새 담당자가 기존 개발자의 기억 없이도 현재 상태를 확인하고 복구할 수 있어야 한다.

### 우선순위 1. 운영 안정성을 크게 높일 일

#### 11.5 실제 약관을 이용한 관리자 문서 반입 끝단 검증

현재 흐름은 작은 디지털 문서로 확인되었으나 실제 약관에서는 후보가 많고 표가 복잡하다. 대표 약관을 임시 반입해 후보 검토, 승인, 원천 승격, 검색과 그래프 반영, 사용자 질문까지 전 과정을 확인해야 한다.

**완료 기준:** 실패 시 기존 운영 자료가 유지되고, 재시도·취소·이력이 명확해야 한다.

#### 11.6 완전 오프라인 설치기 구현과 새 장비 시험

설치 범위와 매뉴얼은 마련되었지만 실제 설치 매체와 현장 검증은 남아 있다. 응답 모델, 지식 정비 모델, 임베딩·재정렬 모델, 문서 인식 자원, 원문과 교정 자료, 검색 자료, 그래프, 승인 지식, 계산 규칙을 빠짐없이 포함해야 한다.

반면 계정, 대화, 로그, 비밀정보는 기본적으로 제외하고 새 장비에서 초기 관리자를 생성해야 한다. 운영 계산 규칙은 새로 만들지 않고 승인된 기준선을 그대로 옮겨야 한다.

**완료 기준:** 인터넷이 없는 초기화된 새 DGX에서 설치, 재시작, 핵심 질문, 계산, 출처, 관리자 검토까지 모두 재현되어야 한다.

#### 11.7 문서 반영의 원자성과 동시 작업 안전 강화

새 문서를 운영에 반영하는 중간에 실패하거나 두 작업이 동시에 실행되어도 부분 상태가 남지 않도록 해야 한다.

**완료 기준:** 검증 완료 전에는 기존 운영 상태가 유지되고, 성공 시 관련 자료가 한 번에 같은 기준으로 전환되며, 실패 시 자동으로 이전 상태가 보존되어야 한다.

### 우선순위 2. 사용 범위와 유지관리성을 넓힐 일

#### 11.8 스캔 문서와 표 계산 자료 반입 확대

- 스캔 문서는 문서 인식과 교정 절차를 관리자 흐름에 연결한다.
- 엑셀 형태의 규칙표는 형식 검사, 원천 연결, 승인 절차를 거쳐 반영한다.
- 입력 유형마다 지원 여부와 실패 사유를 화면에서 명확히 안내한다.

#### 11.9 새 보험 세대의 동적 확장

새 세대가 추가될 때 화면과 내부 목록을 여러 곳에서 고치지 않도록, 승인된 규칙과 문서에서 지원 범위를 읽게 한다.

#### 11.10 지식 그래프 품질 개선

- 고립 항목, 근거 없는 관계, 과도하게 일반적인 동의어를 지속 정리한다.
- 전체 규모보다 핵심 질문에서 유효한 연결 비율을 품질 지표로 삼는다.
- 시각화는 제한된 범위와 읽기 전용 원칙을 유지한다.

#### 11.11 실무 평가 자료의 지속 확장

- 실제 실패 질문을 익명화해 사용자 검증 사례로 추가한다.
- 문구 일치보다 근거, 조건, 계산, 최종 표현을 각각 평가한다.
- 새 문서, 지식, 규칙, 모델이 들어올 때 같은 평가 자료를 반복 사용한다.

### 11.12 우선순위 요약

| 순위 | 핵심 목표 | 최종 판단 질문 |
|---|---|---|
| 0 | 현재 안정 기준선의 인수 완결 | 실무자가 안심하고 현재 버전을 인수할 수 있는가 |
| 1 | 운영·이전 과정의 실패 안전성 | 새 문서와 새 장비에서도 기존 운영 상태를 보호할 수 있는가 |
| 2 | 지원 범위와 유지관리성 확장 | 새 문서·세대·질문을 같은 원칙으로 지속 수용할 수 있는가 |

## 12. 쉬운 용어 설명

| 용어 | 쉬운 설명 |
|---|---|
| RAG | 질문과 관련된 문서를 먼저 찾고, 그 내용을 바탕으로 답을 만드는 방식 |
| OCR | 이미지나 스캔 문서에 있는 글자와 표를 컴퓨터가 읽을 수 있게 바꾸는 기술 |
| 교정 기준선 | 자동 추출 결과를 사람이 확인·수정해 신뢰할 수 있는 기준 자료로 확정한 것 |
| 문서 조각 | 긴 문서를 검색하기 좋은 작은 단위로 나눈 것 |
| 키워드 검색 | 질문에 들어 있는 정확한 단어나 표현을 중심으로 찾는 방식 |
| 의미 검색 | 표현이 달라도 뜻이 비슷한 내용을 찾는 방식 |
| 임베딩 | 문장이나 문서의 의미를 숫자 좌표로 바꿔 유사도를 비교하게 하는 표현 |
| 재정렬 | 처음 찾은 여러 결과를 질문과 더 관련 있는 순서로 다시 배치하는 과정 |
| 혼합 검색 | 키워드 검색과 의미 검색의 장점을 합치는 방식 |
| 근거성 | 답변의 각 핵심 내용이 실제 원문으로 뒷받침되는 정도 |
| 출처 추적 | 답변이나 규칙이 어느 문서, 어느 쪽, 어느 표에서 왔는지 거슬러 확인하는 것 |
| 지식 그래프 | 개념, 조항, 조건, 예외, 근거를 점과 선의 관계로 연결한 지식 구조 |
| 온톨로지 | 업무에서 쓰는 개념의 이름, 뜻, 동의어, 관계를 정리한 공통 지식 체계 |
| 지식 후보 | 문서에서 발견했지만 아직 실무 승인을 받지 않은 개념이나 동의어 |
| 활성 지식 | 검토와 승인을 거쳐 실제 서비스가 사용하도록 반영된 지식 |
| 결정 규칙 | 공제, 한도, 제외처럼 같은 입력에 같은 결과를 내도록 명확히 정한 계산 기준 |
| 예상 보상금 | 입력된 조건과 승인 규칙으로 계산한 참고 금액이며 최종 지급액은 아님 |
| 사람 검토 | 자동 판단이 안전하지 않을 때 담당자가 원문과 증빙을 확인해 결정하는 절차 |
| 검토 필요 | 정보 부족, 충돌, 예외 때문에 자동 결론을 내리지 않았다는 상태 |
| 대체 경로 | 주된 처리 방식이 사용할 수 없을 때 제한적으로 사용하는 보조 처리 방식 |
| 회귀 오류 | 새 변경 때문에 이전에 잘되던 기능이 다시 깨지는 문제 |
| 무결성 | 문서, 지식, 관계, 규칙이 빠지거나 어긋나지 않고 서로 일치하는 상태 |
| 실패 시 차단 | 오류가 있는데도 계속 적용하지 않고 기존 안전 상태를 유지하는 방식 |
| 사용자 검증 | 실제 사용자가 실제 화면에서 질문, 답변, 출처, 계산을 확인하는 최종 점검 |
| 오프라인 우선 | 인터넷 연결 없이도 핵심 모델과 자료가 장비 내부에서 동작하도록 하는 운영 원칙 |
| 안정 기준선 | 문제가 생겼을 때 돌아갈 수 있도록 검증하고 보존한 운영 버전과 자료 상태 |
