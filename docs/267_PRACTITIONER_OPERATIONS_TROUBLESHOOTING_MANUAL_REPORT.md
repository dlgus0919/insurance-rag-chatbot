# 실무자 전체 운영 오류 대응 매뉴얼 구현 보고서

## 1. 목적과 범위

실무자가 화면에서 관찰한 오류·검토 상태를 안전하게 분류하고, 업무를 계속할 수 있는 경우와
관리자 이관이 필요한 경우를 구분할 수 있도록 기준 매뉴얼과 배포 PDF를 추가했다.

이 작업은 오류 대응 문서와 PDF 생성에 한정했다. 데이터, 검색 인덱스, GraphDB, 활성 룰,
LLM 모델과 서버 상태는 변경하지 않았다.

## 2. 근거와 작성 원칙

- 인증·권한·세션, API 오류, 문서 반입 차단, 관리자 진단, 보험금 계산 응답의 실제 코드와
  화면 문구를 우선 확인했다.
- 전용 오류 계약이 없는 활성 인덱스 상태, LLM 지연, DGX 운영 상태는 오류 코드가 있는 것처럼
  만들지 않고 `전용 화면 오류 계약 없음`으로 구분했다.
- `requires_review=true`는 계산 엔진 오류가 아니라 추가 확인이 필요한 업무 검토 상태로 명시했다.
- 실무자 조치는 조회, 입력 재확인, 단일 재시도, 관리자 이관으로 한정했다. 삭제, 재빌드,
  서버 재시작, 모델 변경은 금지 사항으로 분리했다.
- 고객 정보, 원문 문서, 로그인 정보, 운영 비밀값은 매뉴얼과 테스트에 넣지 않았다.

## 3. 산출물

- 기준 원본: `docs/266_PRACTITIONER_OPERATIONS_TROUBLESHOOTING_MANUAL.md`
- 배포 PDF: `output/pdf/practitioner_operations_troubleshooting_manual.pdf`
- 생성기: `scripts/build_operations_manual_pdf.py`
- 구조·민감정보 방지 테스트: `tests/test_operations_manual_artifacts.py`
- PDF 내용 검증: `tests/test_operations_manual_pdf.py`
- 문서 전용 의존성 선언: `requirements-docs.txt`

README의 빠른 대응 절에서 기준 매뉴얼을 연결했다. 기존 DGX 운영 절차는 그대로 유지했다.

## 5. 남은 운영 유의사항

- `RAG-001`의 공통 오류 계약은 존재하지만, 모든 검색 경로가 같은 화면 문구를 사용한다고
  단정하지 않는다. 화면의 실제 문구와 함께 이관해야 한다.
- 시스템 자원 부족은 앱 상태 API만으로 확정할 수 없다. 운영 담당자가 별도 읽기 전용 상태를
  확인해야 한다.
- PDF 생성은 Korean-capable 글꼴이 설치된 환경을 전제로 한다. 배포 환경에서 글꼴이 없으면
  생성기를 실행하기 전에 글꼴 준비 상태를 확인해야 한다.
