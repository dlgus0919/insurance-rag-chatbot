# 실무자 전체 운영 오류 대응 매뉴얼 설계

**작성일:** 2026-07-15
**상태:** 설계 승인 반영본
**구현 범위:** 운영 문서 작성, PDF 배포본 생성과 기존 진입 문서 연결

## 1. 목적

실무자가 애플리케이션 사용 중 오류나 비정상 상태를 만났을 때 업무 지속 가능 여부를 판단하고, 안전한 1차 조치를 수행한 뒤 필요한 증거를 갖춰 관리자에게 이관할 수 있는 전체 운영 대응 매뉴얼을 제공한다.

이 매뉴얼은 단순 오류 문구 모음이 아니다. 사용자 화면, API, 검색 인덱스, GraphDB, LLM 서버, DGX Spark 시스템까지 이어지는 실제 운영 경로를 기준으로 증상과 조치 절차를 연결한다.

## 2. 범위

다음 오류 영역을 모두 포함한다.

1. 로그인, 세션, 권한
2. 화면 로딩, 네트워크, API 요청
3. 일반 질의, RAG 검색, 근거 표시
4. 보험금 계산, 입력 검증, 실무 검토 필요 상태
5. 문서 업로드, 문서 판독, 지식 후보 생성과 승인 반영
6. BM25 및 Chroma 인덱스
7. GraphDB 파일, 빌드, 검색 인덱스 정합성
8. LLM 공급자, 모델 서버, 응답 지연
9. DGX Spark 프로세스, 메모리, 저장공간, 시스템 상태

다음 항목은 범위에서 제외한다.

- 비밀키, 비밀번호, 개인식별정보의 수집이나 문서 기재
- 데이터 삭제, DB 재생성, 모델 교체 같은 파괴적 복구 절차의 실무자 직접 수행
- 실제 코드와 운영 명령에서 확인되지 않은 추정성 조치
- NVIDIA 또는 외부 제품 문서 전체의 재작성

## 3. 대상 독자와 책임 경계

### 3.1 실무자

- 화면에서 증상과 오류 문구를 식별한다.
- 업무 지속 가능 여부를 판단한다.
- 새로고침, 재로그인, 입력 보정, 제한된 재시도처럼 되돌릴 수 있는 조치만 수행한다.
- 오류 시각, 요청 ID, 기능명, 민감정보가 제거된 화면 정보를 기록한다.
- 이관 기준을 만족하면 추가 시도를 중단하고 관리자에게 전달한다.

### 3.2 관리자

- 관리자 페이지의 시스템 상태, 검색 진단, GraphDB 정합성, 지식 반입 감사 기록을 확인한다.
- 승인된 읽기 전용 상태 확인 명령을 수행한다.
- 서비스 재시작, 인덱스 재빌드 또는 데이터 복구가 필요하면 별도 운영 변경 절차로 전환한다.

### 3.3 개발자

- 재현 가능한 애플리케이션 결함, 데이터 계약 불일치, 반복되는 내부 오류를 분석한다.
- 코드 수정이 필요한 문제는 운영 매뉴얼이 아니라 별도의 개발 작업으로 추적한다.

## 4. 문서 구조

매뉴얼은 빠른 판단과 상세 조사를 분리한다.

### 4.1 첫 화면: 빠른 장애 분류

- 서비스 전체가 열리지 않는가
- 로그인만 실패하는가
- 특정 기능만 실패하는가
- 답변은 생성되지만 근거 또는 계산 결과가 불완전한가
- 관리자 화면에서 인덱스 또는 GraphDB가 비정상인가
- LLM 응답만 지연되거나 실패하는가

각 질문은 해당 상세 항목으로 바로 이동할 수 있어야 한다.

### 4.2 오류 색인

화면 문구, API 오류 코드, 기능명, 운영 상태명으로 검색할 수 있는 표를 제공한다. 같은 원인이 여러 화면 문구로 나타나는 경우 하나의 대표 대응 항목으로 연결한다.

### 4.3 상세 대응 항목

모든 상세 항목은 다음 필드를 사용한다.

| 필드 | 내용 |
|---|---|
| 식별자 | 안정적인 운영 매뉴얼 항목 ID |
| 증상 | 실무자가 관찰할 수 있는 화면 상태 |
| 오류 코드·문구 | 실제 코드나 화면에서 확인한 값 |
| 심각도 | 긴급, 주요, 일반, 안내 |
| 업무 영향 | 전체 중단, 부분 중단, 우회 가능, 영향 없음 |
| 즉시 확인 | 추가 변경 없이 확인할 항목 |
| 실무자 조치 | 되돌릴 수 있고 권한 내에서 가능한 조치 |
| 중단·이관 기준 | 반복 시도를 멈추는 조건 |
| 관리자 진단 | 관리자 페이지와 읽기 전용 명령 |
| 복구 확인 | 정상으로 판단할 재검증 절차 |
| 수집 증거 | 오류 시각, 요청 ID, 기능명 등 |
| 금지 사항 | 비밀번호 수집, 임의 삭제 등 |

## 5. 오류 분류와 심각도

### 5.1 긴급

- 전체 서비스 접근 불가
- 데이터 손상 또는 잘못된 승인 반영 의심
- 인증 우회, 권한 노출 또는 민감정보 노출 의심
- 반복적인 프로세스 종료나 시스템 메모리 고갈

실무자는 재시도와 변경을 중단하고 즉시 관리자에게 이관한다.

### 5.2 주요

- 로그인 또는 핵심 질의 기능이 다수 사용자에게 실패
- 보험금 계산이 완료되지 않음
- 필수 인덱스나 GraphDB가 없거나 읽기 실패
- 활성 LLM 공급자가 응답하지 않음

관리자는 영향 범위를 확인하고 운영 복구 또는 개발 이관을 결정한다.

### 5.3 일반

- 특정 입력, 특정 문서, 특정 노드에서만 발생
- 재입력이나 안전한 재시도로 회복 가능
- 일부 근거가 누락되지만 다른 검색 결과는 정상

### 5.4 안내

- `requires_review=true`
- 검토 후보 대기 또는 보류
- 아직 진단 이력이 없음
- 현재 사용하지 않는 LLM 공급자의 경고

이 상태들은 자동으로 장애로 분류하지 않는다.

## 6. 근거 수집 원칙

문서 작성 시 다음 순서로 근거를 수집한다.

1. `src/api/exceptions.py`와 전역 예외 처리에서 API 오류 코드를 수집한다.
2. 인증, 채팅, 계산, 관리자, 지식 반입 라우트의 오류 조건을 수집한다.
3. 프런트엔드에서 실제로 표시하는 사용자 문구를 수집한다.
4. 테스트에서 보장하는 오류 계약과 상태 전이를 확인한다.
5. README와 DGX 운영·시연 문서의 검증된 명령만 선별한다.
6. 코드와 문서가 다르면 현재 테스트와 실행 코드의 동작을 우선하고 불일치를 별도로 기록한다.

## 7. 안전 요구사항

- 비밀번호, API 키, 토큰, 전체 사용자 질의, 원본 보험 문서는 수집 예시에 포함하지 않는다.
- 로그 예시는 민감정보가 제거된 형태만 사용한다.
- 실무자 조치에는 삭제, 강제 종료, DB 수정, 인덱스 재생성을 포함하지 않는다.
- 관리자 명령은 읽기 전용 확인과 변경 작업을 명확히 분리한다.
- 변경 작업은 별도 승인과 백업·롤백 절차가 필요한 것으로 표시한다.
- 동일 작업의 무한 재시도를 금지하고 최대 재시도 횟수 또는 이관 조건을 명시한다.

### 8.3 구현 보고서

- 실제 매뉴얼 작성 완료 후 프로젝트 규칙에 따라 `docs/` 아래에 변경 및 검증 보고서 작성

## 9. 검증 전략

### 9.1 정적 검증

- 실제 오류 코드와 문구가 매뉴얼 항목에 연결되는지 대조한다.
- 내부 경로, 계정명, 비밀번호, API 키가 문서에 포함되지 않았는지 검색한다.
- 모든 상세 항목에 실무자 조치, 이관 기준, 복구 확인이 존재하는지 확인한다.
- 파괴적 명령이 실무자 절차에 포함되지 않았는지 확인한다.
- Markdown과 PDF에서 제목, 절 번호, 오류 항목 ID가 일치하는지 확인한다.

### 9.2 PDF 생성 및 시각 검증

- 프로젝트에서 재실행 가능한 생성 스크립트로 PDF를 만든다.
- 한국어 글꼴을 명시적으로 등록하고, 대상 실행 환경에 존재하지 않을 때 이해 가능한 오류로 중단한다.
- 표가 페이지 폭을 넘으면 열 너비, 줄바꿈 또는 항목별 블록 레이아웃으로 조정한다.
- 머리말, 꼬리말, 페이지 번호와 문서 버전을 포함한다.
- `pdfinfo`로 파일 유효성과 페이지 수를 확인한다.
- `pypdf` 또는 `pdfplumber`로 핵심 제목과 오류 항목 ID가 추출되는지 확인한다.
- Poppler `pdftoppm`으로 모든 페이지를 `tmp/pdfs/` 아래 PNG로 렌더링한다.
- 렌더링된 전 페이지에서 한글 깨짐, 검은 사각형, 텍스트 잘림, 표 겹침, 빈 페이지와 잘못된 페이지 전환이 없는지 시각적으로 확인한다.
- 검증이 끝나면 `tmp/pdfs/`의 중간 산출물을 제거하고 최종 PDF만 `output/pdf/`에 유지한다.

### 9.3 시나리오 검증

최소 다음 시나리오를 따라가며 문서만으로 대응 가능한지 확인한다.

1. 로그인 실패
2. 세션 만료 또는 권한 거부
3. 일반 질의 응답 실패
4. 근거 없는 답변 또는 GraphDB 정합성 경고
5. 보험금 계산 입력 오류와 검토 필요 상태
6. 문서 업로드 차단
7. 지식 후보 생성 실패
8. 인덱스 누락
9. GraphDB 파일 누락 또는 읽기 실패
10. 활성 LLM 서버 연결 실패
11. 저장공간 부족 또는 시스템 자원 포화

### 9.4 완료 기준

- 실무자가 화면 문구나 오류 코드로 대응 항목을 찾을 수 있다.
- 실무자와 관리자의 권한 경계가 모든 항목에서 분명하다.
- 오류가 아닌 검토·대기·경고 상태를 장애와 구분한다.
- 관리자 이관 시 필요한 최소 증거가 일관되게 정의되어 있다.
- 실제 코드나 검증된 운영 문서로 근거를 확인할 수 없는 조치가 없다.
- Markdown과 PDF가 동일한 운영 내용을 제공한다.
- PDF 전 페이지의 한국어, 표, 여백, 머리말·꼬리말과 페이지 번호에 시각적 결함이 없다.

## 10. 비기능 요구사항

- 한국어로 작성하되 오류 코드와 명령은 원문을 유지한다.
- 초보 실무자도 이해할 수 있는 표현을 우선한다.
- 동일한 조치를 여러 곳에 복제하지 않고 공통 절차로 연결한다.
- 운영 변경과 개발 수정은 별도 작업으로 분리한다.
- 향후 오류가 추가될 때 항목 ID와 색인만 확장할 수 있는 구조를 유지한다.
