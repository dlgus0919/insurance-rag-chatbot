# 271. 실행 중 LLM 표시 및 탈모 약관 근거 운영 반영 릴리스 보고서

## 목적

이번 릴리스는 다음 네 가지 보완을 운영 앱에 반영한다.

1. 수술종수 질의와 심평원 수가 조회 의도를 분리한다.
2. ICD 진단코드만으로 심평원 수가 조회가 시작되는 것을 막는다.
3. 수술명 접미사 `술`과 독립적인 음주 표현을 구분한다.
4. 탈모 질의에 대해 선택 세대별 직접 약관 근거와 추가 확인 질문을 제공한다.

함께, 설치되어 있거나 별도 프로세스에 남아 있는 모델이 아니라 현재 앱이 실제로 사용할 수 있는 LLM만 로그인·채팅·관리자 화면에 표시하도록 운영 경로를 정리했다.

## 운영 반영 내용

### 실행 중 LLM만 표시

- 앱의 활성 provider가 SGLang 또는 vLLM이면 Ollama 설치 목록이나 잔류 프로세스를 모델 선택지에 섞지 않는다.
- Ollama provider를 명시적으로 활성화한 경우에만 실행 중인 Ollama 모델을 선택지에 포함한다.
- 브라우저에 남아 있는 이전 EXAONE 선택값은 현재 활성 기본 모델로 복원한다.
- 로그인, 채팅, 관리자 화면의 사용자 문구를 `기동 중인 LLM`으로 통일했다.
- HTML·JavaScript 번들은 무효화 가능한 버전으로 갱신하고, 현재 진입 문서와 사용자용 정적 자산에는 `no-cache` 응답 정책을 적용했다.

운영 앱의 모델 API는 최종적으로 SGLang의 Qwen3 Next Instruct 80B A3B FP8 한 건만 반환했다. EXAONE 7.8B는 모델 API와 사용자용 정적 자산에서 모두 0건이었다.

### 수술종수와 수가 조회 경계

- 수가 조회는 사용자 질문의 `수가`, `수가코드`, `심평원`, `수가표`, `점수`, `수술코드` 또는 수가 코드 형식만으로 허용한다.
- GraphDB 일반 안내 문구의 `코드`는 직접 조회를 유발하지 않는다.
- `N39.3` 같은 ICD 진단코드만 있는 질의는 직접 수가 조회를 시작하지 않는다.
- `수술`, `절제술`, `폐쇄술`, `이식술`의 접미사 `술`은 음주 표현으로 보정하지 않는다. 반대로 `술먹고`, `술마시고` 및 띄어쓴 형태는 독립 음주 표현으로 유지한다.

운영 경로의 저비용 smoke에서 `충수절제술의 1-5종 수술종수는?` 및 `N39.3 보상 기준을 알려줘.`는 모두 심평원 직접 조회 컨텍스트를 만들지 않았다.

### 탈모 직접 약관 근거의 승격

소스 온톨로지에만 있던 탈모 판단 프로필을 기존 실무자 승인 흐름으로 운영 active manifest에 승격하고 GraphDB를 재빌드했다.

- 승인 기록: 실무자 릴리스 승인 사유와 함께 후보를 승인·적용으로 남겼다.
- 운영 active manifest: 탈모, 노화현상으로 인한 탈모, 질병성 탈모, 치료·약물 부작용 탈모 관련 개념이 포함된 새 버전으로 갱신했다.
- GraphDB: 새 active manifest를 기준으로 읽기 전용 원본에서 재구성했다.
- 4세대 자사 약관 및 5세대 표준약관의 직접 조항을 각각 판단 근거로 사용한다.

운영 active manifest 기준 검증 결과는 다음과 같다.

| 선택 세대 | 일반 탈모 | 노화현상으로 인한 탈모 | 질병 진단으로 인한 탈모 | 직접 근거 |
| --- | --- | --- | --- | --- |
| 4세대 | 추가 확인 필요 | 조건부 보상 제외 조항 확인 | 추가 확인 필요 | 4세대 자사 약관 p.78 |
| 5세대 | 추가 확인 필요 | 조건부 보상 제외 조항 확인 | 추가 확인 필요 | 5세대 표준약관 p.296 |

일반 탈모나 질병성 탈모는 자동 면책 또는 자동 보상으로 확정하지 않는다. 원인, 진단명·코드, 의사소견, 치료 목적, 급여·비급여 여부 및 업무·일상생활 지장 여부를 확인하도록 구조화된 질문을 제공한다. 5세대 자사 상품 약관이 등록되지 않은 경우에는 표준약관 참고 기준이라는 제한을 유지한다.

## 미실행 검증과 남은 위험

- 새 브라우저 프로필과 이전 localStorage를 가진 실제 브라우저 프로필의 GUI 조작은 브라우저 제어 연결이 닫혀 있어 직접 관찰하지 못했다. 대신 모델 API, 정적 자산 검색, Node 회귀에 의해 EXAONE 제거와 이전 선택값 복원 경로를 검증했다.
- 인증된 운영 `/api/chat/stream` 요청은 계정·대화 데이터 변경을 피하기 위해 실행하지 않았다. 대신 기존 Qwen endpoint, 운영 active manifest, 직접 근거와 canonical 상태를 분리 검증했다.
- 전체 검색 파이프라인을 별도 프로세스로 중복 적재하는 방식은 DGX 자원 절약을 위해 중단했다. 앱 health와 기존 Qwen 서버는 정상 상태를 유지했다.
- 이번 반영 후에도 새 약관 판단을 늘릴 때는 코드 상수를 추가하지 않고, 문서 근거를 후보로 만들고 실무자 승인 기록을 거쳐 active manifest와 GraphDB에 승격해야 한다.
