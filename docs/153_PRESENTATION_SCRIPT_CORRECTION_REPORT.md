## 1. 보험금 계산 기능 설명이 현재 구현보다 과장됨

### 원문

> 제출받은 이 청규 서류들을 자동으로 분류하고 분석해서 보험금을 자동으로 계산하고 산출 근거를 자동으로 생성해주는 프로그램입니다.

### 문제

현재 프로젝트에는 `보험금 계산` 기능이 구현되어 있지만, **영수증·진단서·세부내역서를 업로드 받아 자동 분류/OCR/추출까지 끝내는 완전 자동 파이프라인은 아직 구현 완료 상태가 아니다.**  
현재 구현은 입력 폼 기반 계산, 표준코드 매칭, 세대별 규칙 적용, review path 결합 쪽이 중심이다.

### 권장 수정

> 둘째는 보험금 계산 보조 기능입니다. 현재는 청구 항목, 세대, 진단코드, 방문 구분 등 입력 정보를 바탕으로 보험금 계산과 검토 사유를 구조화해 보여주는 단계까지 구현했습니다. 영수증·진단서·세부내역서의 자동 분류와 자동 추출은 후속 확장 과제로 남아 있습니다.

## 2. OCR 파이프라인 설명이 현재 확정 구조와 다름

### 원문

> PP-Structure로 레이아웃을 분석하고, CLOVA OCR로 글자를 인식한 뒤, 노이즈와 표를 보정하고, CODEX로 검증한 다음 RAG 청크로 변환하도록 했습니다.  
> ... PP-Structure와 CLOVA OCR을 결합한 True Hybrid 방식을 채택했습니다

### 문제

현재 문서 기준으로는:

- **기본 확정 OCR 엔진은 CLOVA native**
- **True Hybrid는 선택 실행 가능한 보조 경로**
- Vision 후처리는 OpenAI Vision LLM 기반이며, **Codex가 런타임 OCR 파이프라인의 정식 단계로 들어가 있지는 않다**

즉 “CODEX 검증”과 “True Hybrid를 기본 채택”은 현재 구현 상태를 정확히 설명하지 못한다.

### 권장 수정

> OCR 파이프라인은 CLOVA OCR을 기본 엔진으로 사용하고, 필요 시 PP-Structure를 결합한 True Hybrid 경로를 선택적으로 활용합니다. 이후 표 구조와 숫자 셀은 Vision LLM 후처리로 보정한 뒤 RAG 청크로 변환합니다.

## 3. OCR 도구 선택 설명이 과도하게 단정적임

### 원문

> 결국 한국어에 특화되고 병합셀과 다단 헤더를 복원하는 CLOVA OCR을 채택했고, 여기에 처리 성능이 가장 강한 True Hybrid를 결합했습니다.

### 문제

현재 상태는 “CLOVA + True Hybrid를 모두 유지”가 맞지만, **최종 기본 경로는 CLOVA native**다.  
따라서 “True Hybrid를 최종 채택했다”는 식의 설명은 현재 운영 기본값과 다르다.

### 권장 수정

> 비교 결과 CLOVA OCR을 기본 경로로 확정했고, 복잡한 레이아웃 대응이 필요할 때는 PP-Structure를 결합한 True Hybrid 경로를 보조적으로 사용할 수 있게 했습니다.

## 4. 운영 검색 모드 수가 현재 앱과 다름

### 원문

> 질의는 일반 질의, 퀵코드, 약관 정형검색 세 가지 모드로 처리됩니다.

### 문제

현재 앱에는 **네 가지 모드**가 있다.

- 일반 질의
- 퀵 코드 검색
- 약관 정형 검색
- 보험금 계산

### 권장 수정

> 질의는 일반 질의, 퀵 코드 검색, 약관 정형 검색, 보험금 계산 네 가지 모드로 처리됩니다.

## 5. 운영 아키텍처 설명에서 GraphDB/관계형 DB가 빠져 있음

### 원문

> 문서와 인덱스 계층에서는 PDF와 OCR 문서를 전처리·청크화해 Chroma, BM25, Parquet로 관리합니다.

### 문제

현재 구조는 단순 `Chroma + BM25 + Parquet`만이 아니다. 실제 운영 구조에는 다음이 함께 들어간다.

- Chroma 벡터 인덱스
- BM25
- SQLite GraphDB
- 표준코드/비급여 모델용 관계형 SQLite
- 일부 구조화 표용 Parquet

현재 상태를 설명하는 문장으로는 누락이 크다.

### 권장 수정

> 문서와 인덱스 계층에서는 PDF와 OCR 문서를 전처리·청크화한 뒤, Chroma 벡터 인덱스와 BM25, SQLite 기반 GraphDB, 표준코드 관계형 DB, 일부 구조화 표용 Parquet 인덱스를 함께 사용합니다.

## 6. 모델 평가 수치가 현재 보고서와 다름

### 원문

> 대형 모델 4종 평가에서는 gpt-oss-20b가 정확도 37퍼센트로 가장 안정적이고 구조화된 답변을 보였습니다.

### 문제

현재 최신 4모델 평가 보고서 기준으로는 `sglang_gpt_oss`가 가장 높았지만, 수치는 **37%가 아니라 5/17 = 29.4%**다.  
“정확도 37%”는 현재 기준 보고서와 일치하지 않는다.

### 권장 수정

> 대형 모델 4종 비교에서는 GPT-OSS가 상대적으로 가장 안정적인 편이었지만, 최신 평가 기준 통과율은 약 29% 수준으로 아직 낮았습니다.

## 7. GraphDB를 “도입 계획”으로만 설명하면 현재 상태와 어긋남

### 원문

> 마지막으로 향후 계획인 Graph DB입니다.  
> ... 실제로 SQLite를 활용해 그래프 디비 구축을 시도하고 있습니다.

### 문제

현재는 GraphDB가 단순 계획 단계가 아니다.

- SQLite GraphDB 산출물이 이미 구축되어 있음
- RAG 런타임에 구조화 근거로 연결됨
- 보험금 계산에도 review path 보조층으로 연결됨

따라서 “도입 계획” 또는 “구축 시도 중”만으로 말하면 현 구현 수준을 지나치게 낮게 설명하게 된다.

### 권장 수정

> 마지막으로 GraphDB 확장 방향입니다. 현재는 SQLite 기반 GraphDB를 이미 구축해 RAG와 보험금 계산 검토 경로에 연결해 두었고, 이를 더 정교하게 확장하는 단계에 있습니다.

## 8. GraphDB 역할 설명에서 의학 인과 추론처럼 들리는 부분은 수정이 필요함

### 원문

> 질병명만으로는 보장 여부를 판단할 수 없고, 질병코드가 달라도 인과관계가 있으면 하나의 질병 흐름으로 봐야 합니다.  
> 질병에서 합병증, 치료, 보상으로 이어지는 경로를 봐야 하는데...

### 문제

현재 GraphDB는 **질병 → 합병증 의학 인과를 전역 지식으로 추론하지 않는다.**  
현재 구현은 “합병증”을 의학 causal graph가 아니라 **문서 기반 판단 개념과 review path**로 다룬다.

즉 현재 구조를 설명할 때 “질병 인과를 그래프가 추론한다”처럼 들리면 안 된다.

### 권장 수정

> 보상 판단은 진단명, 시술, 특약, 면책, 증빙 요건이 함께 엮여 있기 때문에 관계형 검토가 필요합니다. 현재 GraphDB는 질병의 의학적 인과를 추론하는 그래프라기보다, 약관 조항과 사례집, 진단코드, 합병증 판단 개념, 증빙 요구를 연결해 검토 경로를 보여주는 문서 기반 그래프로 확장되고 있습니다.

## 9. GraphDB 한계 설명은 현재 상태를 반영해 표현을 조정하는 편이 맞음

### 원문

> 따라서 우선 과제는 GraphDB와 RAG 검색 결과의 근거 문서 연결 정합성을 보강하는 것으로 잡았습니다.

### 문제

이 내용 자체는 맞지만, **현재는 그 과제를 이미 일부 수행한 뒤의 상태**다.  
따라서 “이제부터 잡았다”보다는 “여전히 남아 있는 핵심 과제”로 표현하는 편이 현재 구현 상태와 맞다.

### 권장 수정

> 따라서 지금도 남아 있는 핵심 과제는 GraphDB 구조화 근거와 RAG 검색 결과 사이의 근거 문서 연결 정합성을 더 안정화하는 것입니다.

## 총평

현재 대본에서 가장 크게 수정해야 할 부분은 아래 네 가지다.

1. **보험금 계산을 완전 자동 문서처리 단계처럼 말한 부분**
2. **OCR 기본 경로를 True Hybrid로 단정한 부분**
3. **운영 모드가 3개라고 말한 부분**
4. **GraphDB를 아직 계획/시도 단계로만 설명한 부분**

발표에서 현재 구현 수준을 정확히 보여주려면, GraphDB는 “이미 연결된 상태”, 보험금 계산은 “입력 기반 계산 보조 단계”, OCR은 “CLOVA 기본 + True Hybrid 선택 경로”로 설명하는 것이 가장 안전하다.
