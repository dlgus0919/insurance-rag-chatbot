# 관리자 GraphDB 3D 시각화 설계

**작성일:** 2026-07-15
**상태:** 설계 승인 반영본
**실행 인계:** 세부 계획 승인 후 Developer 채팅에 구현 위임

## 1. 목적

관리자가 GraphDB의 핵심 구조를 의미적으로 이해하고, 검색 또는 노드 선택을 통해 특정 개념의 상위 관계와 하위 구조를 탐색할 수 있는 3D 시각화 화면을 제공한다.

전체 GraphDB를 한 번에 렌더링하지 않는다. 기본 화면은 핵심 노드로 구성한 메인 구조를 보여주고, 선택 이후에는 제한된 부분 그래프로 전환해 의미 전달과 렌더링 비용을 함께 통제한다.

## 2. 현재 시스템 전제

- 애플리케이션은 FastAPI가 정적 SPA를 같은 출처에서 제공한다.
- 관리자 페이지에는 시스템 상태, RAG 진단, GraphDB 정합성 확인 기능이 이미 존재한다.
- GraphDB는 SQLite 기반 프로퍼티 그래프이며 `graph_nodes`, `graph_edges`, `graph_aliases`, 근거 연결 테이블과 빌드 manifest를 사용한다.
- 개발 시에는 별도 업무용 PC의 브라우저에서 DGX Spark 서버에 접속한다.
- 실사용 시에는 DGX Spark 자체 데스크톱 브라우저에서 관리자 화면을 실행한다.
- 실사용 시 LLM 서버와 브라우저 WebGL이 DGX Spark의 통합 CPU·GPU·메모리 자원을 함께 사용한다.

## 3. 범위

### 3.1 포함

- 관리자 전용 GraphDB 메뉴와 화면
- 핵심 노드 기반 메인 구조
- 노드명과 별칭 검색
- 노드 클릭 또는 검색 선택 시 카메라 확대 연출
- 선택 노드의 상위 1단계와 제한된 하위 트리
- 노드 유형, 관계, 근거를 확인하는 상세 패널
- 렌더링·응답 크기·탐색 깊이 제한
- WebGL 실패 또는 자원 부족 시 대체 표시
- DGX Spark에서 LLM 동시 실행 성능 검증

### 3.2 제외

- 전체 GraphDB의 동시 렌더링
- GraphDB 수정, 노드 편집, 관계 삭제
- 일반 사용자에게 그래프 화면 공개
- VR, AR, 다중 사용자 동시 편집
- 그래프 기반 자동 의사결정 또는 보험금 계산
- GPU 기반 그래프 분석 엔진 도입

## 4. 기술 접근법

### 4.1 권장안

`3d-force-graph` 계열의 Three.js/WebGL 렌더러를 사용한다. 현재 프런트엔드는 외부 패키지를 브라우저가 직접 해석하지 않고 소스 ES 모듈을 정적으로 제공하므로, 구현 시 다음 중 현재 배포 절차와 맞는 한 가지 방식을 검증 후 고정한다.

1. 프런트엔드 빌드 결과를 실제 배포 진입점으로 전환하고 npm 의존성을 번들링
2. 버전이 고정된 자체 호스팅 배포 번들을 `frontend/vendor/`에 두고 라이선스 포함

외부 CDN 런타임 의존은 허용하지 않는다.

### 4.2 대안 제외 사유

- Three.js 직접 구현은 세밀한 제어가 가능하지만 카메라, 선택, 레이아웃, 객체 수명 관리 범위가 크게 증가한다.
- 서버 생성 이미지나 정적 스냅숏은 브라우저 부하는 작지만 검색·클릭·확대·부분 탐색 요구를 충족하지 못한다.

## 5. 사용자 경험

### 5.1 관리자 메뉴

관리자 사이드바에 `GraphDB 탐색` 메뉴를 추가한다. 기존 `시스템 상태`와 `검색 진단`은 유지하고, 3D 그래프는 별도 탭에서 필요할 때만 초기화한다.

### 5.2 메인 구조 보기

첫 진입 시 핵심 노드로 구성된 그래프를 표시한다.

핵심 노드 점수는 다음 신호를 결합한다.

- 업무 의미가 큰 개념 노드 유형
- 전체 연결 수 또는 선택된 계층 관계 연결 수
- 계층 루트 또는 상위 노드 여부
- 근거 연결 유무와 신뢰도
- 특정 노드 유형이나 문서에 편중되지 않도록 하는 유형별 할당량

초기 후보 한도는 다음과 같이 둔다.

- 노드 80~150개
- 관계 150~300개

이 값은 구현 상수로 고정하기 전에 DGX Spark 실측으로 조정한다. API에는 절대 상한을 두어 클라이언트 요청으로 제한을 우회할 수 없게 한다.

### 5.3 검색

- 정규화된 노드명과 별칭을 검색한다.
- 완전 일치, 접두 일치, 부분 일치 순으로 결과를 정렬한다.
- 노드 유형과 연결 수를 함께 표시해 동명이거나 유사한 노드를 구분한다.
- 검색 결과 수에 서버 상한을 적용한다.

### 5.4 집중 보기

노드 클릭 또는 검색 결과 선택 시 다음 순서로 전환한다.

1. 선택 노드를 강조한다.
2. 카메라가 선택 노드로 이동하며 확대한다.
3. 메인 구조를 흐리게 유지하거나 집중 부분 그래프로 교체한다.
4. 선택 노드의 상위 관계 1단계를 표시한다.
5. 하위 관계는 중요도순으로 제한된 트리를 표시한다.
6. 한도를 초과한 하위 노드는 `더 보기`로 단계 확장한다.
7. 일반 연관 관계는 기본 계층과 구분해 별도 토글로 표시한다.

하위 깊이는 데이터 분포 검증 후 기본값을 정하되, 한 번의 응답과 한 화면에서 노드·관계 절대 상한을 넘지 않는다.

### 5.5 상세 패널

선택 노드에 대해 다음 정보를 표시한다.

- 정식 명칭과 노드 유형
- 별칭
- 직접 연결 수
- 표시 중인 상위·하위·일반 관계 수
- 관계 유형과 방향
- 신뢰도와 생성 출처
- 연결된 근거 문서, 페이지, 행 정보

원문 전체를 그래프 응답에 포함하지 않고, 상세 요청 또는 기존 근거 보기 경로로 지연 로딩한다.

### 5.6 탐색 복구

- `메인 구조로 돌아가기`
- 이전 선택으로 돌아가기
- 현재 노드를 중심으로 다시 배치
- 필터 초기화
- 현재 표시 노드·관계 수 안내

## 6. 그래프 의미 정책

GraphDB의 모든 방향성 관계를 자동으로 상위·하위로 간주하지 않는다.

구현 전에 실제 데이터에 대해 다음을 조사한다.

- 노드 유형별 개수
- 관계 유형별 개수
- 관계 유형별 출발·도착 노드 유형 조합
- 연결 차수 분포와 상위 허브
- 연결되지 않은 노드 비율
- 연결요소 크기 분포
- 후보 계층 관계의 실제 예시

조사 결과로 다음 정책을 명시적으로 작성한다.

- 계층 관계로 취급할 관계 유형
- 각 관계 유형의 부모·자식 방향
- 메인 구조에 우선 포함할 노드 유형
- 일반 연관 관계로만 표시할 관계 유형
- 문서·테이블 행처럼 기본 화면에서 축약할 대량 노드 유형

정책에 등록되지 않은 관계는 임의로 상위·하위로 해석하지 않는다.

## 7. 데이터와 API 설계

### 7.1 서버 측 선택과 사전 계산

- 핵심 노드 점수와 차수 통계를 GraphDB 빌드 또는 별도 준비 단계에서 계산한다.
- 메인 구조의 초기 좌표를 사전 계산하거나 결정적 배치 규칙으로 생성한다.
- 요청마다 전체 노드와 전체 관계를 스캔하지 않는다.
- 검색과 주변 관계 조회에 필요한 SQLite 인덱스를 검증하고 부족한 인덱스만 추가한다.

### 7.2 API 경계

관리자 전용 읽기 API를 별도 라우터로 분리한다.

- 메인 구조 조회
- 노드와 별칭 검색
- 선택 노드 주변 관계 조회
- 선택 노드 상세 및 근거 요약 조회

모든 API는 기존 관리자 권한 검사를 재사용하고 다음을 보장한다.

- 읽기 전용 GraphDB 연결
- 요청 및 응답 한도
- 안정적인 정렬과 결정적 결과
- GraphDB 없음, 읽기 실패, 노드 없음의 구분된 오류 계약
- 파일 시스템 절대 경로와 내부 민감정보 비노출

### 7.3 응답 데이터

렌더링 응답에는 필요한 최소 필드만 포함한다.

- 노드 ID, 표시명, 유형, 점수, 연결 수, 선택 상태, 선택적 좌표
- 관계 ID, 출발 ID, 도착 ID, 관계 유형, 계층 분류
- 전체 후보 수, 잘린 수, 적용한 한도
- 그래프 빌드 버전 또는 manifest 식별값

근거 원문과 큰 `properties_json`은 기본 응답에서 제외한다.

## 8. 프런트엔드 구조

기존 `frontend/js/pages/admin.js`가 계속 커지지 않도록 GraphDB 기능을 분리한다.

- 관리자 Graph API 호출 모듈
- 그래프 데이터 정규화와 상태 관리 모듈
- 3D 렌더러 수명 주기 모듈
- 관리자 GraphDB 페이지 조정 모듈
- 기존 관리자 HTML과 CSS의 최소 연결 변경

렌더러는 다음 수명 주기를 가져야 한다.

1. GraphDB 탭 진입 시 생성
2. 데이터 수신 후 제한된 레이아웃 계산
3. 안정화 후 물리 시뮬레이션과 불필요한 애니메이션 중지
4. 탭 이탈 시 이벤트 제거와 렌더 루프 중지
5. 관리자 페이지 이탈 시 geometry, material, texture, renderer 해제

## 9. DGX Spark 자원 예산

DGX Spark의 통합 메모리 구조에서는 브라우저와 LLM이 같은 시스템 자원 풀을 공유한다. 고정된 GPU 메모리 예산을 추정값만으로 확정하지 않고, 구현 전후 실측을 통해 상한을 고정한다.

### 9.1 기본 절약 정책

- GraphDB 탭이 활성화될 때만 WebGL 생성
- 그림자, 후처리, 발광 입자, 상시 자동 회전 미사용
- 단순 구체와 선을 공유하여 객체 수 최소화
- 모든 노드에 상시 3D 텍스트를 붙이지 않고 선택·호버 라벨만 표시
- 내부 렌더 해상도와 픽셀 비율 상한 적용
- 카메라 이동과 짧은 레이아웃 안정화 후 연속 렌더 중지 또는 저주기 전환
- 창이 숨겨지거나 탭을 벗어나면 즉시 일시정지
- LLM 추론 중에도 자동 배경 애니메이션을 수행하지 않음

### 9.2 실측 조건

DGX Spark에서 동일한 모델과 동일한 질의를 사용해 다음 조건을 비교한다.

1. LLM 서버만 실행
2. LLM 서버와 관리자 페이지 실행, GraphDB 탭 미진입
3. 메인 그래프 표시
4. 최대 허용 집중 그래프 표시
5. 집중 그래프 카메라 이동 중 LLM 추론
6. 그래프 안정화 후 LLM 연속 질의

관찰 항목:

- LLM 첫 토큰 지연과 전체 응답 시간
- 브라우저 프레임률과 긴 프레임
- CPU·GPU 사용률
- 시스템 가용 메모리와 스왑 변화
- 브라우저 프로세스 메모리
- API 응답 시간과 응답 크기
- 온도와 지속 부하 여부

DGX Spark의 통합 GPU에서는 `nvidia-smi` 전체 메모리 수치만으로 판단하지 않고 DGX Dashboard, 프로세스별 정보, 시스템 메모리와 브라우저 측정을 함께 사용한다.

### 9.3 초기 합격 목표

- 메인 그래프 최초 표시 2초 이내
- 검색 선택 후 집중 그래프 표시 1초 이내
- 카메라 전환 중 30 FPS 이상
- 안정화 후 불필요한 지속 렌더링 없음
- 그래프 사용에 따른 LLM 첫 토큰 지연 악화 10% 이내
- 스왑의 지속 증가, 브라우저 중단, LLM OOM 없음

측정 환경, 모델, 동시 요청 수와 그래프 크기를 결과에 함께 기록한다. 목표를 충족하지 못하면 시각 효과가 아니라 노드·관계 수, 렌더 해상도, 라벨 수를 먼저 줄인다.

## 10. 장애와 대체 동작

- GraphDB 파일 없음: 상태 안내와 운영 매뉴얼 연결
- GraphDB 읽기 실패: 내부 경로를 숨긴 오류 메시지와 요청 ID 표시
- 메인 구조 산출물 없음: 빈 3D 화면 대신 재빌드 필요 상태 표시
- 검색 결과 없음: 필터와 검색어 확인 안내
- 응답 한도 초과: 잘린 개수와 `더 보기` 제공
- WebGL 초기화 실패: 2D 계층 목록과 상세 패널 제공
- 컨텍스트 손실: 1회 안전 재초기화 후 실패 시 2D로 전환
- API 요청 실패: 기존 그래프를 유지하고 오류 상태만 표시
- 탭 이탈: 진행 중 요청 취소, 렌더 루프와 물리 계산 중지

## 11. 테스트 전략

### 11.1 백엔드 단위 테스트

- 핵심 노드 점수와 유형별 할당량
- 결정적인 메인 구조 선택
- 관계 방향 정책
- 검색 우선순위와 별칭 검색
- 상위 1단계 및 제한된 하위 탐색
- 노드·관계 상한과 잘림 메타데이터
- 관리자 권한 거부
- GraphDB 없음, 손상, 노드 없음
- 민감 경로 비노출

### 11.2 프런트엔드 단위 테스트

- API 응답 정규화
- 메인 보기와 집중 보기 상태 전환
- 검색 결과 선택
- 표시 한도와 `더 보기`
- 탭 이탈 시 요청 취소와 렌더러 정리
- WebGL 실패 시 2D 대체
- HTML 삽입 방지를 위한 라벨 이스케이프

### 11.3 브라우저 통합 테스트

- 관리자만 GraphDB 탭 접근 가능
- 메인 구조 렌더링
- 노드 클릭 후 카메라 전환과 상세 패널 갱신
- 검색 후 동일한 집중 보기로 전환
- 메인 구조 복귀
- API 실패와 WebGL 실패 표시
- 반복 진입·이탈 후 중복 이벤트나 렌더 루프가 남지 않음

### 11.4 DGX 실측 테스트

- 개발 PC 원격 접속 기능 검증
- DGX Spark 로컬 브라우저 기능 검증
- 실제 LLM 서버를 올린 상태에서 자원·지연 측정
- 최대 허용 그래프에서 장시간 정지 상태와 반복 탐색 검증

## 12. 예상 파일 경계

세부 구현 계획에서 실제 저장소 상태를 다시 확인한 뒤 다음 책임 경계를 사용한다.

- `src/graph/visualization.py`: 점수, 계층 정책, 부분 그래프 조회
- `src/api/routes/admin_graph.py`: 관리자 GraphDB 읽기 API
- `src/api/schemas/admin_graph.py`: 요청·응답 계약
- `src/api/main.py`: 관리자 GraphDB 라우터 등록
- `frontend/js/modules/admin-graph.js`: API 호출과 데이터 정규화
- `frontend/js/pages/admin-graph.js`: 화면 상태와 상호작용
- `frontend/js/graph/renderer-3d.js`: WebGL 렌더러 수명 주기
- `frontend/html/admin.html`: 관리자 메뉴와 GraphDB 패널
- `frontend/css/admin.css`: GraphDB 화면 스타일
- `frontend/vendor/`: 오프라인 배포용 고정 번들과 라이선스, 해당 방식을 선택한 경우에만 사용
- `tests/test_api_admin_graph.py`: 백엔드 계약과 제한 검증
- `tests/test_admin_graph_frontend.mjs`: 프런트엔드 상태와 안전성 검증
- `tests/e2e/admin-graph.spec.js`: 관리자 탐색 흐름

기존 사용자 변경이 많은 파일과 충돌하지 않도록 구현 시작 전에 `git status --short`와 대상 파일 diff를 다시 확인한다.

## 13. Developer 채팅 인계 요구사항

세부 구현 계획은 Developer 채팅이 추가 설계 추측 없이 실행할 수 있어야 한다.

- 각 단계의 정확한 대상 파일과 책임
- API 요청·응답 예시와 상한
- 계층 관계 정책을 확정하는 사전 프로파일링 명령
- 실패 테스트, 최소 구현, 통과 테스트 순서
- DGX Spark 실측 명령과 기록 양식
- 외부 CDN 금지와 의존성 버전 고정
- 기존 변경 파일 보존과 원격 push 금지
- 구현 완료 후 변경 보고서 작성

Developer 채팅은 먼저 DGX 데이터 분포와 현재 배포 진입점을 검증하고, 검증 결과가 이 설계의 전제와 다를 때 임의로 범위를 넓히지 않고 사용자에게 보고해야 한다.

## 14. 완료 기준

- 관리자가 핵심 GraphDB 구조를 기본 화면에서 이해할 수 있다.
- 검색이나 클릭으로 선택 노드에 자연스럽게 확대된다.
- 상위 1단계와 제한된 하위 트리가 의미 정책에 따라 표시된다.
- 전체 그래프를 클라이언트로 전송하거나 렌더링하지 않는다.
- GraphDB 및 근거 데이터는 읽기 전용으로 유지된다.
- 관리자 권한과 응답 상한을 우회할 수 없다.
- DGX Spark 로컬 브라우저에서 LLM 서버와 함께 초기 성능 목표를 만족한다.
- WebGL 실패 시에도 핵심 정보를 2D 대체 화면으로 확인할 수 있다.
- 탭 이탈 후 불필요한 GPU 렌더링이나 이벤트 리스너가 남지 않는다.
