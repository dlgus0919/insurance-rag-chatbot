# 보험금 계산 스레드 스냅샷 설계

## 목적

보험금 계산과 일반 질의를 하나의 채팅 스레드 안에서 이어갈 수 있게 한다. 실무자는 한 고객의 영수증 계산 결과를 보고, 추가 확인 항목을 질문하고, 나중에 확인 결과를 반영해 같은 스레드에서 재계산 흐름을 이어갈 수 있어야 한다.

대표 흐름:

1. A 고객 영수증으로 보험금 계산 기능을 사용한다.
2. 추가 확인 필요 항목에 대해 일반 질의로 자세한 설명을 묻는다.
3. 실무자가 확인 항목을 확인한 뒤 같은 스레드를 다시 연다.
4. "이 항목을 보상한다면", "이 항목은 보상하지 않는다면", "이 항목이 급여 본인부담으로 확인됐다면" 같은 후속 조건으로 예상 지급액 변화를 질의하고 재계산한다.

## 원칙

- 000번 규칙을 따른다. LLM은 지급 판단이나 금액 산정을 확정하지 않는다.
- 지급액 변경은 기존 보험금 계산 파이프라인을 다시 호출해 산정한다.
- 약관 지식, 공제율, 지급 판단 값은 코드 상수로 새로 만들지 않는다.
- 개인정보성 원문 전체를 저장하지 않는다. 계산에 필요한 입력 항목, 금액, 분류, 계산 결과, 근거 요약만 저장한다.
- 기존 세션/메시지 저장 흐름을 우선 재사용한다.

## 권장 접근

기존 `ChatMessage.sources`에 이미 사용 중인 `assistant_meta` 패턴을 재사용해 보험금 계산 스냅샷을 저장한다. 새 테이블은 만들지 않는다. 현재 요구는 한 스레드 안의 계산 결과 재열람과 후속 질의/재계산이므로, JSON 메타 저장으로 충분하다.

저장 텍스트도 함께 상세화한다. 메타를 읽지 못하는 export, 이전 UI, 운영 점검 상황에서도 사람이 계산 결과를 이해할 수 있어야 하기 때문이다.

## Claim Snapshot 구조

보험금 계산 assistant 메시지의 `sources` 마지막에 다음 형태의 메타를 추가한다.

```json
{
  "__kind": "assistant_meta",
  "claim_snapshot": {
    "schema_version": 1,
    "claim_id": "claim-...",
    "created_at": "ISO-8601",
    "input": {
      "items": [],
      "context": {}
    },
    "result": {
      "claimed_amount": "...",
      "deductible": "...",
      "payable_amount": "...",
      "policy_generation": "4th",
      "calculation_status": "...",
      "line_results": [],
      "review_reasons": [],
      "applied_basis": []
    }
  }
}
```

저장 대상은 API 응답에 이미 있는 필드로 제한한다. 원본 OCR 이미지, 주민번호, 전화번호, 원문 영수증 전체 텍스트는 저장하지 않는다.

## P0: 저장과 재열람

보험금 계산 완료 시 다음을 수행한다.

- assistant 메시지 본문을 상세 텍스트로 저장한다.
- `sources`에 공개 근거와 `claim_snapshot` 메타를 함께 저장한다.
- 채팅 내역 재열람 시 `claim_snapshot`이 있으면 계산 결과 카드로 복원한다.
- `claim_snapshot`이 없는 기존 메시지는 기존 텍스트 렌더링을 유지한다.

상세 텍스트에는 다음을 포함한다.

- 계산 기준
- 총 청구금액, 예상 공제금액, 예상 지급금액
- 항목별 계산 결과
- 추가 확인 필요 항목과 자동 산정 제외 금액
- 항목별 검토 사유
- 적용 근거 요약

## P1: 일반 질의 컨텍스트 연결

일반 질의 생성 시 같은 세션의 모든 `claim_snapshot`을 읽어 프롬프트 앞에 요약 블록으로 붙인다.

블록 예시:

```text
[이 스레드의 보험금 계산 내역]
계산 1:
- 예상 지급금액: 620,000원
- 추가 확인 필요: 미분류 비급여 120,000원
- 검토 사유: 급여/비급여 구분 확인 필요
```

스레드 안에서 여러 계산이 있으면 모두 포함한다. 다만 프롬프트 과대화를 막기 위해 각 계산은 핵심 필드만 요약하고, 전체 길이가 일정 기준을 넘으면 오래된 계산부터 더 짧게 압축한다.

## P2: 조건부 재계산

사용자가 이전 계산의 추가 확인 항목에 대해 다음처럼 말할 수 있다.

- "도수치료 항목을 보상한다면 지급액이 어떻게 달라지나요?"
- "이 비급여 항목은 보상하지 않는다면 그대로 0원인가요?"
- "추가 확인 항목이 급여 본인부담으로 확인됐다면 다시 계산해 주세요."
- "MRI는 보상 대상이고, 나머지 비급여는 보상 제외라면 얼마인가요?"

처리 원칙:

1. 시스템은 같은 스레드의 `claim_snapshot`에서 대상 계산과 대상 항목 후보를 찾는다.
2. 항목명과 변경 의도가 명확하면 수정된 계산 입력을 만든다.
3. 실제 지급액은 기존 보험금 계산 파이프라인으로 다시 계산한다.
4. 대상 항목이나 변경 의미가 모호하면 계산하지 않고 확인 질문을 반환한다.

허용하는 1차 변경 의도:

- 보상한다면: 해당 Human Task 항목을 자동 계산 대상으로 전환할 수 있는지 확인한다. 분류가 여전히 불명확하면 사용자에게 급여/비급여/3대비급여 등 분류 확인을 요청한다.
- 보상하지 않는다면: 해당 항목을 지급액 0원으로 유지하는 조건부 결과를 설명한다.
- 급여 본인부담으로 확인됐다면: 기존 금액을 급여 본인부담 항목으로 재입력해 계산한다.
- 비급여로 확인됐다면: 기존 금액을 비급여 항목으로 재입력해 계산한다.
- 3대비급여로 확인됐다면: 기존 금액을 3대비급여 항목으로 재입력해 계산한다.

금지하는 1차 변경 의도:

- LLM이 "보상 대상" 여부를 임의 확정하는 것
- LLM이 공제율, 한도, 지급률을 생성하는 것
- 원문 근거 없이 새 약관 규칙을 만드는 것

## 프론트엔드 동작

- 보험금 계산 직후에는 현재 계산 결과 카드 표시를 유지한다.
- 좌측 채팅 내역에서 다시 열 때도 `claim_snapshot` 기반으로 같은 계산 결과 카드를 표시한다.
- 일반 질의 모드로 전환해도 `currentSession`은 유지한다.
- 계산 모드에서 다시 계산하면 같은 스레드에 새 계산 스냅샷이 추가된다.

## 백엔드 동작

- `claim` route는 계산 결과 저장 시 `claim_snapshot` 메타를 추가한다.
- `chat` route는 히스토리 로드 후 같은 세션의 `claim_snapshot`을 추출해 일반 질의 프롬프트에 추가한다.
- 조건부 재계산은 별도 후속 단계에서 구현한다. 이때도 최종 산정은 `run_claim_calculation`을 사용한다.

## 테스트

필수 테스트:

- 보험금 계산 저장 메시지에 상세 텍스트와 `claim_snapshot`이 포함된다.
- 세션 메시지 조회 시 `claim_snapshot`이 공개 출처로 노출되지 않는다.
- 프론트엔드가 `claim_snapshot` 메시지를 계산 결과 카드로 복원한다.
- 일반 질의 프롬프트에 같은 세션의 계산 스냅샷 요약이 포함된다.
- 기존 일반 질의와 기존 보험금 계산 API 응답은 깨지지 않는다.

P2 구현 시 추가 테스트:

- "보상하지 않는다면"은 기존 Human Task 0원 상태를 유지해 설명한다.
- "급여 본인부담으로 확인됐다면"은 기존 계산 파이프라인을 다시 호출한다.
- 모호한 항목명은 재계산하지 않고 확인 질문을 반환한다.

## 한계

- P0/P1은 후속 설명 품질을 높이지만, 조건부 재계산까지 자동 완성하지는 않는다.
- P2 자연어 해석은 오인식 가능성이 있으므로 명확한 경우에만 자동 재계산한다.
- 스레드에 계산이 과도하게 많으면 프롬프트 길이를 제한해야 한다.
- 기존 과거 메시지는 `claim_snapshot`이 없으므로 상세 카드 복원이 제한된다.

## 완료 기준

- 한 스레드에서 보험금 계산과 일반 질의를 섞어도 세션이 유지된다.
- 좌측 채팅 내역 재열람 시 보험금 계산 결과가 상세하게 보인다.
- 일반 질의가 같은 스레드의 보험금 계산 내역을 참조해 설명할 수 있다.
- 조건부 재계산은 LLM 단독 계산이 아니라 기존 결정론 계산 파이프라인을 통해 수행하도록 설계가 고정된다.
