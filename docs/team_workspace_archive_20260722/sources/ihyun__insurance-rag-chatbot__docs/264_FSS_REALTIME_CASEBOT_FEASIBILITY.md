# 264. FSS 사례 실시간 챗봇 반영 가능성 검토

## 결론

금융감독원 금융분쟁조정 사례 페이지를 챗봇 지식에 "실시간"으로 직접 연결하는 방식은 내부망 운영 전제에서는 불가능하거나 비권장이다.

가능한 대안은 외부망에서 사례집/PDF/HTML을 정기 수집한 뒤, 보안 검토와 실무자 승인을 거쳐 내부망 챗봇에 반입하는 방식이다. 현재 프로젝트의 관리자 문서 intake, 후보 검토, 승인 후 인덱스/GraphDB 반영 구조와도 이 방식이 더 잘 맞는다.

## 검토 대상

- URL: `https://www.fss.or.kr/fss/job/fncCnflCase/list.do?menuNo=200516`
- 성격: 금융감독원 금융분쟁조정 사례 목록/사례집 성격의 외부 공개 자료
- 주의: 엄밀히는 법원 판례가 아니라 금융분쟁조정 사례이므로, 챗봇 UI와 답변에서는 "판례"와 "분쟁조정 사례"를 구분하는 것이 안전하다.

## 실시간 연동이 어려운 이유

1. 내부망에서 외부 사이트 접근이 막힐 가능성이 높다.
   - 챗봇 서버가 금감원 사이트에 직접 outbound 요청을 보내야 실시간 조회가 가능하다.
   - 내부망/폐쇄망 운영이면 DNS, HTTPS, 방화벽, 프록시, 인증서 검증, 감사 정책에서 차단될 수 있다.

2. 외부 페이지 구조가 안정적인 API가 아닐 수 있다.
   - 공개 웹 목록은 HTML, 검색 파라미터, 첨부파일 링크 구조가 바뀔 수 있다.
   - 크롤러가 깨지면 챗봇 근거가 누락되거나 오래된 자료를 최신처럼 답할 위험이 있다.

3. 보안 검토 없이 자동 반입하면 위험하다.
   - 외부 HTML/PDF를 내부망에 자동 저장하면 악성 파일, 스크립트, 파일명/메타데이터 오염, 파서 취약점 문제가 생길 수 있다.
   - 내부망 반입 자료는 백신 검사, 확장자 제한, 해시 기록, 반입 승인 로그가 필요하다.

4. 저작권/이용조건 확인이 필요하다.
   - 공개 자료라고 해서 내부 서비스에 자동 복제, 재가공, 재배포가 항상 허용되는 것은 아니다.
   - 챗봇에는 출처 URL, 수집일, 문서 제목, 원문 근거를 함께 남겨야 한다.

5. "실시간"은 RAG 품질과도 잘 맞지 않는다.
   - 새 문서를 바로 검색에 넣으면 chunking, embedding, BM25/Chroma 인덱스, GraphDB 반영, 품질 검증이 필요하다.
   - 검증 없이 자동 반영하면 잘못 추출된 표/문장이나 중복 문서가 답변 근거로 노출될 수 있다.

## 가능한 구현안

### 권장안: 정기 반입 + 승인 반영

외부망 또는 허가된 수집 서버에서 금감원 자료를 주기적으로 내려받고, 내부망에는 검증된 파일 묶음만 반입한다.

흐름:

1. 외부망에서 사례 목록과 첨부 PDF/HTML을 수집
2. 파일 해시, 수집일, 원본 URL, 제목, 게시일 메타데이터 생성
3. 보안 검사 후 내부망 반입
4. 관리자 문서 intake로 dry-run 처리
5. 실무자 검토/승인
6. 승인된 문서만 active source overlay, 검색 인덱스, GraphDB에 반영

장점:

- 내부망 보안 정책과 충돌이 적다.
- 현재 프로젝트의 지식 반영 원칙과 맞다.
- 답변 근거의 출처, 버전, 수집일을 남길 수 있다.

단점:

- 완전 실시간은 아니다.
- 수집/반입 운영 절차가 필요하다.

### 조건부 가능안: 내부망 프록시/DMZ 중계

보안팀이 특정 도메인 allowlist, 프록시, DMZ 중계 서버를 승인하면 준실시간 연동은 가능하다.

필수 조건:

- `fss.or.kr` 도메인 outbound 접근 승인
- 수집 서버와 챗봇 서버의 권한 분리
- 크롤링 주기 제한과 실패 알림
- 원문 저장소, 해시, 수집 로그, 감사 로그
- 인덱스 반영 전 관리자 승인 단계

이 경우에도 챗봇 요청 시마다 실시간으로 외부 사이트를 조회하는 방식보다는, 중계 서버가 주기적으로 수집하고 내부 챗봇은 승인된 내부 사본만 조회하는 방식이 안전하다.

### 비권장안: 사용자 질문마다 외부 사이트 실시간 조회

사용자가 질문할 때마다 챗봇이 금감원 페이지를 직접 검색/크롤링하는 방식은 운영에 부적합하다.

문제:

- 내부망에서 동작하지 않을 가능성이 높다.
- 응답 속도가 외부 사이트 상태에 종속된다.
- 외부 페이지 장애가 챗봇 장애로 이어진다.
- 수집 결과를 검증하기 전에 답변 근거로 사용하게 된다.
- 감사/재현성이 떨어진다.

## 현재 프로젝트 기준 판단

현재 레포의 원칙은 신규 문서를 즉시 운영 지식으로 넣지 않고, dry-run intake와 실무자 승인을 거친 뒤 active source/index/GraphDB에 반영하는 것이다.

따라서 금감원 사례집도 다음처럼 다루는 것이 맞다.

- 실시간 직접 연동: 불가 또는 비권장
- 정기 수집 후 내부망 반입: 가능
- 관리자 업로드/승인 기반 반영: 가능
- 자동 승인 없는 즉시 인덱싱: 비권장

## 제안 문구

피드백에 대한 답변은 아래처럼 정리할 수 있다.

> 금감원 금융분쟁조정 사례를 챗봇 근거로 활용하는 것은 가능하지만, 내부망 운영 환경에서는 외부 사이트를 실시간으로 직접 조회하는 방식은 어렵습니다. 대신 외부망에서 정기적으로 사례집을 수집하고, 보안 검토 및 실무자 승인 후 내부망 지식 인덱스에 반영하는 방식으로 구현하는 것이 현실적입니다. 이 방식은 최신성은 일/주 단위로 제한되지만, 보안성과 답변 근거의 재현성을 확보할 수 있습니다.

## 후속 작업

- 금감원 자료 이용조건과 내부 재가공 가능 범위 확인
- 외부망 수집 주기 결정: 일 1회, 주 1회 등
- 수집 대상 범위 확정: 목록 HTML, 상세 HTML, 첨부 PDF
- 반입 패키지 포맷 정의: 원문 파일, manifest, hash, source URL, collected_at
- 관리자 intake에서 출처 URL/수집일이 답변 근거로 노출되는지 확인
