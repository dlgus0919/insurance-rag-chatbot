# 신한EZ손해보험 보험 RAG 챗봇

## 2차 발표 준비 상세본

**주제:** 단순 문서 검색 RAG에서 문서 근거 기반 보험 보상 판단 지원 시스템으로의 확장  
**기준일:** 2026-06-15  
**프로젝트:** `insurance-rag-chatbot`

---

# 1. 발표 핵심 메시지

중간발표 당시 프로젝트는 보험 약관, 심평원 자료, 실무가이드, 상담사례집을 검색하고 출처와 함께 답변하는 OCR 기반 하이브리드 RAG 챗봇이었다.

중간발표 이후에는 다음 기능을 추가하면서 프로젝트의 범위를 확장했다.

- GraphDB를 실제 RAG와 보험금 계산 경로에 연결
- 약관과 사례를 문서 기반 보상 검토 경로로 구조화
- 보험금 계산 보조 기능을 SPA에 통합
- 실무자 승인형 온톨로지 운영 체계 구축
- 질문 유형별 검색 라우팅과 RAG 파라미터 자동 조절
- E2E, review path, 모델-인덱스 조합, 결함 유형 중심으로 평가 체계 확대
- DGX Spark에서 실행 가능한 운영형 웹 서비스 구조 정리

> 이번 단계의 핵심은 AI가 그럴듯한 답을 만드는 것이 아니라, 답변과 계산 결과가 실제 약관·지침·코드·증빙 근거와 연결되도록 만드는 것이었다.

# 3. 현재 시스템 구조

```text
사용자
  ↓
FastAPI + SPA
  ├─ 일반 질의
  ├─ 보험금 계산
  ├─ 세션 관리
  └─ 관리자 진단
  ↓
질문 분석 및 자동 라우팅
  ├─ 일반 설명 검색
  ├─ 퀵 코드 검색
  └─ 약관 조항 검색
  ↓
Hybrid RAG
  ├─ BM25 키워드 검색
  ├─ ChromaDB 벡터 검색
  ├─ RRF 결과 결합
  └─ reranker 재정렬
  ↓
GraphRAG
  ├─ 수술·수가·약관 관계
  ├─ 조항·사례·판단 조건
  ├─ 필요 증빙
  └─ 검토 조치
  ↓
로컬 LLM
  ↓
답변 + 출처 + 구조화 근거 + 검토 필요 사항
```

현재 시스템은 단일 Vector DB만 사용하는 구조가 아니다.

- 비정형 문서 검색: ChromaDB, BM25
- 문서 관계 및 검토 경로: SQLite GraphDB
- 비급여 표준코드: 관계형 SQLite
- 수술종수·장해율 등 구조화 표: Parquet
- 답변 생성: SGLang, vLLM, Ollama 기반 로컬 LLM

# 4. GraphDB: 계획에서 실제 운영 기능으로

## 4.1 도입 목적

기존 Vector RAG는 질문과 유사한 문장을 찾는 데 강하지만 다음과 같은 관계를 직접 검증하기 어렵다.

- 특정 수술이 몇 종 수술에 해당하는가
- 수술명과 HIRA 수가코드가 어떻게 연결되는가
- 어떤 약관 별표와 지급비율이 적용되는가
- 어떤 조건에서 보상, 면책 또는 추가 심사가 필요한가
- 판단을 위해 어떤 증빙이 추가로 필요한가

이를 보완하기 위해 문서에서 추출한 보험 지식을 노드와 엣지로 구조화했다.

## 4.2 현재 GraphDB의 두 계층

### 수술·수가·약관 구조화 계층

- `SurgeryProcedure`: 수술명
- `SurgeryGrade`: 수술종수
- `SurgeryCategory`: 수술 분류
- `MedicalFeeCode`: HIRA 수가코드
- `PolicyAppendix`: 약관 별표
- `PolicyBenefitRule`: 지급 규칙
- `CoverageItem`: 보장 항목
- `NonpayStandardCode`: 비급여 표준코드

주요 관계:

- `HAS_GRADE`: 수술명과 수술종수 연결
- `HAS_MEDICAL_FEE_CODE`: 수술명과 수가코드 연결
- `POLICY_COVERS_PROCEDURE`: 약관 별표와 수술 연결
- `PAYS_BY_RATIO`: 지급비율 연결

### 문서 기반 보상 판단 계층

- `PolicyClause`: 약관 조항
- `CaseExample`: 상담·분쟁 사례
- `ClaimCondition`: 적용 조건
- `DecisionConcept`: 보상, 면책, 조건부 판단
- `EvidenceRequirement`: 필요 증빙
- `DiagnosisCode`: 문서에 등장한 진단코드
- `ComplicationConcept`: 합병증·후유증 등 검토 개념
- `ReviewAction`: 담당자 검토 조치
- `PolicyGeneration`: 실손 세대
- `VisitContext`: 입원·통원 맥락
- `FacilityContext`: 의료기관 맥락

주요 관계:

- `APPLIES_WHEN`: 조항의 적용 조건
- `HAS_DECISION`: 조항과 판단 결과 연결
- `REQUIRES_EVIDENCE`: 판단에 필요한 증빙 연결
- `HAS_REVIEW_ACTION`: 담당자가 수행할 검토 조치 연결
- `SIMILAR_CASE_FOR`: 유사 사례 연결

## 4.3 GraphDB가 제공하는 실무 가치

- 수술명, 수술종수, 수가코드, 약관 별표를 한 흐름으로 조회
- 보상 가능성뿐 아니라 적용 조건과 예외 조건을 함께 확인
- 필요한 진단서, 영수증, 세부내역서 등 증빙 요구를 표시
- 근거 부족 시 확정 답변 대신 추가 확인이나 사람 검토로 전환
- Graph 노드와 엣지에 원문 evidence를 연결해 판단 출처 추적

## 4.4 사실 상태 구분

GraphDB에서 검색된 정보는 모두 확정 사실로 취급하지 않는다.

| 상태 | 의미 | 답변 처리 |
|---|---|---|
| `confirmed` | 문서 근거와 관계가 충분히 확인됨 | 확정 근거로 표시 |
| `candidate` | 관계 후보이나 추가 검증 필요 | 검토 필요 영역으로 분리 |
| `review_required` | 실무자 판단 또는 추가 증빙 필요 | 검토 조치 제시 |
| `missing` | 구조화 근거가 부족하거나 없음 | 단정하지 않고 누락 표시 |

이 구분은 LLM이 후보 관계를 확정적인 지급 판단처럼 말하지 않도록 하기 위한 안전장치다.

## 4.5 의학 인과 그래프와의 차이

현재 GraphDB는 질병 간 의학적 인과관계를 추론하는 그래프가 아니다.

- 질병이 특정 합병증을 일으킨다고 자동 판단하지 않음
- 특정 질병에 특정 시술이 필요하다고 일반화하지 않음
- 외부 의학 상식을 근거 없이 보험 판단에 사용하지 않음

대신 사용자가 제시한 청구 상황을 약관 조항, 사례, 증빙 요건과 연결해 **문서 근거 기반 검토 경로**를 만든다.

## 4.6 근거 정합성 개선

중간발표 당시 주요 한계는 GraphDB와 RAG 검색 결과의 근거 연결 불일치였다.

이후 다음 기능을 추가했다.

- Graph 노드와 엣지에 `source_evidence_id` 저장
- Graph evidence와 원문 chunk 연결
- GraphDB와 VectorStore의 chunk key 동기화 검사
- canonical chunk manifest 도입
- 관리자 페이지에서 Graph/vector 동기화 상태 진단
- 근거가 확인되지 않은 candidate rule을 확정 영역에서 제외

# 5. 보험금 계산 보조 기능

## 5.1 구현 범위

SPA의 보험금 계산 화면에서 다음 정보를 입력할 수 있다.

- 청구 항목명
- 의료·비급여 코드
- 청구 금액과 수량
- 실손 세대
- 입원·통원 구분
- 급여·비급여 분류
- 진단코드
- 보장 주제
- 청구 상황 메모

계산 결과는 다음과 같이 구조화해 제공한다.

- 총 청구금액
- 예상 공제금액
- 예상 지급금액
- 항목별 계산 결과
- 적용한 계산 기준
- 검토가 필요한 이유
- 코드 또는 보장 후보
- GraphDB 기반 검토 경로

## 5.2 주요 개선 사항

- 4세대와 5세대 실손 공제 규칙 분리
- 복수 청구 항목별 `line_results` 계산
- 급여·비급여, 중증·비중증 맥락 반영
- 비급여 표준코드 후보 검색
- 불명확한 항목은 `requires_review`로 전환
- 미해결 비급여 항목은 human task로 전달
- 계산 결과와 근거를 프론트엔드에서 분리 표시

## 5.3 현재 한계

현재 기능은 완전 자동 보험금 심사 시스템이 아니다.

- 영수증·진단서 파일 업로드 후 자동 분류·추출하는 전체 과정은 미완성
- 입력 정보가 부족하면 정확한 계산을 확정할 수 없음
- 비급여 표준코드가 여러 개 매칭되면 실무자 선택이 필요
- 약관상 면책·한도·특약 우선순위를 모두 자동 확정하지 않음

> 현재 단계는 보험금을 자동 확정하는 시스템이 아니라, 입력 정보를 바탕으로 계산 결과와 검토 사유를 구조화하는 보조 시스템이다.

# 6. RAG 검색 방식 개선

## 6.1 검색 모드 자동 라우팅

기존에는 사용자가 일반 질의, 퀵 코드, 약관 정형 검색을 직접 선택해야 했다.

현재는 기본 화면을 일반 질의로 단순화하고 내부 라우터가 질문을 다음 전략 중 하나로 분류한다.

- `general`: 일반 설명 및 종합 검색
- `quickcode`: 수가·진단·수술 코드 중심 검색
- `formal`: 약관 조항과 별표 중심 검색

운영 감사 로그에는 다음 진단 정보가 저장된다.

- 최종 선택된 검색 경로
- 질문 의도
- 라우팅 이유
- 감지된 핵심 표현

## 6.2 자동 RAG 파라미터 조절

질문 유형에 따라 검색 범위와 답변 생성 온도를 자동 조절한다.

- 코드·조항 조회: 낮은 temperature와 집중된 검색
- 보장 판단·조건 비교: 근거 누락을 방지하기 위한 넓은 검색
- 모호한 의료 표현: 소폭 높은 temperature 허용
- 일반 설명: 설명력을 위한 제한적 temperature 적용

운영 기본값:

- `AUTO_RAG_PARAMS_MODE=apply`
- `AUTO_RAG_TOPK_STRATEGY=rule`

40문항 평가 결과:

| 전략 | 통과 | 통과율 |
|---|---:|---:|
| 규칙 기반 자동 조절 | 29/40 | 72.5% |
| 고정 baseline | 28/40 | 70.0% |
| reranker threshold 자동 조절 | 28/40 | 70.0% |

reranker 점수만으로 후보를 과도하게 줄이는 방식은 일부 필수 근거를 제거해 기본값으로 채택하지 않았다.

# 8. LLM 운영 모델 선정

## 8.1 현재 역할별 모델

| 역할 | Provider | 모델 | 선정 이유 |
|---|---|---|---|
| 일반 질의 답변 주력 | SGLang | `qwen3-next-80b-a3b-instruct-fp8` | 40문항 평가 최고 통과율 |
| 온톨로지 후보 정제 | SGLang | `qwen3-30b-a3b-instruct-2507-fp8` | 구조화된 후보 설명과 batch 작업에 적합 |
| 저부하 fallback | SGLang | `gpt-oss-20b` | 상대적으로 낮은 부하와 안정적 출력 |
| Ollama fallback | Ollama | `exaone3.5:7.8b` | 빠른 로컬 fallback |
| 이미지 인식 후보 | vLLM | `gemma-4-31b-it-nvfp4` | 비전 후보 기능 보존 |

검색 계층 모델:

# 9. 평가 체계의 변화

## 9.1 기존 평가

기존 평가는 검색과 답변의 기본 동작을 확인하는 smoke test 중심이었다.

- 상위 검색 결과에 정답 근거가 포함되는지
- 출처 페이지가 정확한지
- 답변에 필수 키워드가 포함되는지
- LLM이 정상적으로 응답하는지

## 9.2 E2E 평가

현재는 사용자의 실제 이용 흐름 전체를 검증한다.

```text
로그인
→ 질문 입력
→ 검색
→ GraphDB 조회
→ LLM 스트리밍
→ 출처·경고 표시
→ 세션 저장
```

검색과 모델이 정상이어도 API 스트리밍, 세션 저장, 화면 렌더링이 실패하면 서비스 전체로는 실패한 것으로 본다.

## 9.3 Graph review path 평가

정답 문장만 확인하지 않고 다음 검토 경로가 적절하게 생성되는지 평가한다.

- 관련 약관 조항
- 적용 조건
- 보상·면책·조건부 판단 후보
- 필요한 증빙
- 담당자 검토 조치
- 사람 검토 필요 여부

## 9.4 모델×인덱스 매트릭스 평가

답변 품질은 LLM뿐 아니라 어떤 인덱스를 사용하는지에도 영향을 받는다.

따라서 다음 조합을 비교한다.

```text
모델
  × 기본 인덱스
  × OCR 보정본 인덱스
  × 원본+보정본 통합 인덱스
```

이를 통해 단순히 가장 큰 모델을 선택하는 대신, 특정 문서와 질문 유형에서 가장 안정적인 모델·인덱스 조합을 찾는다.

## 9.5 결함 유형 분석

평가 실패를 하나의 정확도 점수로만 처리하지 않고 원인별로 분류한다.

| 결함 유형 | 의미 | 개선 대상 |
|---|---|---|
| Retrieval defect | 정답 근거 검색 실패 | 검색어 확장, BM25/vector 조정 |
| Index defect | OCR 오류, chunk 누락 | OCR·청킹·인덱스 재구축 |
| Graph defect | 관계 또는 evidence 연결 오류 | extractor·Graph 빌드 수정 |
| Generation defect | 근거는 있지만 숫자·조건 누락 | 프롬프트·모델 수정 |
| Grounding defect | 근거에 없는 내용 생성 | evidence guardrail 강화 |
| Format defect | 반복, reasoning 노출, 응답 중단 | 모델 템플릿·서빙 수정 |
| API/UI defect | 스트리밍·렌더링·세션 오류 | 서비스 코드 수정 |
| Evaluation defect | 답변은 맞지만 채점 규칙이 부정확 | 평가셋 기준 수정 |

이 방식은 “모델 정확도가 낮다”에서 끝나지 않고 실제로 어느 계층을 수정해야 하는지 판단할 수 있게 한다.

# 10. 실무자 승인형 온톨로지

## 10.1 도입 배경

보험 용어와 약관 표현은 검색 품질을 높이기 위해 지속적으로 확장해야 한다. 그러나 잘못된 동의어, 지급 표현, 면책 표현을 자동 반영하면 위험하다.

따라서 후보 생성은 자동화하되 운영 반영에는 실무자 승인을 요구하도록 설계했다.

## 10.2 운영 흐름

```text
원천 문서·Graph evidence
→ 온톨로지 후보 추출
→ 품질·위험도 검사
→ 실무자 승인 / 보류 / 거절
→ 승인 로그 기록
→ active manifest 병합
→ RAG와 Graph planner에서 사용
```

주요 산출물:

- 후보 저장소
- 승인·보류·거절 로그
- 적용 로그
- active ontology manifest
- CLI 검토 도구
- DGX 로컬 검토 GUI

## 10.3 안전장치

- 기본 manifest 직접 수정 금지
- 운영 후보 전체 자동 승인 금지
- 지급·면책·감액·계산 규칙 자동 승인 금지
- source evidence가 없는 후보 자동 승인 금지
- 승인 결과와 적용 결과를 별도 로그로 보존
- 문제가 발생하면 이전 manifest로 복구 가능

> 보험 도메인에서는 자동으로 확장되는 지식보다, 근거와 승인 이력을 확인할 수 있는 지식이 더 중요하다.

# 11. 현재 확인된 주요 한계

## 11.1 표와 코드 검색

- 심평원 표의 다중 행 구조 검색이 여전히 어려움
- 코드가 여러 표와 문서에 중복 등장하면 잘못된 출처가 선택될 수 있음
- OCR 표는 행 단위 grounding이 충분하지 않은 경우가 있음

## 11.2 비급여 표준코드 매칭

- 하나의 항목명에 여러 표준코드 후보가 생성될 수 있음
- 도수치료, MRI, 표적항암제 등에서 특수 코드와 일반 코드가 충돌 가능
- 계산 전에 후보를 선택하거나 추가 정보를 받는 UI가 필요

## 11.3 Graph 조항 구조

- 일부 조항은 아직 chunk 단위로 구성되어 조·항·호·단서 구분이 거칠 수 있음
- 보상 조항과 면책 단서가 같은 chunk에 있으면 관계 범위가 넓어질 수 있음
- 약관 우선순위와 충돌 해결 규칙의 추가 구조화가 필요

## 11.4 완전 자동 심사와의 차이

- 문서 업로드부터 최종 보험금 확정까지 완전 자동화된 상태가 아님
- 의학적 인과관계를 AI가 확정하지 않음
- 구조화 근거가 부족하면 사람 검토를 요구
- 시스템의 역할은 최종 결정이 아니라 검색·계산·검토 지원

# 14. 발표용 요약 문장

## 30초 요약

중간발표 이후 프로젝트는 OCR 기반 보험 문서 검색 챗봇에서 GraphRAG 기반 보상 판단 지원 시스템으로 확장됐다. GraphDB를 실제 RAG와 보험금 계산 경로에 연결해 수술, 수가코드, 약관 조항, 지급 조건, 필요 증빙을 관계 기반으로 조회할 수 있게 했다. 또한 질문 자동 라우팅, RAG 파라미터 자동 조절, 실무자 승인형 온톨로지, E2E·review path 중심 평가 체계를 추가해 운영 안전성을 강화했다.

## GraphDB 강조 요약

중간발표 당시 GraphDB는 도입 계획과 한계 분석 단계였다. 현재는 SQLite 기반 GraphDB가 실제 운영 RAG에 연결되어 수술명, 수술종수, 수가코드, 약관 별표뿐 아니라 약관 조항, 사례, 적용 조건, 증빙 요구, 검토 조치까지 구조화한다. 이를 통해 챗봇은 유사 문서를 보여주는 수준을 넘어, 어떤 근거와 조건을 따라 검토해야 하는지 설명할 수 있게 됐다.

## 평가 체계 요약

기존에는 검색 상위 결과와 LLM 답변 정확도를 확인하는 기본 평가가 중심이었다. 현재는 로그인부터 답변 표시까지의 E2E 흐름, GraphDB가 생성한 review path, 모델과 인덱스 조합별 성능, 검색·인덱스·Graph·생성·UI 계층별 결함 원인을 함께 평가한다.

# 15. 마무리 메시지

이번 단계에서 가장 중요하게 본 기준은 다음과 같다.

1. 답변이 실제 문서 근거와 연결되어 있는가
2. 확정 근거와 검토 후보가 구분되어 있는가
3. 계산 결과에 적용 기준과 보류 사유가 함께 표시되는가
4. AI가 판단할 수 없는 부분을 사람 검토로 안전하게 넘기는가
5. 운영 중 발생한 실패 원인을 재현하고 개선할 수 있는가

현재 시스템은 완전 자동 보험금 심사 시스템은 아니다. 그러나 단순 문서 검색 챗봇에서 벗어나, 보험 약관과 의료코드, 사례, 증빙 요구를 연결하고 보상 담당자의 검색·계산·검토 업무를 지원하는 플랫폼으로 확장할 기반을 마련했다.
