단순 검색 RAG → 보상 판단 지원 시스템으로 확장

2026-06-15 · insurance-rag-chatbot

# **1\. 핵심 메시지**

*기존 챗봇이 “근거를 찾아 답하는 RAG”였다면, 이후 작업은 이를 보상 판단 경로, 보험금 계산, 운영 배포, 실무자 승인형 온톨로지까지 연결한 보험 업무 지원 시스템으로 확장한 과정입니다.*

지난 발표는 RAG 챗봇 구조(OCR, Hybrid RAG, FastAPI/SPA, LLM 비교, GraphDB 도입 가능성)를 소개했고, 이번 발표는 그 이후의 확장 작업에 초점을 둡니다.

## **2\. 한눈에 보는 변화**

| 구분 | 지난 발표 | 이후 작업 |
| :---- | :---- | :---- |
| RAG | 텍스트/OCR 하이브리드 검색 | Graph 구조화 근거·검토 경로를 답변에 병합 |
| GraphDB | 도입 계획, 초기 한계 | 조항·사례·증빙·면책/한도/공제 rule node로 확장 |
| 보험금 계산 | 확장 방향 제시 | 4/5세대 실손, 복수 항목 계산, 검토 필요 상태 구현 |
| 프론트/백엔드 | 챗봇 UI·API 소개 | SPA/API 통합, 관리자 진단, Graph 근거 표시 |
| 평가 | 기본 RAG/LLM 평가 | E2E·review path·모델×인덱스 매트릭스·결함 분석 |
| 온톨로지 | 고도화 필요성 | 실무자 승인 workflow, 후보 생성 MVP, 정책 외부화 |

# **3\. 주요 작업**

## **3.1 GraphRAG 기반 보상 판단 경로**

GraphDB를 단순 수술/수가 매핑이 아니라 문서 기반 보상 판단 그래프로 확장했습니다.

* 약관 조항·사례·판단 조건·증빙·진단코드·검토 조치를 노드로 구조화

* APPLIES\_WHEN / REQUIRES\_EVIDENCE / HAS\_REVIEW\_ACTION 등으로 적용 조건·검토 액션 연결

* confirmed · candidate · review\_required · missing 상태 구분 → 후보 근거를 확정 사실처럼 말하지 않도록 설계

*GraphDB는 의학 일반지식 그래프가 아니라, 우리 문서에 근거한 보상 판단 경로 그래프입니다.*

## **3.2 면책·한도·공제·필요서류 rule node**

rule을 속성이 아닌 독립 노드로 승격했습니다.

* ExclusionReason(면책) · BenefitLimit(한도) · DeductibleRule(공제) · RequiredDocument(필요서류) · CoordinationRule(중복보상) · RenewalOrGenerationRule(세대/갱신)

* 단, rule node는 금액을 임의 계산하지 않고 계산 설명·review trigger로만 사용

## **3.3 보험금 계산 구현과 한계**

* /api/claim/calculate 구현, 4/5세대 실손 선택, 복수 항목 line\_results 계산

* 급여/비급여/중증·비중증 구분 공제 반영, 항목 불명확 시 requires\_review 표시

**발견한 한계:**

* 도수치료·MRI·표적항암제 등 비급여 표준코드가 특수 면책 코드로 잘못 매칭 (LLM 문제가 아닌 Standard Matcher 우선순위·disambiguation 문제)

*자동 계산보다 중요한 것은 불확실한 항목을 무리하게 확정하지 않고 검토 필요로 넘기는 안전장치입니다.*

## **3.4 운영형 웹앱 구조 정리**

* FastAPI가 API \+ 정적 SPA 동시 제공, 로그인·채팅·관리자 화면 구성

* /api/chat/stream(SSE), /api/sessions/\*(세션), /api/admin/\*(감사로그·통계·진단)

* Graph 근거·검토 경로 UI 표시, 보험금 계산 패널 통합, 모델/인덱스 선택 개선

## **3.5 평가 체계 확장 (결함 유형 분석)**

* Graph QA·review path 평가, 보험금 계산 E2E, 모델×인덱스 매트릭스, 회귀/payload 테스트

**주요 학습:**

* 실패 다수가 LLM이 아닌 retrieval\_miss·표 row-level 검색·source coverage 문제에서 발생

* 심평원 표 코드·다중 행 표·문서별 코드 분리 질의는 여전히 취약 → 다음 개발 우선순위로 확인

## **3.6 LLM 운영 후보 정리**

* SGLang/vLLM/Ollama provider 경로 유지, Qwen Thinking reasoning leak 차단, Llama 3.3 70B enablement

* 다운로드됨 / 기동 검증됨 / 기본 후보 / 비활성 상태를 분리 관리 (예: gpt-oss-120b는 메모리 부족으로 비활성)

## **3.7 실무자 승인형 온톨로지 workflow**

후보 생성은 자동화하되, 실무자가 승인한 후보만 active manifest에 반영합니다.

* 후보(candidates.jsonl) → 승인 로그 → 적용 로그 → active manifest, CLI·검토 GUI 제공

**안전장치:**

* 운영 manifest 직접 수정 금지, 전체 자동 승인 금지, 지급/면책/감액/계산 rule·근거 없는 후보 자동 승인 금지

*보험 도메인에서는 자동 지식 확장보다 승인 가능한 지식 확장이 중요합니다.*

## **3.8 운전자보험 조항 세부 질의 패치**

* clause\_detail\_lookup intent 추가, 담보명·조항 표제어 보강 검색, 중복 source 제거, deterministic 요약 생성

# **4\. 진행 중 / 예정 (현재 상태)**

*아래 항목은 완료 사실로 단정하지 않고 현재 상태로 표현합니다.*

## **4.1 검색 라우팅·파라미터 자동 조절**

* 질문 유형별 검색 전략 자동 선택, top-k·temperature 자동 조절 로직 반영 중 (수동 → 자동 설정 구조로 전환 중)

* 사용자 화면은 단순화, 내부는 질문 분류·index routing·reranking 고도화

## **4.2 Q\&A 평가셋·모델 재평가**

* 현재 40문항 기반 1차 평가 완료 (파라미터 자동 설정 반영 전 상태)

* 자동 조절 로직 수정 후 확장 질문셋으로 모델별 재평가 예정 (문항 수는 확장 가능)

*평가셋은 현재 40문항 기반 1차 테스트를 진행했고, 자동 조절 로직 반영 후 확장 질문셋으로 모델별 재평가를 진행할 예정입니다.*
