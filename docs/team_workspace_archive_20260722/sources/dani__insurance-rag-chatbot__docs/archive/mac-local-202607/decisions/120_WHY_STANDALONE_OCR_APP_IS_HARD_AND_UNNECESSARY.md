# 120. OCR 인식 전용 앱을 만들기 어려운 이유와 이 프로젝트에서 불필요한 이유

작성일: 2026-06-17

## 결론

OCR 자체는 이 프로젝트에 필요하다. 하지만 별도의 OCR 인식 전용 앱을 새로 만드는 것은 현재 목적에 비해 비용과 위험이 크다.

이 프로젝트의 목표는 "문서를 글자로 읽는 앱"이 아니라 "보험금 계산에 필요한 근거를 안전하게 구조화하고 검산하는 시스템"이다. 따라서 OCR은 독립 제품이 아니라 보험금 계산 파이프라인 앞단의 입력 수집 수단으로 붙는 것이 맞다.

권장 구조는 다음과 같다.

```text
문서 이미지/PDF
-> 검증된 OCR 엔진 실행
-> 보험금 계산용 구조화
-> 금액/문서 간 검산
-> 사용자/심사 확인 항목 분리
-> 기존 claim_calculation pipeline
```

## 지금까지 확인한 OCR 실험

### Azure Document Intelligence

Azure `prebuilt-layout`는 현재 가장 안정적인 1차 OCR 엔진으로 확인됐다.

- 12장 문서 전체를 처리했다.
- 표 구조를 JSON으로 제공했다.
- 진료비 계산서/영수증의 주요 금액과 표 구조를 반복 가능하게 추출했다.
- 구조화 엔진 `src/mobile_ocr/claim_structuring.py`를 통해 보험금 계산 후보 payload를 만들 수 있었다.
- 검증 결과 `tests/test_claim_ocr_structuring.py` 4개 테스트가 통과했다.

다만 Azure도 완전하지 않았다.

- page 11 공단부담금 합계를 `3,100,690`이 아니라 `23,100,690`으로 잘못 읽었다.
- 일부 한글 라벨이 깨졌다.
- 금액 문장 주변의 수식 번호를 금액처럼 오인할 가능성이 있었다.

따라서 Azure 결과도 바로 계산에 넣으면 안 되고, 반드시 검산 gate가 필요하다.

### PaddleOCR-VL

PaddleOCR-VL은 GPU 실행 가능성까지 확인했다.

- DGX Spark/GB10 환경에서 source build 경로로 실행했다.
- GPU OCR 자체는 성공했다.
- Markdown/JSON 산출물이 생성됐다.

하지만 보험금 계산에 바로 쓰기에는 한계가 있었다.

- 긴 의료 텍스트와 표 세부값의 안정성이 부족했다.
- 특정 금액/항목을 잘 읽는 경우도 있지만, 전체 표 구조를 계산 입력으로 신뢰하기 어렵다.
- 현재 기준에서는 Azure를 대체하기보다 의심 셀 보조 판독용으로 쓰는 것이 적합하다.

### MinerU

MinerU는 `.venv-mineru`에 설치하고 12장 전체를 실제 실행했다.

- 출력 경로: `data/images_test/mineru_ocr/full_12`
- 비교 JSON: `data/images_test/mineru_ocr/mineru_claim_field_comparison.json`
- 비교 문서: `eundeo_docs/119_MINERU_OCR_RUN_AND_CLAIM_FIELD_COMPARISON.md`
- 비교 결과: 49개 필드 중 41 pass, 1 warn, 7 fail

좋았던 점:

- Markdown, HTML table, `content_list.json`, `middle.json`, layout/span PDF를 생성한다.
- page 10 진단서는 핵심 필드가 매우 좋았다.
- page 11 영수증의 주요 금액과 비급여 금액을 많이 잡았다.

한계:

- page 12 수술확인서에서 `전십자인대`를 `전심자인대`로 오인식했다.
- page 11 공단부담금 합계를 Azure와 동일하게 `23,100,690`으로 잘못 남겼다.
- page 9 합계 페이지는 숫자 truncation과 decimal corruption이 심했다.
- page 11 진료과 `정형외과3`을 `정형의과3`으로 읽었다.

따라서 MinerU도 단독 OCR 앱의 핵심 엔진으로 쓰기보다는 Azure와 병렬 비교하는 보조 엔진으로 적합하다.

## OCR 인식 전용 앱을 만들기 어려운 이유

### 1. OCR의 문제가 "글자 인식"에서 끝나지 않는다

보험 문서는 단순 텍스트 문서가 아니다.

- 진료비 세부산정내역
- 진료비 계산서/영수증
- 진단서
- 수술확인서
- 안내문/영수증 하단 결제 정보

각 문서마다 표 구조, 합계 위치, 라벨 표현, 금액 열이 다르다. OCR 앱이 글자를 읽어도, 보험금 계산에는 다음 단계가 추가로 필요하다.

- 문서 유형 분류
- 표 행/열 복원
- 금액 정규화
- 비급여/급여/전액본인부담 분리
- 3대 비급여 후보 분류
- 진단서와 수술확인서의 진단코드 교차 확인
- 영수증 합계 검산
- 약관 세대와 자기부담금 조건 연결

즉 OCR 앱을 만든다는 것은 사실상 OCR UI가 아니라 문서 이해 및 보험금 계산 전처리 시스템을 만드는 일이다.

### 2. 엔진별 오류가 서로 다르다

Azure, PaddleOCR-VL, MinerU 모두 장점이 다르지만 오류도 다르다.

| 엔진 | 장점 | 실제 확인된 문제 |
|---|---|---|
| Azure | 표 JSON, 반복 가능성, 구조화에 가장 적합 | `23,100,690` 같은 금액 오염, 한글 라벨 오류 |
| PaddleOCR-VL | GPU 기반 시각 판독 후보, 문서 이미지 이해 가능성 | 표 전체 구조와 긴 의료 텍스트 안정성 부족 |
| MinerU | HTML table, Markdown, content list, layout/span PDF | 진단명 오인식, page 9 숫자 깨짐, Azure와 같은 합계 오류 |

단일 OCR 앱이 이 오류들을 모두 해결하려면 엔진 선택 UI가 아니라, 엔진별 결과를 비교하고 검산하는 후처리 레이어가 필요하다. 이 후처리 레이어가 실제 핵심이다.

### 3. 보험금 계산은 고위험 숫자 처리다

보험금 계산에서 숫자 하나가 틀리면 결과가 바로 달라진다.

이번 실험에서도 다음 문제가 확인됐다.

- `3,100,690`이 `23,100,690`으로 읽힘
- `75,322`와 `75,320`처럼 문서 간 2원 차이 발생
- 금액의 쉼표/마침표가 섞임
- `0`이 `O`, `A`, `∞`, 빈칸 등으로 잡힘
- 일부 금액이 `5,240,200`이 아니라 잘린 형태로 나옴

일반 OCR 앱은 "대충 읽힌 텍스트"를 보여주는 데는 충분할 수 있다. 하지만 보험금 계산 시스템은 "이 숫자를 계산에 사용해도 되는가"를 판단해야 한다. 그래서 OCR 앱보다 검산 가능한 구조화 엔진이 더 중요하다.

### 4. 별도 앱을 만들면 민감정보/보안 범위가 커진다

보험 청구 문서에는 민감정보가 포함된다.

- 환자 정보
- 진단명
- 진단코드
- 수술명
- 진료기간
- 병원명
- 결제 정보 일부

별도 OCR 앱을 만들면 파일 업로드, 저장, 열람, 삭제, 권한, 로그 마스킹, 감사 추적까지 모두 새로 설계해야 한다. 현재 프로젝트 안에서 OCR을 backend pipeline으로 처리하면 기존 인증, 세션, 감사 로그, 데이터 저장 정책에 붙일 수 있다.

### 5. 운영 환경 호환성이 어렵다

이번 실험에서 환경 문제도 반복적으로 확인됐다.

- Docker 권한이 세션마다 달랐다.
- PaddleOCR-VL Docker 이미지는 `linux/amd64`라 `linux/arm64` 호스트에서 `exec format error`가 발생했다.
- PaddlePaddle GPU는 GB10/Blackwell 환경에 맞춰 별도 source build가 필요했다.
- MinerU는 설치 가능했지만 `.venv-mineru`만 약 8.3GB였다.
- MinerU의 Torch 환경에서는 `cuda_available=False`가 나와 pipeline backend로 실행했다.

별도 OCR 앱을 만들면 이 환경 의존성을 앱 배포 문제로 다시 떠안게 된다. 반면 현재 방식처럼 backend 실험/배치 파이프라인으로 붙이면 엔진별 환경을 분리해서 관리할 수 있다.

## 이 프로젝트에서 OCR 앱이 불필요한 이유

### 1. 이미 필요한 기능은 backend pipeline으로 구현 가능하다

현재 이미 다음 흐름이 가능하다.

```text
Azure OCR 산출물
-> claim_structuring.py
-> claim_ocr_structured.json
-> 검산 결과
-> 보험금 계산 후보 payload
```

구조화 결과는 다음 필드를 생성한다.

- `ClaimCaseContext` 후보
- `ClaimItemInput` 후보 목록
- 영수증 합계
- 비급여 항목별 금액
- 진단코드/진단명
- 수술명/수술일자
- 검증 결과
- 추가 사용자 입력 필요 항목

즉 OCR 앱 화면 없이도 보험금 계산에 필요한 중간 산출물을 만들 수 있다.

### 2. 사용자가 원하는 것은 OCR 결과가 아니라 보험금 계산 가능 여부다

사용자에게 중요한 질문은 "문자가 잘 읽혔는가"가 아니다.

실제로 필요한 질문은 다음이다.

- 이 문서가 입원 청구 건인가?
- 어떤 진단코드인가?
- 어떤 수술을 했는가?
- 비급여 총액이 얼마인가?
- MRI, 주사료, 병실료 차액 등 보장 판단에 중요한 항목이 있는가?
- 합계가 맞는가?
- 약관상 계산에 필요한 정보가 빠져 있는가?

따라서 별도 OCR 앱을 만들기보다, 기존 챗봇/보험금 계산 화면에서 "문서 업로드 후 계산 후보와 검토 필요 항목을 보여주는 기능"으로 붙이는 것이 맞다.

### 3. OCR 결과는 단독으로 신뢰할 수 없고 반드시 계산 검산과 결합돼야 한다

OCR 앱은 보통 텍스트와 표를 보여준다. 하지만 이 프로젝트에서는 다음 검산이 더 중요하다.

- 비급여 항목 합계 = 비급여 총액
- 급여 본인부담 + 전액본인부담 + 비급여 = 환자부담 총액
- 이미 납부한 금액 + 납부할 금액 = 환자부담 총액
- 진단서와 수술확인서의 진단코드 일치
- 수술일자와 진료기간의 관계 확인
- 3대 비급여 후보 분리

이 검산은 OCR 앱이 아니라 보험금 계산 파이프라인의 책임이다.

### 4. 여러 OCR 엔진은 UI 기능이 아니라 검증 source로 쓰는 것이 효율적이다

별도 앱을 만들면 "Azure 결과 보기", "MinerU 결과 보기", "Paddle 결과 보기" 같은 화면이 늘어난다. 하지만 실무적으로 더 유용한 것은 다음이다.

```text
Azure 값: 5,240,200
MinerU 값: 5,240,200
PaddleOCR-VL 값: 불명확
검산 결과: pass
계산 사용 여부: 사용 가능
```

또는:

```text
Azure 값: 23,100,690
MinerU 값: 23,100,690
Codex/시각 기준: 3,100,690
검산 결과: warn
계산 사용 여부: 직접 사용 금지
```

사용자에게 필요한 것은 OCR 원문 뷰어가 아니라 "이 값을 계산에 써도 되는지"에 대한 판정이다.

### 5. OCR 앱보다 review gate가 더 가치 있다

현재 구조화 결과는 `candidate_ready_with_review` 상태다. 이 상태를 개선하려면 OCR 앱을 만드는 것보다 다음을 개발하는 것이 효과적이다.

- 약관 세대 입력
- 사고/상해/질병 구분 입력
- 자기부담금/한도 입력
- 3대 비급여 확정 질문
- OCR 이상치만 보여주는 review UI
- 검산 통과 항목과 검토 필요 항목 분리

즉 다음 개발 목표는 "OCR 앱"이 아니라 "청구 계산 review panel"이다.

## 권장 개발 방향

### 만들지 않는 것

- 독립 실행형 OCR 인식 앱
- OCR 엔진 선택 전용 UI
- OCR 원문 전체를 사람이 직접 비교하는 화면
- OCR 결과를 그대로 보험금 계산에 넣는 기능

### 만들어야 하는 것

- 기존 보험금 계산 흐름 안의 문서 업로드 기능
- OCR 실행 job 관리
- OCR 결과 구조화 adapter
- `claim_structuring.py` 검산 gate 강화
- 계산 사용 가능/검토 필요/사용 금지 필드 분리
- 검토 필요 항목만 보여주는 review UI
- Azure, MinerU, PaddleOCR-VL 결과를 비교하는 내부 evidence table

권장 구조:

```text
문서 업로드
-> Azure OCR 실행
-> 필요 시 MinerU/PaddleOCR-VL 병렬 실행
-> claim_structuring.py
-> field-level validation
-> review panel
-> claim_calculation pipeline
```

## 최종 정리

OCR 인식 전용 앱을 만들기 어려운 이유는 OCR 자체가 어려워서만은 아니다. 보험금 계산에 필요한 것은 글자 인식이 아니라, 인식된 값을 계산에 사용할 수 있는지 검증하는 일이다.

이번 실험에서 Azure, PaddleOCR-VL, MinerU 모두 쓸모는 있었지만, 어느 엔진도 단독으로 보험금 계산 입력을 완전히 보장하지 못했다. 따라서 이 프로젝트에서는 별도 OCR 앱을 만드는 것보다, 현재 백엔드 안에 OCR을 흡수하고 구조화/검산/review gate를 강화하는 것이 더 안전하고 효율적이다.

한 줄 결론:

```text
OCR 앱은 불필요하고, OCR 기반 보험금 계산 검증 파이프라인은 필요하다.
```
