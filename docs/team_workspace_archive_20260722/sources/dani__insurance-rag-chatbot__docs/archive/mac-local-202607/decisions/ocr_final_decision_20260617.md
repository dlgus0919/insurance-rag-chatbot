# 보험 챗봇 프로젝트 OCR 적용 보류 판단 보고서

작성일: 2026-06-17

## 1. 결론

현재 개발 중인 보험 챗봇 프로젝트에는 OCR 기능을 정식 범위로 포함하지 않는 것이 타당하다.

이 결론은 OCR 기술 자체가 불필요하다는 뜻이 아니다. 보험금 계산 업무에서 OCR은 장기적으로 유용한 입력 수단이 될 수 있다. 다만 현재 실험 결과 기준으로는 OCR 산출물을 사람의 검수 없이 보험금 계산 로직에 연결할 만큼 안정적이지 않다. 특히 보험금 계산은 숫자, 진료 코드, 항목별 금액 배치가 하나만 틀려도 결과가 달라지는 고위험 처리이므로, “대체로 읽힘” 수준의 OCR을 제품 기능으로 포함하기 어렵다.

따라서 이번 단계의 권장 결정은 다음과 같다.

| 항목 | 판단 |
|---|---|
| DGX Spark 기반 온디바이스 OCR | 현재 프로젝트 적용 불가 |
| 외부 OCR API 기반 독립 OCR 앱 | 별도 앱 개발 불필요 |
| 현재 챗봇/보험금 계산 기능 | OCR 없이 안정화 우선 |
| OCR의 향후 활용 | 검수 보조 또는 내부 실험 기능으로 제한 |

한 줄로 정리하면, **지금 필요한 것은 OCR 앱이 아니라 신뢰 가능한 보험금 계산 시스템이며, 현재 OCR은 그 계산 시스템의 자동 입력으로 사용할 수 없다.**

## 2. 검토 배경

보험 청구 문서에는 진단서, 수술확인서, 진료비 계산서/영수증, 진료비 세부산정내역서 등이 포함된다. 이 문서들을 OCR로 읽어 자동으로 보험금 계산에 연결할 수 있다면 사용자 편의성이 높아진다.

다만 보험 문서 OCR은 일반 문서 OCR과 다르다. 단순히 글자를 읽는 것만으로는 충분하지 않고, 다음 조건을 모두 만족해야 한다.

- 문서 종류를 정확히 분류해야 한다.
- 표의 행과 열 구조를 보존해야 한다.
- 진료 코드, 단가, 횟수, 일수, 총액, 본인부담금, 공단부담금, 비급여 금액이 올바른 열에 들어가야 한다.
- 진단명, 질병분류기호, 수술명, 수술일자를 문서 간 교차 검증해야 한다.
- 합계 금액과 세부 금액의 산식이 맞아야 한다.
- 검증 실패 시 자동 계산을 중단해야 한다.

즉 이 프로젝트에서 필요한 것은 “OCR 텍스트 추출”이 아니라 “계산에 사용 가능한 구조화 데이터 생성”이다. 이 기준으로 보면 현재 OCR 결과는 아직 정식 적용 기준을 충족하지 못한다.

## 3. 시도한 두 가지 접근

### 3.1 DGX Spark 온디바이스 OCR

첫 번째 접근은 고객의 민감 정보를 외부로 내보내지 않기 위해 DGX Spark 서버에서 모든 OCR을 로컬로 처리하는 방식이었다. 이 방향은 보안 관점에서 가장 바람직하다. 고객 문서에는 환자 정보, 진단명, 질병분류기호, 수술명, 진료기간, 병원명, 결제 정보 등이 포함되므로 외부 API 전송을 피할 수 있다면 가장 안전하다.

그러나 실제 실험 결과, 현재 온디바이스 OCR은 보험금 계산에 바로 연결하기 어렵다.

Gemma 4 31B OCR 실험에서는 문서 종류, 표 행 개수, 날짜, 주요 합계 금액, 진단명과 질병분류기호는 비교적 잘 읽었다. 하지만 보험금 계산에 직접 필요한 세부 항목에서는 다음 문제가 확인됐다.

| 평가 항목 | 결과 |
|---|---|
| 문서 종류 판별 | 12장 모두 올바르게 분류 |
| 세부내역 행 검출 | 158 / 158행 |
| 세부내역 행별 총액 | 153 / 158행 일치, 약 96.8% |
| 세부내역 코드 완전 일치 | 94 / 155행, 약 60.6% |
| 영수증 최종 결제 요약 | 주요 합계 금액 정확 |
| 영수증 항목별 금액 배치 | 여러 행과 열에서 이동 발생 |

특히 진료 코드 완전 일치율이 약 60.6%에 그친 점은 치명적이다. 보험금 계산에서는 진료 코드와 항목명이 보장 판단의 근거가 될 수 있는데, 코드가 일부 누락되거나 다른 숫자로 인식되면 계산 결과가 달라질 수 있다.

대표 오류는 다음과 같다.

- 한 셀 안에서 두 줄로 인쇄된 진료 코드의 뒷자리가 누락됨
- `J2000` 항목에서 횟수, 일수, 총액, 본인부담금, 공단부담금이 한 칸씩 밀림
- `120,000`이 `120,00`으로 인식됨
- `201,000`이 `200,100`으로 인식됨
- `12,520`이 `12,502`로 인식됨
- 영수증의 MRI 비급여 금액이 다른 행에 배치됨
- 주사료 비급여 `1,432,000`이 `1,432`처럼 천 단위가 누락됨

이 오류들은 단순 오탈자가 아니라 계산값을 바꾸는 오류다. 따라서 현재 온디바이스 OCR 결과는 “검수 보조 자료”로는 의미가 있지만, 보험금 자동 계산 입력으로 사용할 수 없다.

또한 DGX Spark 환경에서 로컬 OCR 엔진을 운영하는 과정도 안정적이지 않았다. PaddleOCR-VL, MinerU 등 로컬 OCR 후보는 GPU 실행 가능성이나 산출물 생성 가능성은 확인했지만, 의료 문서의 긴 텍스트와 복잡한 표를 일관되게 구조화하는 데 한계가 있었다. 일부 도구는 설치 용량, Docker/ARM64 호환성, CUDA/Blackwell 환경 호환성, Torch GPU 사용 여부 등 운영 환경 이슈도 있었다.

결론적으로 온디바이스 OCR은 보안 방향은 맞지만, 현재 품질과 운영 안정성 기준으로는 제품 기능에 포함하기 어렵다.

### 3.2 OCR 전용 앱

두 번째 접근은 외부 OCR API를 사용하더라도 우선 인식률을 확보하기 위해 OCR 전용 앱을 만드는 방식이었다. Azure Document Intelligence, Naver CLOVA OCR, Vision LLM 보정 등 외부 API 기반 방식은 일부 영역에서 로컬 OCR보다 안정적인 결과를 보였다.

그러나 별도의 OCR 앱을 만드는 것은 현재 프로젝트 목적에 비해 비용과 위험이 크다.

이 프로젝트의 목표는 “문서를 글자로 읽는 앱”이 아니라 “보험금 계산에 필요한 근거를 안전하게 구조화하고 검산하는 챗봇/계산 시스템”이다. OCR 앱이 텍스트와 표를 보여주더라도, 실제 보험금 계산에는 다음 후처리가 다시 필요하다.

- 문서 유형 분류
- 표 행/열 복원
- 금액 정규화
- 비급여/급여/전액본인부담 분리
- 3대 비급여 후보 분류
- 진단서와 수술확인서의 진단코드 교차 확인
- 영수증 합계 검산
- 약관 세대와 자기부담금 조건 연결

즉 OCR 앱을 만든다는 것은 별도 UI를 하나 더 만드는 문제가 아니라, 보험 문서 이해와 계산 검산 시스템을 중복으로 만드는 일에 가깝다.

또한 별도 앱은 민감정보 관리 범위를 넓힌다. 파일 업로드, 저장, 열람, 삭제, 권한, 로그 마스킹, 감사 추적, 외부 API 전송 동의, 장애 시 문서 잔존 여부까지 새로 설계해야 한다. 현재 프로젝트 안에서조차 OCR 결과를 계산에 바로 넣기 어려운데, 별도 앱을 만들면 보안과 운영 책임만 커진다.

따라서 외부 OCR API를 쓰는 전용 앱은 “OCR 인식률 확인용 실험 도구”로는 가능하지만, 이 프로젝트의 본 기능으로 만들 필요는 낮다.

## 4. OCR을 현재 프로젝트에 포함하기 어려운 핵심 이유

### 4.1 보험금 계산은 OCR 허용오차가 매우 낮다

일반 OCR은 사람이 읽기 편한 초안을 만드는 수준이면 가치가 있다. 하지만 보험금 계산에서는 숫자 하나, 행 하나, 코드 하나가 틀리면 계산 결과가 바뀐다.

이번 실험에서 확인된 오류는 대부분 계산 리스크와 직접 연결된다.

| 오류 유형 | 영향 |
|---|---|
| 금액 자리수 누락 | 청구 금액 과소/과대 계산 |
| 숫자 순서 바뀜 | 세부 항목 합계 불일치 |
| 행/열 밀림 | 다른 진료 항목에 금액 배정 |
| 진료 코드 뒷자리 누락 | 보장 판단 근거 오류 |
| 진단 구분 오인식 | 지급 심사 판단 오류 |
| 의료기관명/주소 환각 | 문서 신뢰도 저하 |

OCR 결과를 사람이 검토한다면 보조 도구로 쓸 수 있다. 그러나 현재 프로젝트에 기능으로 포함한다면 사용자는 OCR 결과가 계산에 반영된다고 기대하게 된다. 이 기대를 충족할 품질은 아직 확인되지 않았다.

### 4.2 엔진별 장점은 있으나 단독 신뢰 가능한 엔진은 없다

실험 결과 각 엔진은 장점이 있었지만, 어느 하나도 보험금 계산 자동 입력을 보장하지 못했다.

| 엔진/방식 | 장점 | 한계 |
|---|---|---|
| Gemma 4 31B | 문서 종류, 핵심 진단/수술 정보, 주요 합계 인식 양호 | 진료 코드 완전 일치율 낮음, 영수증 항목별 행/열 이동 |
| PaddleOCR-VL | 로컬 GPU 기반 OCR 가능성 | 긴 의료 텍스트와 표 세부값 안정성 부족 |
| MinerU | Markdown/HTML table 등 다양한 산출물 생성 | 일부 진단명 오인식, 숫자 truncation, 합계 오류 |
| Azure Document Intelligence | 표 JSON과 반복 가능성 | 금액 오염, 한글 라벨 오류 가능 |
| CLOVA OCR/Hybrid | 한국어와 표 구조에 강점 | 외부 API 의존, 비용/지연/민감정보 전송 이슈 |

결국 필요한 것은 단일 OCR 앱이나 단일 OCR 엔진이 아니라, 여러 OCR 결과를 비교하고 검산하는 후처리 레이어다. 하지만 그 후처리 레이어를 만들려면 별도의 제품 수준 개발과 검증 기간이 필요하다.

### 4.3 온디바이스 OCR은 보안상 바람직하지만 현재 운영 가능성이 낮다

온디바이스 방식은 고객 민감정보를 외부로 내보내지 않는다는 점에서 이상적이다. 그러나 현재 결과 기준으로는 다음 한계가 있다.

- 정확도가 보험금 계산 자동화 기준에 미달한다.
- 복잡한 의료 표에서 행/열 구조가 흔들린다.
- 설치와 실행 환경이 DGX Spark의 ARM64, Blackwell, CUDA, Docker 권한 조건에 민감하다.
- 모델과 OCR 도구별 런타임을 안정적으로 유지해야 한다.
- 추론 시간이 길거나 자원 점유가 커질 수 있다.
- 오류가 발생했을 때 일반적인 OCR 실패가 아니라 잘못된 보험금 계산으로 이어질 수 있다.

따라서 “보안 때문에 로컬 OCR을 해야 한다”는 방향은 맞지만, “현재 로컬 OCR을 제품에 넣을 수 있다”는 결론으로 이어지지는 않는다.

### 4.4 외부 OCR API는 인식률을 높일 수 있지만 프로젝트 요구와 충돌한다

외부 OCR API는 품질 측면에서 일부 장점이 있다. 그러나 고객의 민감 문서를 외부로 전송해야 하므로 보안, 동의, 계약, 로그, 보관 기간, 장애 대응 정책이 필요하다.

또한 외부 API를 써도 결과를 그대로 계산에 넣을 수 없다. 실제 실험에서 안정적인 API OCR도 금액 오염, 라벨 오류, 표 구조 오류 가능성이 있었고, 검산 gate가 필요했다.

즉 외부 API는 “OCR 정확도” 문제를 일부 줄일 수는 있지만, “보험금 계산에 사용 가능한 검증 데이터인가” 문제를 해결하지 못한다.

### 4.5 별도 OCR 앱은 문제를 해결하지 않고 책임 범위만 늘린다

별도 앱을 만들면 사용자에게 OCR 결과를 보여줄 수는 있다. 그러나 현재 프로젝트에서 필요한 핵심은 OCR 결과 화면이 아니라 다음 판정이다.

- 이 값은 계산에 사용 가능한가?
- 이 값은 검토가 필요한가?
- 이 값은 사용하면 안 되는가?
- 어떤 문서와 어떤 산식으로 검증됐는가?

이 판정은 OCR 앱의 책임이 아니라 보험금 계산 파이프라인의 책임이다. 별도 OCR 앱은 UI와 운영 범위를 늘리지만, 계산 검증 문제를 해결하지 못한다.

## 5. 현재 적용할 경우 예상 리스크

현재 OCR을 프로젝트에 포함하면 다음 리스크가 발생한다.

| 리스크 | 설명 |
|---|---|
| 잘못된 보험금 계산 | OCR 숫자 오류가 계산 결과에 직접 반영될 수 있음 |
| 사용자 신뢰 하락 | OCR이 읽은 값을 시스템 계산값으로 오해할 수 있음 |
| 민감정보 처리 부담 증가 | 이미지/PDF 업로드, 저장, 외부 전송, 로그 관리 범위 확대 |
| 운영 장애 가능성 증가 | OCR 모델/API/환경 이슈가 챗봇 안정성에 영향 |
| 검수 책임 불명확 | 사람이 확인해야 하는 값과 자동 사용 가능한 값의 경계가 불명확 |
| 개발 범위 확대 | OCR, 구조화, 검산, review UI까지 신규 개발 필요 |

특히 현재 챗봇의 본질은 약관/근거 기반 답변과 보험금 계산 로직의 신뢰성이다. OCR을 무리하게 포함하면 핵심 기능의 안정화보다 불확실성이 큰 입력 채널에 개발 역량이 분산된다.

## 6. 권장 의사결정

### 6.1 이번 단계에서 하지 않을 것

- OCR 자동계산 기능을 정식 릴리즈 범위에 포함하지 않는다.
- DGX Spark 온디바이스 OCR을 운영 기능으로 붙이지 않는다.
- 외부 OCR API 기반 독립 OCR 앱을 새로 만들지 않는다.
- OCR 결과를 검산 없이 보험금 계산에 넣지 않는다.
- OCR 원문 전체를 사용자가 직접 비교하는 별도 화면을 만들지 않는다.

### 6.2 이번 단계에서 할 것

- 현재 챗봇과 보험금 계산 로직의 안정화에 집중한다.
- OCR은 “향후 후보 기능” 또는 “내부 검수 보조 실험”으로 남긴다.
- OCR 관련 실험 결과는 향후 재검토 근거로 보관한다.
- 문서 업로드 기능이 필요하다면 OCR 자동계산이 아니라 “사용자 입력 보조” 수준으로 범위를 제한한다.

### 6.3 향후 재검토 조건

OCR 적용은 다음 조건을 충족할 때 다시 검토하는 것이 합리적이다.

| 재검토 조건 | 기준 |
|---|---|
| 진료 코드 인식 | 계산에 필요한 코드 완전 일치율이 운영 기준에 도달 |
| 금액 인식 | 항목별 금액, 합계, 산식 검증 통과율 확보 |
| 표 구조 | 행/열 이동 없이 계산 항목 매핑 가능 |
| 문서 간 검증 | 진단서, 수술확인서, 영수증, 세부내역서 간 핵심 값 교차 검증 가능 |
| 보안 정책 | 외부 API 사용 여부, 저장/삭제/로그 정책 확정 |
| 검수 UI | 자동 사용/검토 필요/사용 금지 필드 분리 가능 |
| 테스트셋 | 다양한 병원 양식과 스캔 품질을 포함한 검증 데이터 확보 |

이 조건이 충족되기 전까지 OCR은 제품 기능이 아니라 연구 과제로 관리하는 것이 안전하다.

## 7. 상급자 보고용 요약

OCR은 보험 챗봇의 장기 기능으로는 가치가 있지만, 현재 프로젝트에 포함하기에는 품질과 운영 리스크가 크다. DGX Spark 기반 온디바이스 OCR은 고객 민감정보를 외부로 보내지 않는다는 점에서 가장 바람직한 방향이지만, 실제 실험에서는 진료 코드 누락, 금액 자리수 오류, 영수증 항목별 행/열 이동 등 보험금 계산에 직접 영향을 주는 오류가 확인됐다. Gemma 4 31B 실험에서도 문서 분류와 주요 합계는 양호했으나, 진료 코드 완전 일치율이 약 60.6%에 그쳐 자동 계산 입력으로 사용하기 어렵다.

외부 OCR API를 활용한 별도 OCR 앱도 대안으로 검토했지만, 별도 앱은 문제를 해결하지 않는다. 보험금 계산에 필요한 것은 OCR 결과를 보여주는 화면이 아니라, 인식된 값이 계산에 사용 가능한지 검증하는 구조화/검산 파이프라인이다. 별도 앱을 만들면 민감정보 처리 범위, 업로드/저장/삭제, 권한, 로그 마스킹, 외부 전송 동의 등 운영 책임이 커진다. 하지만 OCR 결과를 계산에 안전하게 반영해야 하는 핵심 문제는 여전히 남는다.

따라서 현재 단계에서는 OCR을 정식 기능에 포함하지 않고, 기존 챗봇과 보험금 계산 로직의 안정화에 집중하는 것이 합리적이다. OCR은 향후 충분한 테스트셋, 검산 gate, review UI, 보안 정책이 갖춰진 뒤 재검토하는 것이 안전하다.

## 8. 최종 문장

현재 OCR은 “읽을 수 있는 수준”까지는 접근했지만, “보험금 계산에 자동 반영해도 되는 수준”에는 도달하지 못했다. 온디바이스 OCR은 보안상 이상적이지만 현재 정확도와 운영 안정성이 부족하고, OCR 전용 앱은 계산 검증 문제를 해결하지 못한 채 민감정보 처리 범위만 넓힌다. 따라서 이번 프로젝트에서는 OCR을 포함하지 않는 것이 기술적, 보안적, 운영적으로 가장 합리적인 결정이다.
