# 보험 약관 RAG 챗봇 개발 명세서

> **문서 버전**: v1.0
> **작성일**: 2026-04-30
> **수신**: 개발자 (Codex)
> **목적**: 보험금 청구 업무 담당자가 약관 PDF를 직접 뒤지지 않고, 챗봇에게 질문하여 정확한 보상 기준·약관 조항을 즉시 확인할 수 있는 RAG 기반 챗봇을 구축한다.

---

## 1. 프로젝트 개요

### 1.1 배경
- 현재 보험금 청구 요청이 들어오면, 담당자가 약 **1,429 페이지 분량의 보험 약관 PDF**(건강보험 행위 급여·비급여 목록표 및 급여 상대가치점수, 보건복지부 고시)를 직접 검색하여 보상 가능 여부, 적용 조항, 점수/금액 등을 확인해야 한다.
- 이 과정은 시간이 많이 소요되고, 담당자별 검색 결과가 달라질 수 있어 일관성이 떨어진다.

### 1.2 목표
- PDF 약관 내용을 학습한 챗봇을 통해, 자연어 질문에 대해 약관에 근거한 정확한 답변을 제공한다.
- **모든 답변에는 반드시 출처(조항 번호 + 페이지)가 함께 표시되어야 한다.**
- 보험금 청구 담당자가 데모 화면에서 즉시 사용할 수 있는 형태로 1차 완성한다.

### 1.3 비목표 (Non-Goals)
- 보험금 자동 산정/지급 시스템은 본 프로젝트 범위에 포함되지 않는다.
- 외부(고객) 노출용 서비스가 아니다. **사내 담당자용 의사결정 보조 도구**다.
- 학습용 fine-tuning은 하지 않는다 (RAG로만 구현).

## 2. 기술 스택

| 영역 | 선택 기술 | 비고 |
|---|---|---|
| 언어 | Python 3.11+ | |
| UI | **Streamlit** | 빠른 프로토타이핑, 사내 데모용. Gradio도 무방하나 본 명세는 Streamlit 기준으로 작성. |
| LLM | **오픈소스 로컬 LLM** | 1순위: `Qwen2.5-14B-Instruct` (한국어 우수), 2순위: `Llama-3.1-8B-Instruct`. 추론 서버는 **vLLM** 또는 **Ollama** 사용. |
| 임베딩 모델 | `BAAI/bge-m3` (다국어, 한국어 성능 검증됨) 또는 `intfloat/multilingual-e5-large` | 한국어 보험/의료 도메인 용어를 잘 처리해야 함. |
| 벡터 DB | **ChromaDB** (로컬 영속화) | 1차 데모는 Chroma. 데이터가 커지면 FAISS+메타데이터 분리 구조로 마이그레이션. |
| PDF 파싱 | `pdfplumber` (테이블 추출) + `PyMuPDF (fitz)` (텍스트/페이지 메타) | 본 약관은 표가 다수 포함되어 있어 표 보존이 중요. |
| 오케스트레이션 | LangChain 또는 LlamaIndex | 1순위: **LlamaIndex** (RAG 특화, 한국어 예제 풍부). |
| 패키지 관리 | `uv` 또는 `poetry` | `uv` 권장 (속도). |

> **하드웨어 가정**: GPU VRAM 24GB 이상 (예: RTX 4090, A6000). VRAM 부족 시 8B 모델 + 4bit 양자화로 fallback.

## 3. 입력 자료

- **파일명**: `BZ202603053039374.pdf`
- **분량**: 1,429 페이지
- **내용 유형**:
  - 보건복지부 고시 본문
  - 부칙 (시행일자별)
  - 행위 급여/비급여 목록표 (표 형태, 분류번호·코드·분류·점수)
  - 산정지침 (텍스트)
- **언어**: 한국어 (전문용어 다수)
- **구조 특징**:
  - `제N편 / 제N부 / 제N장 / 제N절` 형태의 다단계 섹션 구조
  - `가-25`, `AU941` 같은 분류번호·코드 체계
  - 페이지 하단 페이지 번호 존재

## 6. 인덱싱 파이프라인 상세

### 6.1 PDF 파싱 (`src/ingest/pdf_parser.py`)
- **PyMuPDF**로 페이지별 텍스트 추출 (페이지 번호 메타데이터 보존).
- **pdfplumber**로 표(table) 영역 별도 추출 → 마크다운 형식 문자열로 변환.
- 본 PDF는 페이지 헤더에 `제1편 행위 급여·비급여 목록 및 급여 상대가치점수` 등 섹션명이 반복되므로, 헤더/푸터 노이즈 제거 로직 필요.
- 출력 형식 (페이지 단위 dict 리스트):
  ```python
  {
      "page": 117,
      "section_path": ["제1편", "제2부", "제1장 기본진료료", "제1절 기본진료료"],
      "text": "...",
      "tables_md": ["| 분류번호 | 코드 | 분류 | 점수 |\n|...|"]
  }
  ```

### 6.2 섹션 구조 추출
- 정규식으로 `제(\d+)편`, `제(\d+)부`, `제(\d+)장`, `제(\d+)절`, `제(\d+)조` 패턴을 인식하여 섹션 트리 빌드.
- 각 페이지가 어느 섹션에 속하는지 매핑.
- 분류번호 패턴 `가-\d+`, `나-\d+` 등도 추출하여 메타데이터에 포함.

### 6.3 청킹 (`src/ingest/chunker.py`)
- **전략**: 조항(또는 분류번호) 단위 우선 청킹 + 길이 초과 시 슬라이딩 윈도우.
- 청크 크기 기준값: **500~800 토큰**, 오버랩 **80 토큰**.
- 표는 가능한 한 분할하지 않는다. 표가 한 청크에 들어가지 않으면, 표 머리(헤더 행)를 모든 분할 청크에 복제한다.
- 각 청크는 다음 메타데이터를 가진다:
  ```python
  {
      "chunk_id": "p0117_c02",
      "page_start": 117,
      "page_end": 117,
      "section_path": "제1편 > 제2부 > 제1장 > 제1절",
      "clause_codes": ["가-25", "가-26"],
      "doc_title": "건강보험 행위 급여·비급여 목록표 및 급여 상대가치점수",
      "source_file": "BZ202603053039374.pdf"
  }
  ```

### 6.4 임베딩 + 적재 (`src/ingest/build_index.py`)
- 임베딩 모델: `BAAI/bge-m3` (HuggingFace `sentence-transformers`로 로딩).
- 배치 크기: 32 (GPU 사용).
- Chroma `PersistentClient`로 `chroma_db/`에 저장. 컬렉션명: `insurance_terms_v1`.
- 1회 실행 후 결과 캐시 (`data/processed/chunks.jsonl`)하여 재실행 시 임베딩만 다시 수행 가능.
- 실행 명령:
  ```bash
  python scripts/01_ingest.py --pdf data/raw/BZ202603053039374.pdf --rebuild
  ```

## 7. 검색·생성 파이프라인 상세

### 7.1 검색기 (`src/retrieval/retriever.py`)
1. 사용자 질문을 임베딩 → 벡터 검색 top-20.
2. (선택) `BAAI/bge-reranker-v2-m3` cross-encoder로 재정렬 후 top-5 선택.
3. 동일 페이지/조항이 중복되는 경우 dedup.
4. 반환: 청크 텍스트 + 메타데이터 리스트.

### 7.2 프롬프트 (`src/retrieval/prompts.py`)
시스템 프롬프트 (한국어):
```
당신은 보험금 청구 담당자를 돕는 보험 약관 전문 어시스턴트입니다.
아래 [참고 자료]에 포함된 내용만을 근거로 답변하십시오.
[참고 자료]에 없는 내용은 절대 추측하지 말고 "약관에서 해당 내용을 찾을 수 없습니다."라고 답하십시오.

답변 규칙:
1. 한국어로 답변합니다.
2. 답변 마지막에 반드시 [출처] 섹션을 만들고, 사용한 근거의 (조항 번호, 페이지)를 모두 나열합니다.
3. 표/숫자(점수, 코드)는 원문 그대로 인용합니다. 임의로 반올림하거나 변형하지 않습니다.
4. 질문이 모호하면 사용자에게 되묻습니다.
```

유저 프롬프트 템플릿:
```
[참고 자료]
{context}

[질문]
{question}

[답변]
```

`{context}`는 청크별로 다음 형태로 직렬화:
```
--- 자료 1 ---
[섹션] 제1편 > 제2부 > 제1장 > 제1절
[조항] 가-25
[페이지] 117
{청크 텍스트}
```

### 7.3 LLM 호출 (`src/llm/client.py`)
- vLLM OpenAI 호환 API 또는 Ollama 사용.
- temperature: **0.1** (사실 기반 답변 우선).
- max_tokens: 1024.
- 스트리밍 응답 지원 (Streamlit `st.write_stream`과 연동).

### 7.4 RAG 엔진 (`src/chat/engine.py`)
- 입력: 질문 (str), 대화 히스토리 (list).
- 처리: 질문 재구성(history-aware) → 검색 → 프롬프트 구성 → LLM 호출.
- 출력:
  ```python
  {
      "answer": "...",
      "sources": [
          {"clause": "가-25", "page": 117, "section": "..."},
          ...
      ],
      "raw_chunks": [...]   # UI에서 펼쳐 볼 수 있도록
  }
  ```

## 8. UI 요구사항 (`src/app.py`, Streamlit)

### 8.1 화면 구성
- **상단**: 제목 "보험 약관 챗봇 (사내용)" + 현재 인덱스된 문서 정보 (파일명, 페이지 수, 마지막 인덱싱 시각).
- **사이드바**:
  - top-k 슬라이더 (기본 5)
  - 모델 선택 드롭다운 (Qwen2.5-14B / Llama-3.1-8B)
  - "대화 초기화" 버튼
- **본문**: 채팅 인터페이스 (`st.chat_message`).
  - 사용자 메시지: 우측, 회색.
  - 봇 메시지: 좌측, 답변 + **출처 카드**(각 카드 클릭 시 원문 청크 펼쳐짐).
- **하단**: 입력창 + 전송 버튼.

### 8.2 출처 표시 형식
답변 아래에 다음 형식으로 카드 표시:
```
📌 출처
  · [가-25] 감염예방·관리료  (p.117)  [원문 보기]
  · [가-26] 야간진료관리료    (p.118)  [원문 보기]
```
"원문 보기" 클릭 시 `st.expander`로 해당 청크 텍스트 표시.

### 8.3 예외/에러 UX
- 검색 결과가 비어있거나 유사도 임계치(예: cosine < 0.3) 미만일 때:
  → "약관에서 관련 내용을 찾지 못했습니다. 질문을 좀 더 구체적으로 해 주세요."
- LLM 서버 연결 실패: 빨간 배너로 안내.

- `test_retriever.py`: 더미 벡터DB에 청크 적재 후, 질문 → 예상 청크가 top-k에 포함되는지.

### 11.2 평가 셋 (`tests/eval_questions.yaml`)
실제 보험금 청구 담당자가 사용할 법한 질문 **20문항** 작성 (예시):
- "감염예방·관리료 1등급 점수가 얼마인가?"
- "야간전담간호사 운영비율 20% 이상 25% 미만일 때 상급종합병원의 점수는?"
- "뇌사장기기증자 관리료에 포함되는 비용 항목은?"
- "한방병원 가등급 입원 기본진료료 점수는?"

각 항목의 정답(조항코드, 페이지, 핵심 숫자)을 명시하고, 자동 평가 스크립트로:
- **답변 정확도**: 정답 숫자/코드가 답변에 포함되는지 (string match).
- **출처 정확도**: 정답 페이지가 출처 목록에 포함되는지.
- **거절 정확도**: 약관에 없는 질문 5개를 섞고, 챗봇이 "찾을 수 없다"고 답하는지.

### 11.3 수용 기준 (Acceptance Criteria)
- [ ] 평가셋 20문항 중 **17문항 이상** 답변 정확.
- [ ] 모든 답변에 출처(조항+페이지)가 포함된다.
- [ ] 약관 외 질문 5문항 모두 거절 답변.
- [ ] 한 질문 평균 응답시간 **15초 이하** (top-k=5, 14B 모델 기준).
- [ ] 인덱싱 스크립트가 1회 실행으로 오류 없이 완료된다.

1. 위 디렉터리 구조대로 **새 레포지토리**를 생성한다.
2. `pyproject.toml`에 §9.2 의존성을 추가하고 `uv sync`로 환경 구성.
3. **§6 인덱싱 파이프라인**부터 구현한다. 청크 메타데이터의 정확도가 시스템 품질을 좌우하므로, 작은 페이지 범위(예: 100~120페이지)로 먼저 파싱·청킹하여 메타데이터(섹션 경로, 조항 코드, 페이지)가 잘 잡히는지 단위 테스트로 검증 후 전체 적용.
4. **§7 검색·생성 파이프라인**을 구현한다. 우선 vLLM 미실행 환경에서도 단위 테스트가 돌도록, LLM 호출부는 인터페이스로 추상화하고 mock 구현체를 둔다.
5. **§8 Streamlit UI**를 구현한다. 출처 카드와 원문 펼치기는 누락 금지.
6. **§11 평가셋 20문항**을 작성하고 자동 평가 스크립트(`scripts/03_eval.py`)를 만든다.
7. README에 §10 실행 절차를 그대로 옮겨 담당자가 따라할 수 있게 한다.
8. 각 마일스톤(M1~M5)이 끝날 때마다 **샘플 질문 3개에 대한 답변 결과를 캡처**하여 PR 설명에 첨부한다.

> **주의 사항**
> - 본 PDF는 **표가 매우 많고 숫자(점수)가 핵심 정보**다. 청크 분할로 인해 숫자가 잘리거나 표 헤더와 분리되지 않도록 각별히 주의할 것.
> - 모든 답변은 **약관 원문 기반**이어야 하며, LLM의 일반 지식 답변(hallucination)을 막는 프롬프트 가드(§7.2)를 반드시 포함할 것.
> - 페이지 번호는 **PDF 물리 페이지가 아닌 문서 인쇄 페이지 번호**(본문 하단에 인쇄된 번호)를 우선 사용한다. 둘이 다를 경우 둘 다 메타데이터에 보존한다.
