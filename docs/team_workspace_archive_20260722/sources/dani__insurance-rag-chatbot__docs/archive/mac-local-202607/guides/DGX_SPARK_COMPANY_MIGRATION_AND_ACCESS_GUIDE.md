# 보험 AI 챗봇 회사 DGX Spark 이관 및 실무자 접속 가이드

작성일: 2026-06-11
대상 시스템: NVIDIA DGX Spark 기반 보험 AI 챗봇
운영 원칙: 외부 생성형 AI API를 사용하지 않고 로컬 LLM으로 처리

## 1. 목적

현재 개인 명의 DGX Spark에서 개발한 보험 AI 챗봇을 회사 명의 DGX Spark로 이관하고, 실무자가 SSH나 개발 도구 없이 PC 또는 승인된 모바일 기기의 브라우저에서 사용할 수 있도록 하기 위한 조건과 권장 구성을 정리한다.

정식 회사 도입 시 권장하는 전체 구조는 다음과 같다.

```text
실무자 PC 또는 승인된 모바일 기기
        |
        | HTTPS
        v
https://insurance-ai.company.local
        |
        v
사내 DNS + Reverse Proxy
        |
        v
회사 명의 DGX Spark
        |
        +-- FastAPI + SPA 웹 애플리케이션
        +-- 검색 인덱스 및 GraphDB
        +-- 임베딩 및 리랭커
        +-- 로컬 LLM
        +-- 사용자 및 감사 로그 DB
```

핵심 원칙은 다음과 같다.

- 보험 문서, 사용자 질문, 검색 결과와 LLM 추론을 DGX Spark 내부에서 처리한다.
- 실무자에게 LLM 서버나 SSH를 직접 공개하지 않는다.
- 실무자는 회사 내부 HTTPS URL로 접속한다.
- 개인 Tailscale 계정은 개발과 제한된 데모에만 사용한다.
- 정식 운영에서는 회사가 승인한 내부망, VPN 또는 ZTNA를 사용한다.

## 2. 회사 DGX Spark 하드웨어 조건

### 2.1 필수 및 권장 사양

현재 개발 환경과의 호환성을 고려하면 동일한 NVIDIA DGX Spark 구성이 가장 안전하다.

| 항목          | 권장 조건                             |
| ------------- | ------------------------------------- |
| 프로세서      | NVIDIA GB10 Grace Blackwell           |
| CPU 아키텍처  | ARM64                                 |
| 메모리        | 128GB 통합 메모리                     |
| 저장장치      | 4TB NVMe 권장                         |
| 운영체제      | NVIDIA DGX OS                         |
| 사내 네트워크 | 유선 10GbE 권장                       |
| 전원          | 정품 240W 전원 어댑터                 |
| 전원 보호     | UPS 권장                              |
| 설치 장소     | 상시 전원, 냉각, 출입통제 가능한 공간 |

현재 개발 환경의 주요 데이터 규모는 대략 다음과 같다.

| 구분                   | 현재 규모 |
| ---------------------- | --------: |
| 검색 및 GraphDB 데이터 |  약 3.4GB |
| Python 가상환경        |  약 5.8GB |
| 임베딩 및 리랭커 모델  |  약 6.5GB |
| LLM 모델               |  약 383GB |

1TB 제품도 기술적으로 사용할 수 있지만 운영 모델 추가, 모델 업데이트, 인덱스 백업, 로그 및 복구 공간을 고려하면 4TB 제품을 권장한다.

### 2.2 장비 수

| 운영 단계        | 권장 구성                             |
| ---------------- | ------------------------------------- |
| 파일럿           | DGX Spark 1대                         |
| 소규모 실무 운영 | 운영 DGX 1대 + NAS 또는 암호화 백업   |
| 중요 업무 운영   | 운영 DGX 1대 + 예비 또는 개발 DGX 1대 |
| 고가용성 필요    | DGX 이중화 또는 별도 GPU 서버 인프라  |

DGX Spark 한 대로 서비스를 시작할 수 있지만, 장비 장애 시 웹앱과 LLM 서비스가 모두 중단된다. 정식 운영에서는 복구 시간 목표와 예비 장비 필요성을 별도로 결정해야 한다.

## 3. 구매 전 회사가 결정할 사항

### 3.1 설치 망

정보보호 및 IT 인프라 부서와 다음 중 설치 위치를 결정해야 한다.

1. AI 전용 내부 서버망
2. 업무 서버망
3. 개발·검증망
4. DMZ
5. 완전 폐쇄망

보험 원문이나 고객 관련 정보를 처리한다면 AI 전용 내부 서버망 또는 회사가 승인한 보호구간이 적합하다.

### 3.2 인터넷 연결 정책

초기 DGX OS 구성 및 업데이트에는 인터넷 연결이 필요할 수 있다. 분리망에서는 다음 방법 중 회사 정책에 맞는 절차를 선택한다.

1. 구축 기간에만 제한적으로 인터넷 연결을 허용한다.
2. NVIDIA 등 승인된 도메인만 방화벽에서 허용한다.
3. 최신 복구 이미지와 설치 파일을 외부에서 내려받아 보안 절차에 따라 반입한다.
4. 설치 완료 후 인터넷 아웃바운드를 차단한다.
5. 이후 모델과 패키지는 승인된 오프라인 반입 절차로 업데이트한다.

운영 중에는 외부 LLM API가 필요하지 않으므로 다음 구성이 가능하다.

```text
외부 인터넷 통신: 기본 차단
LLM 추론: DGX Spark 내부
임베딩 및 검색: DGX Spark 내부
보험 문서 및 인덱스: DGX Spark 내부
사용자 접속: 허용된 사내망에서만
```

## 4. 회사 DGX Spark 초기 설정

### 4.1 시스템 설정

- 회사 자산번호 등록 및 장비 관리자 지정
- DGX OS 및 보안 업데이트 적용
- 회사 표준 관리자 계정 생성
- 개인 계정 및 개인 이메일 계정 사용 금지
- 사내 NTP 시간 동기화 설정
- 고정 IP 또는 DHCP 예약
- 회사 표준 호스트명 설정
- Wi-Fi와 Bluetooth 비활성화 검토
- 디스크 암호화 및 Secure Boot 정책 검토
- 관리자 SSH 공개키 등록
- 비밀번호 기반 SSH 로그인 제한
- 호스트 방화벽 적용
- NVIDIA Enterprise 지원 및 유지보수 등록 검토

### 4.2 네트워크 설정 예시

```text
DGX 내부 IP: 10.20.30.50
내부 DNS: insurance-ai.company.local
사용자 서비스: HTTPS 443
관리 포트: SSH 22
애플리케이션 내부 포트: 18080
SGLang 내부 포트: 30000
vLLM 내부 포트: 30001
Ollama 내부 포트: 11434
```

권장 방화벽 정책은 다음과 같다.

| 포트  | 용도                | 접근 허용 대상                |
| ----- | ------------------- | ----------------------------- |
| 443   | 챗봇 HTTPS          | 승인된 실무자 업무망          |
| 22    | 서버 관리           | 관리자망 또는 보안 관리자     |
| 18080 | FastAPI 내부 서비스 | Reverse Proxy 또는 로컬호스트 |
| 30000 | SGLang              | DGX 내부 프로세스             |
| 30001 | vLLM                | DGX 내부 프로세스             |
| 11434 | Ollama              | DGX 내부 프로세스             |

LLM 서버 포트와 FastAPI 내부 포트를 실무자 네트워크 또는 인터넷에 직접 공개하면 안 된다.

## 5. 현재 개발 결과의 이관 조건

### 5.1 소스코드

- 회사 소유 Git 저장소를 생성한다.
- 검증된 버전을 릴리스 커밋 또는 Git 태그로 고정한다.
- 개발 브랜치를 회사 운영 기준 브랜치로 정리한다.
- 개인 Git 계정, 개인 저장소 및 개인 경로 의존성을 제거한다.
- `.env`, API 키, 사용자 DB, 보험 원문과 모델은 Git에 포함하지 않는다.

### 5.2 Python 및 실행 환경

현재 `.venv` 전체를 그대로 복사하는 방식은 권장하지 않는다. 내부 절대경로와 바이너리 의존성 때문에 새 장비에서 문제가 발생할 수 있다.

다음 중 하나를 사용해 재현 가능한 실행 환경을 만든다.

- ARM64 Docker 이미지
- 고정된 Python dependency lock 파일
- 오프라인 Python wheel 저장소

분리망 반입 패키지는 다음 항목을 포함해야 한다.

```text
Python wheel 패키지
NVIDIA 및 CUDA 호환 런타임
SGLang, vLLM 또는 Ollama
임베딩 및 리랭커 모델
운영용 LLM 모델
검색 및 GraphDB 인덱스
설치·기동·중지 스크립트
상태 점검 및 검증 스크립트
버전·라이선스·체크섬 목록
```

### 5.3 모델

- 운영에 사용할 모델을 1~2개로 우선 제한한다.
- 회사의 상업적 이용 및 내부 업무 사용 가능 여부를 확인한다.
- 모델명, 버전, 양자화 방식과 원본 출처를 기록한다.
- 암호화 저장장치 또는 승인된 사내 전송망으로 이동한다.
- 전송 전후 SHA-256 체크섬을 비교한다.
- 모델 파일을 애플리케이션 소스나 Docker 이미지와 분리된 볼륨에 저장한다.

### 5.4 보험 문서와 검색 데이터

다음 자료를 별도 자산으로 관리한다.

- 보험 원문
- OCR 결과
- 전처리 청크
- ChromaDB
- BM25 인덱스
- GraphDB
- 관계형 코드 DB
- 문서 및 코드 매핑 데이터

각 자료에 대해 회사 반입 권한, 개인정보 포함 여부, 보존기간, 접근권한과 파기 절차를 확인해야 한다.

### 5.5 비밀정보와 사용자 데이터

다음 정보는 개인 장비에서 그대로 복사하지 않고 회사 환경에서 새로 생성하는 것이 원칙이다.

- JWT 비밀키
- 관리자 계정
- 사용자 비밀번호
- 인증서 개인키
- API 키
- Tailscale 인증 키

기존 대화 및 감사 로그를 이전해야 한다면 개인정보·업무정보 검토와 승인 절차를 거친다.

## 6. 실무자 접속 방법

### 6.1 정식 운영 권장 방식

실무자는 Chrome, Edge 또는 승인된 모바일 브라우저에서 내부 URL에 접속한다.

```text
https://insurance-ai.company.local
```

사용 절차는 다음과 같다.

1. 회사 네트워크 또는 회사 VPN에 접속한다.
2. 챗봇 URL을 연다.
3. 회사 계정 또는 발급된 챗봇 계정으로 로그인한다.
4. 질문을 입력하고 답변 및 근거 문서를 확인한다.
5. 사용을 마치면 로그아웃한다.

실무자에게는 SSH, 터미널, 포트포워딩, DGX 계정이나 Tailscale 조작이 필요하지 않다.

### 6.2 PC 접속

권장 조건:

- 회사가 관리하는 업무용 PC
- 사내 업무망 또는 승인된 VPN 연결
- 회사 표준 Chrome 또는 Edge
- 내부 DNS 및 사내 인증서 신뢰 설정
- 사용자별 계정과 MFA 또는 SSO

브라우저 즐겨찾기, 사내 포털 링크 또는 바탕화면 바로가기를 배포하면 사용성이 좋아진다.

### 6.3 모바일 접속

모바일 기기는 다음 조건 중 하나를 만족해야 한다.

- 회사 업무용 Wi-Fi 연결
- 회사 VPN 연결
- 회사가 승인한 모바일 보안망
- MDM으로 관리되는 업무용 휴대폰

모바일에서도 동일한 URL을 사용한다.

```text
https://insurance-ai.company.local
```

정식 배포 전 iOS와 Android에서 다음 항목을 검증한다.

- 로그인 및 세션 유지
- 채팅 입력과 스트리밍 출력
- 긴 답변과 표의 가독성
- 출처 및 GraphDB 근거 패널
- 파일 다운로드와 내보내기
- 화면 확대 및 반응형 레이아웃

개인 휴대폰 사용은 회사의 BYOD, MDM, 개인정보 및 화면 캡처 정책 승인이 필요하다.

### 6.4 사외 접속

사외에서 사용해야 한다면 회사가 이미 승인한 다음 수단을 사용한다.

- 회사 VPN
- 회사 ZTNA
- VDI 또는 가상 데스크톱
- 보안 브라우저
- MDM 기반 모바일 업무환경

금융권 정식 운영에서는 새로운 개인 VPN이나 개인 Tailscale 환경을 도입하기보다 기존 회사 원격접속 체계를 활용하는 것이 적절하다.

## 7. Tailscale 적용 범위

### 7.1 사용할 수 있는 범위

- 개발자 원격관리
- 초기 기능 데모
- 공개 또는 비식별 데이터 기반 PoC
- 회사 정보보호 부서가 외부 ZTNA로 정식 승인한 경우

### 7.2 정식 운영에 부적합한 형태

- 개인 Tailscale 계정으로 직원 초대
- 실사용 보험·고객 데이터 처리
- 완전 폐쇄망에서의 사용
- 외부 SaaS 통신이 금지된 환경
- 전 직원 개인 노트북에 Tailscale을 설치하는 방식
- Tailscale Funnel을 이용한 공개 인터넷 URL

Tailscale은 로컬 LLM과 별개의 외부 네트워크 SaaS이다. 데이터 트래픽은 암호화되지만 장비 등록, 인증, 공개키 교환, 정책 및 일부 장비 메타데이터 처리를 위해 외부 Tailscale 제어 영역과 통신한다.

정식 운영에서는 내부 DNS와 HTTPS를 사용하는 것이 실무자에게도 더 간편하다.

## 8. URL과 HTTPS 구성

회사 내부 URL을 만들기 위해 다음 항목이 필요하다.

- 내부 DNS 레코드
- 회사 인증서 또는 사내 CA 인증서
- Nginx, Caddy 또는 회사 표준 Reverse Proxy
- 방화벽 443 포트 허용
- 실제 URL에 맞는 CORS 설정
- Secure 및 HttpOnly 인증 쿠키
- SSE 스트리밍을 위한 프록시 설정

애플리케이션은 다음처럼 로컬 주소에만 바인딩한다.

```text
FastAPI: 127.0.0.1:18080
Reverse Proxy: 사내망 IP의 443
```

운영 환경 변수 예시는 다음과 같다.

```text
API_COOKIE_SECURE=true
API_JWT_SECRET=<회사에서 생성한 강력한 비밀키>
API_CORS_ORIGINS=https://insurance-ai.company.local
```

## 9. 사용자 인증과 권한

### 9.1 파일럿

- 앱 내부 개별 계정
- 관리자, 직원, 조회자 역할 분리
- 강력한 비밀번호 정책
- 공용 계정 금지
- 사용자별 감사로그 기록

### 9.2 정식 운영

다음 중 회사가 사용하는 인증체계와 연동한다.

- Microsoft Entra ID
- Active Directory
- 사내 SSO
- OIDC
- SAML
- 사내 인증 Reverse Proxy

SSO 도입 시 기대 효과:

- 입사와 퇴사에 따른 권한 자동 반영
- MFA 적용
- 부서 및 직무 기반 접근통제
- 사용자별 감사추적
- 챗봇 비밀번호 별도 관리 제거

현재 앱에는 자체 로그인과 역할 관리가 있으나 회사 SSO 연동은 추가 개발 및 검증이 필요하다.

## 10. 운영 기능 조건

본격적인 회사 도입 전에 다음 기능을 준비해야 한다.

- `systemd` 또는 Docker 기반 자동 기동
- DGX 재부팅 후 웹앱과 LLM 자동 시작
- `/api/health` 기반 상태 점검
- CPU, GPU, 메모리, 디스크, 온도 모니터링
- 접속, 질문, 답변, 관리자 변경 감사로그
- 사용자 DB와 인덱스 정기 백업
- 암호화된 백업 저장소
- 백업 복원 시험
- 장애 및 용량 경고 알림
- 관리자 계정과 일반 사용자 계정 분리
- 모델 변경 승인 및 롤백 절차
- 문서와 인덱스 버전 관리
- 운영, 개발 및 검증 환경 분리

현재 SQLite는 파일럿에 사용할 수 있다. 다수 사용자가 지속적으로 사용하는 정식 운영에서는 회사 PostgreSQL 등 관리형 DB로 이전하는 방안을 검토한다.

## 11. 동시 사용자 및 성능 검증

DGX Spark 한 대가 처리할 수 있는 동시 사용자는 다음 조건에 따라 달라진다.

- LLM 크기와 양자화 방식
- 입력 문맥과 답변 길이
- 동시 질문 수
- 검색, 리랭킹 및 GraphDB 사용량
- 모델 서버의 배치 및 대기열 설정

도입 전 다음 단계로 부하 테스트를 진행한다.

```text
1명 -> 5명 -> 10명 -> 20명 동시 질문
```

각 단계에서 다음 항목을 기록한다.

- 첫 토큰 응답시간
- 전체 답변 완료시간
- GPU 및 통합 메모리 사용량
- 오류율
- 대기열 길이
- 애플리케이션 및 모델 서버 안정성

목표 동시 사용자가 많거나 응답 지연 허용 수준이 낮으면 DGX Spark 추가 도입 또는 더 큰 GPU 서버를 검토한다.

## 12. 보안 및 준법 검토

정식 도입 전 회사의 정보보호, 개인정보, 준법 및 IT 운영 부서와 다음 항목을 검토한다.

- 보험 원문 및 OCR 결과의 사용 권한
- 고객정보 및 개인정보 입력 가능성
- 사용자 질문과 답변의 보존기간
- 로그 열람 권한 및 파기 절차
- 모델 라이선스와 상업적 이용 조건
- 외부 통신 완전 차단 여부
- USB와 외장 저장장치 반입 절차
- 취약점 점검 및 패치 절차
- 계정 생성, 변경 및 회수 절차
- 관리자 작업 감사기록
- 장애 대응 및 복구 목표
- 개인 소유 장비와 계정의 완전한 분리

로컬 LLM을 사용하면 질문과 검색된 문서가 외부 생성형 AI API로 전송되지 않는 장점이 있다. 다만 운영 서버 자체의 네트워크, 사용자 접근, 로그 및 원문 데이터는 별도의 보안 통제가 필요하다.
