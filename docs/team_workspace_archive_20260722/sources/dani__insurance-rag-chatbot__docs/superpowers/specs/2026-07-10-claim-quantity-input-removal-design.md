# 보험금 계산 횟수/수량 입력 제거 개발 명세서

- 작성일: 2026-07-10
- 기준 코드: `88d8f4a` (`origin/master`와 Dani workspace HEAD 동일)
- 대상 기능: 보험금 계산 수동 입력 화면 및 계산 요청 변환
- 상태: 구현 전 승인 명세

## 1. 목적

보험금 계산 화면에서 사용자가 직접 입력하는 `횟수/수량` 필드를 제거한다.
세부내역서의 급여 본인부담금과 비급여 금액은 이미 해당 행의 합계이므로,
수량을 다시 곱하면 같은 비용이 중복 계산될 수 있다.

일반 세부내역서 입력은 다음 규칙으로 통일한다.

> 사용자는 세부내역서 각 행의 급여 본인부담금 합계와 비급여 합계를 입력하고,
> 클라이언트는 서버 요청에 `quantity="1"`을 자동으로 포함한다.

이 변경은 화면에서 불필요하고 위험한 입력을 없애는 것이 목적이다. API와 내부
모델의 `quantity` 필드는 기존 호출자와 특수 계산 경로의 호환성을 위해 즉시
삭제하지 않는다.

## 2. 배경

### 2.1 세부내역서 금액 구조

진료비 세부산정내역의 일반적인 한 행에는 다음 값이 함께 존재한다.

| 원본 열 | 의미 | 일반 계산 화면 입력 여부 |
|---|---|---|
| 금액 | 1회 또는 1단위 단가 | 입력하지 않음 |
| 횟수 | 같은 날의 사용 횟수 또는 수량 | 입력하지 않음 |
| 일수 | 적용 일수 | 입력하지 않음 |
| 총액 | `금액 × 횟수 × 일수` | 검증 자료로 사용 |
| 급여 본인부담금 | 환자가 부담한 급여 금액의 행 합계 | 입력 |
| 공단부담금 | 건강보험 공단 부담분 | 계산 금액으로 입력하지 않음 |
| 전액본인부담금 | 별도 심사 대상 금액 | 자동 합산하지 않고 검토 대상으로 분리 |
| 비급여 | 환자가 부담한 비급여 금액의 행 합계 | 입력 |

`급여 본인부담금`과 `비급여`는 이미 횟수와 일수가 반영된 행 합계다. 따라서
이 값을 입력한 다음 세부내역서의 횟수 또는 `횟수 × 일수`를 다시 입력하면
금액이 중복으로 증가한다.

### 2.2 현재 구현

현재 화면에는 다음 입력이 노출되어 있다.

```text
청구 항목명 / 수가·표준 코드 / 급여 본인부담금 / 비급여 금액 /
횟수·수량 / 항목 분류 힌트 / 기타 추가 정보
```

`frontend/js/pages/chat.js`는 사용자가 입력한 값을 `quantity`로 전송한다.
`src/claim_calculation/pipeline.py`의 `_line_amount_parts()`는 다음과 같이
급여 본인부담금과 비급여 금액에 수량을 곱한다.

```text
insured_copay = insured_copay_amount × quantity
nonpay = nonpay_amount × quantity
```

예를 들어 세부내역서 행의 급여 본인부담금 합계가 10,016원인데 사용자가
세부내역서의 횟수·일수를 합쳐 `4`를 입력하면 계산 기준 금액은 40,064원이
된다. 이는 보험 규칙의 문제가 아니라 입력 단위가 서로 다른 데서 발생하는
중복 곱셈이다.

### 2.3 기존 프로젝트 기준과의 정합성

`docs/235_HOSPITAL_RECEIPT_CLAIM_REQUIRED_FIELDS.md`는 이미 다음 원칙을
정의한다.

- 검증된 합계 금액을 계산 입력으로 사용한다.
- 합계 금액을 넣을 때 `quantity=1`을 사용한다.
- 원본의 단가, 횟수, 일수는 산식 검증과 증빙 추적용으로 보존한다.
- 급여/비급여 분리 입력에서도 합계 금액이면 `quantity=1`을 유지한다.

이번 명세는 기존 원칙을 수동 입력 화면과 API 경계에 일관되게 적용한다.

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| 단가 | 세부내역서의 `금액` 열 값 |
| 원본 횟수 | 세부내역서의 `횟수` 열 값 |
| 원본 일수 | 세부내역서의 `일수` 열 값 |
| 행 합계 | 하나의 세부내역서 행에 기재된 합계 금액 |
| 급여 본인부담금 합계 | 해당 행에서 환자가 부담한 급여 금액 |
| 비급여 합계 | 해당 행에서 환자가 부담한 비급여 금액 |
| 계산 요청 | 한 번의 통원 또는 한 번의 입원에 대한 `/claim/calculate` 요청 |
| 일반 항목 | 일별·회차별 특수 한도를 적용하지 않는 급여 또는 비급여 항목 |
| 일별 특례 항목 | 상급병실료 차액처럼 일수와 일별 한도가 계산에 필요한 항목 |

## 4. 설계 결정

### 4.1 채택안

일반 보험금 계산 화면에서 `횟수/수량` 입력칸을 제거한다. 프론트엔드는
사용자 입력 대신 항상 `quantity: "1"`을 요청 항목에 포함한다.

백엔드의 `ClaimItemRequest.quantity`와 `ClaimItemInput.quantity`는 다음
이유로 유지한다.

1. 기존 API 호출자와 저장된 스냅샷의 역호환성이 필요하다.
2. 현재 일부 내부 테스트와 특수 계산 경로가 이 필드를 참조한다.
3. 필드 전체 삭제는 별도 마이그레이션과 API 버전 변경이 필요한 작업이다.

즉, 이번 변경은 `quantity`의 완전 삭제가 아니라 **일반 사용자 입력에서의
제거와 합계 금액 기준의 1 고정**이다.

### 4.2 검토했지만 채택하지 않은 대안

#### 대안 A: 화면과 API에서 `quantity` 완전 삭제

- 장점: 데이터 의미가 단순해진다.
- 단점: 기존 API, 스냅샷, 후속 재계산, 상급병실료 계산을 동시에 변경해야 한다.
- 판단: 이번 요구 범위보다 크고 회귀 위험이 높아 채택하지 않는다.

#### 대안 B: 현재 입력칸을 유지하고 안내 문구만 추가

- 장점: 코드 변경량이 가장 적다.
- 단점: 사용자가 합계와 단가를 계속 혼동할 수 있고, 잘못된 곱셈을 시스템이
  허용한다.
- 판단: 금전 계산 입력에서 사용자 주의에만 의존하므로 채택하지 않는다.

#### 대안 C: 일반 화면에서 제거하고 특례 정보는 별도 필드로 분리

- 장점: 일반 입력은 단순해지고, 일수가 필요한 계산도 의미가 명확해진다.
- 단점: 특례 항목에 대한 조건부 UI와 계산 필드가 추가로 필요하다.
- 판단: 이번 명세의 채택안이다.

## 5. 범위

### 5.1 포함 범위

- 일반 보험금 계산 행에서 `횟수/수량` UI 제거
- 프론트엔드 요청에 `quantity: "1"` 자동 설정
- 사용자 메시지 요약에서 `× 1` 또는 `x 1` 표시 제거
- 행 초기화, 행 복제, 행 삭제 코드에서 `.claim-quantity` 의존 제거
- API에서 `quantity` 생략 시 기본값 `"1"` 유지
- 급여 본인부담금 또는 비급여 합계를 입력하면서 `quantity != 1`인 직접 API
  요청에 대한 방어 검증
- 기존 그룹 공제 로직과의 회귀 검증
- 일별 특례 항목의 일수를 일반 수량과 분리하는 인터페이스 정의
- 프론트엔드 번들 재생성 및 테스트

### 5.2 제외 범위

- `quantity` API 필드의 즉시 삭제
- DB 스키마 마이그레이션
- 약관 공제율, 최소공제, 보상한도 변경
- OCR 원본의 횟수·일수 삭제
- 여러 통원일을 하나의 요청에서 자동 분할하는 기능
- 전액본인부담금의 자동 보장 판정
- 과거 저장 스냅샷의 일괄 변환

## 6. 사용자 경험 명세

### 6.1 일반 항목 입력

변경 후 한 행에는 다음 필드를 표시한다.

```text
청구 항목명
수가/표준 코드
급여 본인부담금 합계
비급여 금액 합계
항목 분류 힌트
기타 추가 정보
```

라벨은 금액이 1회분이 아니라 합계임을 명확히 하기 위해 다음과 같이 변경한다.

- `급여 본인부담금` → `급여 본인부담금 합계`
- `비급여 금액` → `비급여 금액 합계`

플레이스홀더는 단가가 아니라 세부내역서 행 합계를 입력하도록 안내한다.

```text
세부내역서 해당 행의 본인부담금 합계
세부내역서 해당 행의 비급여 합계
```

별도의 사용 설명 문단을 화면에 추가하지 않는다. 라벨과 플레이스홀더만으로
입력 단위를 명확하게 한다.

### 6.2 계산 단위

한 번의 계산 요청은 다음 중 하나만 포함한다.

- 통원 1회
- 입원 1건

입원은 여러 날짜의 세부 항목을 포함할 수 있다. 같은 입원 시작일과 퇴원일에
속하는 항목은 하나의 계산 요청으로 처리한다.

통원 세부내역서가 여러 진료일을 포함하면 진료일별로 별도 요청을 생성해야 한다.
이번 변경에서 자동 분할하지 않으므로 UI 또는 운영 절차에서 한 요청에 여러
통원일을 섞지 않도록 해야 한다.

### 6.3 사용자 메시지

현재 메시지 예시는 다음과 같다.

```text
메디솝보더라이트 급여본인부담 10016원 / 비급여 0원 x 1
```

변경 후에는 다음처럼 표시한다.

```text
메디솝보더라이트 급여본인부담 합계 10016원 / 비급여 합계 0원
```

사용자에게 내부 호환 필드인 `quantity=1`을 노출하지 않는다.

## 7. 데이터 흐름

### 7.1 일반 수동 입력

```text
사용자
  → 행별 급여 본인부담금·비급여 합계 입력
  → 프론트엔드가 quantity="1" 생성
  → ClaimCalculationRequest
  → ClaimItemInput
  → 금액 파싱
  → 보장/면책 및 공제 그룹 분류
  → 동일 방문·동일 공제 그룹 합산
  → 그룹별 공제 1회 적용
  → 항목별 결과 배분 및 전체 결과 표시
```

메디솝보더라이트 예시는 다음과 같다.

```json
{
  "input_name": "메디솝보더라이트",
  "input_code": "M3010335",
  "insured_copay_amount": "10016",
  "nonpay_amount": "0",
  "quantity": "1"
}
```

### 7.2 OCR 입력

OCR은 원본의 단가, 횟수, 일수, 총액을 계속 추출하고 보존한다.

```text
단가 × 횟수 × 일수 = 총액
```

위 산식은 원본 행 검증에 사용한다. 검증된 행을 계산 요청으로 승격할 때는
급여 본인부담금 합계와 비급여 합계를 전달하고 `quantity="1"`을 설정한다.
현재 `src/hospital_receipt_ocr/claim_adapter.py`의 동작과 같은 방향이다.

원본 횟수와 일수는 `extra_info` 또는 OCR manifest에 남겨 감사와 재검증에
사용한다. 계산 금액에 다시 곱하지 않는다.

## 8. API 명세

### 8.1 호환 필드

`ClaimItemRequest.quantity`는 유지하며 기본값은 `"1"`로 둔다.

```python
quantity: str = "1"
```

웹 클라이언트는 입력 필드에서 값을 읽지 않고 항상 다음 값을 전송한다.

```javascript
quantity: '1'
```

### 8.2 합계 금액 입력 검증

`insured_copay_amount` 또는 `nonpay_amount`가 입력된 분리 금액 모드는 행 합계
입력으로 정의한다. 이 모드에서 직접 API 호출이 `quantity != 1`을 전달하면
자동 계산을 수행하지 않고 422 오류를 반환한다.

권장 오류 메시지:

```text
급여 본인부담금과 비급여 금액은 행 합계를 입력하므로 quantity는 1이어야 합니다.
```

서버가 임의로 값을 1로 덮어쓰지 않고 오류를 반환하는 이유는 외부 호출자의
입력 계약 위반을 숨기지 않기 위해서다. 웹 화면에서는 애초에 1만 전송하므로
일반 사용자에게 이 오류가 발생하지 않는다.

### 8.3 단일 `claimed_amount` 레거시 경로

`claimed_amount + quantity`를 사용하는 기존 호출은 이번 변경에서 제거하지
않는다. 다만 신규 웹 입력과 OCR 변환은 이 경로를 사용하지 않는다.

향후 API 버전 변경 시 다음 중 하나를 별도 결정한다.

- 단가 기반 입력을 명시하는 `amount_basis="unit"` 추가
- 합계 전용 API로 전환하고 `quantity` 폐기

이번 명세에서는 두 작업 모두 수행하지 않는다.

## 9. 일별 특례 항목

### 9.1 문제

현재 상급병실료 차액 계산은 `quantity`를 일수처럼 사용한다.

```text
일별 지급 기준 = min(1일 금액, 일별 한도)
지급액 = 일별 지급 기준 × 일수 × 지급비율
```

일반 수량 필드를 제거하면서 이 값을 무조건 1로 만들면 일별 한도 계산이
부정확해질 수 있다. 반대로 행 합계에 일수를 다시 곱하면 중복 계산된다.

### 9.2 명시적 일수 필드

일별 특례에는 `quantity` 대신 별도의 선택 필드를 사용한다.

```text
service_days: 양의 정수 또는 null
```

권장 데이터 모델:

```python
service_days: str = ""
```

상급병실료 차액처럼 일별 규칙이 확정된 항목에서만 `입원 일수` 입력을
조건부로 표시한다. 일반 항목에는 표시하지 않는다.

행 합계와 일수를 사용하는 산식은 다음과 같다.

```text
1일 평균 금액 = 상급병실료 차액 행 합계 ÷ service_days
지급액 = min(1일 평균 금액, 일별 한도) × service_days × 지급비율
```

`service_days`가 필요한 항목인데 값이 없거나 0 이하이면 1일로 추정하지 않고
자동 계산을 보류하여 Human Task로 보낸다.

### 9.3 단계적 전환

기존 `claimed_amount=1일 금액`, `quantity=일수` 호출은 당장 제거하지 않는다.
새로운 수동 UI와 OCR 경로는 `행 합계 + service_days + quantity=1`을 사용한다.

전환 기간에는 입력 형식을 명확히 구분해야 한다. 한 요청에서 다음 두 형식을
섞지 않는다.

- 레거시: 1일 금액 + quantity=일수
- 신규: 행 합계 + service_days=일수 + quantity=1

신규 형식이 안정화된 뒤 레거시 형식 폐기는 별도 작업으로 진행한다.

## 10. 그룹 공제와의 관계

최신 코드의 `_apply_grouped_deductibles()`는 동일 계산 요청의 동일 공제 그룹을
합산한 후 공제를 한 번 적용한다. 수량 입력 제거는 이 로직을 변경하지 않는다.

일반 처리 순서는 다음과 같아야 한다.

1. 각 행의 합계 금액을 읽는다.
2. 항목별 보장·면책·Human Task 여부를 결정한다.
3. 계산 가능한 항목을 급여, 일반 비급여, 3대비급여, MRI/MRA 등 공제 그룹으로
   분류한다.
4. 동일 방문의 동일 공제 그룹 금액을 합산한다.
5. 그룹 합계에 공제와 건당 한도를 한 번 적용한다.
6. 표시를 위해 공제액과 지급액을 항목별로 배분한다.

수량은 방문 횟수가 아니다. 세부내역서의 `횟수` 열을 통원 횟수로 사용해서는
안 된다.

## 13. 테스트 명세

### 13.1 프론트엔드 테스트

1. 보험금 계산 행에 `.claim-quantity`가 존재하지 않는다.
2. 금액 라벨에 `합계`가 표시된다.
3. 한 항목 요청 payload의 `quantity`가 항상 문자열 `"1"`이다.
4. 여러 항목도 각각 `quantity="1"`이다.
5. 사용자 메시지에 `x 1`, `× 1`이 나타나지 않는다.
6. 행 추가·삭제·초기화가 수량 DOM 없이 정상 동작한다.
7. 모바일·데스크톱에서 입력 필드와 버튼이 겹치지 않는다.

### 13.2 API 스키마 테스트

1. `quantity` 생략 시 `"1"`이 설정된다.
2. 분리 합계 입력에서 `quantity="1"`은 허용된다.
3. 분리 합계 입력에서 `quantity="2"`는 422로 거부된다.
4. `service_days="3"`은 허용된다.
5. `service_days="0"`, `"-1"`, `"1.5"`는 거부된다.

### 13.3 계산 파이프라인 테스트

1. 급여 본인부담금 10,016원, quantity 1의 청구 기준 금액은 10,016원이다.
2. 비급여 합계도 추가 곱셈 없이 그대로 사용된다.
3. 동일 통원 급여 항목 6,000원 두 개는 12,000원으로 그룹 합산되고 공제는
   한 번만 적용된다.
4. 동일 입원 급여 항목도 하나의 입원 공제 그룹으로 합산된다.
5. Human Task 또는 면책 항목은 그룹 합계에서 제외된다.
6. 신규 상급병실료 입력은 행 합계와 service_days로 1일 평균을 계산한다.
7. 상급병실료 service_days 누락 시 자동 지급 계산을 보류한다.
8. 레거시 상급병실료 입력은 호환 기간 동안 기존 결과를 유지한다.

## 16. 알려진 선행 상태와 위험

최신 master 기준 관련 Python 테스트 실행에서 다음 상태가 확인되었다.

- 동일 공제 그룹 전용 테스트: 통과
- 보험금 계산 파이프라인·API 묶음: 53개 통과, 1개 실패

실패 1건은 5세대 도수치료 API 테스트가 산정특례 상태를 입력하지 않은 채
지급액을 기대하는 기존 테스트 조건 불일치다. 수량 입력 제거와 직접 관련은
없지만, 구현 작업의 기준 테스트를 깨끗하게 만들기 위해 변경 전 별도 수정하거나
명시적으로 기준선 실패로 기록해야 한다.

추가 위험은 다음과 같다.

- 한 요청에 여러 통원일을 넣으면 현재 그룹 키가 하나의 방문으로 처리할 수 있다.
- 항목명만으로 상급병실료를 감지하면 오분류 가능성이 있으므로 코드·분류 결과와
  함께 판단해야 한다.
- 외부 API 호출자가 합계와 단가의 의미를 혼용할 수 있다.
- 소스만 수정하고 `frontend/dist/app.min.js`를 재생성하지 않으면 실제 화면과
  소스가 달라진다.

## 18. 최종 결정 요약

일반 보험금 계산에서 사용자가 입력하는 금액은 단가가 아니라 세부내역서의
급여 본인부담금·비급여 **행 합계**다. 따라서 일반 화면의 `횟수/수량`은
보험금 산정에 필요한 입력이 아니며, 합계 금액을 중복 곱하게 만드는 위험이 있다.

일반 화면에서는 수량 입력을 제거하고 서버 요청에 `quantity="1"`을 자동으로
전달한다. 원본 횟수와 일수는 계산 배수가 아니라 검증 증빙으로 보존한다.
일별 특례에서 필요한 일수는 의미가 다른 별도 필드로 처리한다.
